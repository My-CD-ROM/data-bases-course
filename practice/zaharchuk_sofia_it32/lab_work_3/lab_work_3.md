# Практика 3 — ER-діаграма (Варіант 6: Готель)

## Завдання 1. ER-діаграма повної схеми

​```mermaid
erDiagram
    rooms ||--o{ bookings : "бронюється в"
    guests ||--o{ bookings : "оформлює"

    rooms {
        int id PK
        string type
        real price_per_night
        int capacity
        string status
    }
    guests {
        int id PK
        string last_name
        string first_name
        string email
        string phone
    }
    bookings {
        int id PK
        int room_id FK
        int guest_id FK
        date check_in_date
        date check_out_date
    }
​```

## Завдання 2. Тип кожного зв'язку

- **rooms ||--o{ bookings** — 1:N. Рівно один номер готелю відповідає нулю або багатьом бронюванням: той самий номер за час роботи готелю бронюють десятки разів (або жодного разу, якщо номер щойно введений в експлуатацію), але кожне конкретне бронювання стосується рівно одного номера — не можна в одному бронюванні одночасно заброньювати два різні номери як одну позицію.
- **guests ||--o{ bookings** — 1:N. Рівно один гість відповідає нулю або багатьом бронюванням: постійний гість бронює номери багато разів, новий гість у базі — поки жодного разу, але кожне бронювання оформлює рівно один гість.

Прямого зв'язку між rooms і guests немає — вони пов'язані лише через bookings, яка з'єднує обидві вимірні таблиці.

## Завдання 3. Первинні й зовнішні ключі кожної таблиці

**rooms**
- PK: `id`
- FK: немає

**guests**
- PK: `id`
- FK: немає

**bookings**
- PK: `id`
- FK: `room_id` → посилається на `rooms.id`
- FK: `guest_id` → посилається на `guests.id`

## Завдання 4. Якщо додати ще одну сутність

Додав би сутність **staff** (персонал готелю: id, last_name, first_name, position, shift). Логічний новий зв'язок — між `staff` і `bookings`: один співробітник (наприклад, адміністратор на ресепшн) оформлює багато бронювань, але кожне конкретне бронювання оформлює рівно один співробітник. Це знову зв'язок **1:N** (`staff ||--o{ bookings`), реалізований новим зовнішнім ключем `staff_id` у таблиці `bookings`, що посилається на `staff.id`. Сутність `staff` при цьому лишається "вимірною" — має власний PK і не отримує жодного FK, точно як `rooms` і `guests`.

## Завдання 5. Порівняння з прикладом (Хімчистка)

Моя діаграма структурно ідентична прикладу з хімчистки: дві вимірні таблиці (`rooms` і `guests` — аналогічно `services` і `clients`) та одна фактова таблиця (`bookings` — аналогічно `orders`) із двома зовнішніми ключами. Обидва зв'язки в обох діаграмах — 1:N: у хімчистці послуга/клієнт відповідають багатьом замовленням, у готелі номер/гість відповідають багатьом бронюванням. І в обох випадках дві вимірні таблиці не пов'язані одна з одною напряму — лише через фактову таблицю, яка й фіксує конкретну подію (замовлення чистки / бронювання номера).

## Контрольні питання

**1. Чим логічна модель відрізняється від концептуальної, і чим фізична — від логічної?**

Концептуальна модель описує сутності й зв'язки словами чи малюнком, узагалі без типів даних і без прив'язки до того, що це буде реляційна база (наприклад: "є номери, є гості, гість бронює номер на певні дати"). Логічна модель — той самий зміст, розкладений на майбутні таблиці й стовпці з абстрактними типами ("текст", "ціле число", "дата"), але ще без прив'язки до конкретної СУБД. Фізична модель — це вже конкретний SQL DDL для конкретної СУБД: точні типи (наприклад, `INTEGER`/`TEXT`/`REAL` у SQLite чи `SERIAL`/`VARCHAR`/`SMALLINT` у PostgreSQL), точні обмеження й точний синтаксис `CREATE TABLE`.

**2. Чому зв'язок M:N не можна реалізувати двома зовнішніми ключами в одній із двох основних таблиць і завжди потрібна окрема таблиця?**

Якщо додати зовнішній ключ до однієї з двох основних таблиць, у нього можна записати лише одне значення на рядок — а при зв'язку M:N кожен екземпляр однієї сутності пов'язаний з кількома екземплярами іншої одночасно. Один стовпець фізично не може зберігати кілька значень одночасно без порушення самої ідеї реляційної колонки (одне значення — один стовпець — один рядок). Тому M:N завжди розв'язується через окрему проміжну таблицю з двома FK, яка перетворює один зв'язок M:N на два звичайні зв'язки 1:N.

**3. Що означають позначення ||, o{, |{ у синтаксисі mermaid erDiagram, і як прочитати вголос рядок A ||--o{ B?**

`||` означає "рівно один", `o{` означає "нуль або більше", `|{` означає "один або більше" (а `|o` — "нуль або один"). Рядок `A ||--o{ B` читається так: "рівно один екземпляр A відповідає нулю або багатьом екземплярам B" — тобто це стандартний запис зв'язку 1:N, де A — сторона "один", а B — сторона "багато".

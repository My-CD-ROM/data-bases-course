## Завдання 4. Перевірка DEFAULT

Для таблиці `viewers` було додано обмеження `DEFAULT` до поля `phone`. Якщо під час додавання нового глядача номер телефону не вказується, SQLite автоматично встановлює значення `'не вказано'`.

Для перевірки було виконано:

```sql
INSERT INTO viewers (last_name, first_name, email)
VALUES (
    'Іваненко',
    'Олексій',
    'oleksii.ivanenko@gmail.com'
);
```

Після цього виконано запит:

```sql
SELECT *
FROM viewers
WHERE email = 'oleksii.ivanenko@gmail.com';
```

У результаті для нового глядача поле `phone` отримало значення:

```text
не вказано
```

Отже, обмеження `DEFAULT` працює правильно.

## Завдання 5. Перевірка через UPDATE

Для перевірки обмеження `CHECK` було виконано спробу змінити тривалість фільму на від'ємне значення:

```sql
UPDATE movies
SET duration_min = -10
WHERE title = 'Інтерстеллар';
```

SQLite повертає помилку:

```text
CHECK constraint failed: duration_min > 0
```

Це підтверджує, що обмеження `CHECK` діє не тільки під час вставки нового запису, а й під час оновлення вже існуючого запису.

## Завдання 6. Обґрунтування обмежень

Обмеження `NOT NULL` застосовано до поля `last_name` таблиці `viewers`, тому що кожен глядач кінотеатру повинен мати зазначене прізвище, а відсутність цього значення робить інформацію про глядача неповною.

Обмеження `UNIQUE` застосовано до поля `email` таблиці `viewers`, тому що електронна адреса повинна однозначно відповідати конкретному глядачеві й не повинна повторюватися в декількох записах.

Обмеження `CHECK (duration_min > 0)` застосовано до поля `duration_min` таблиці `movies`, тому що тривалість фільму не може бути нульовою або від'ємною і повинна мати додатне значення в хвилинах.

Обмеження `DEFAULT 'не вказано'` застосовано до поля `phone` таблиці `viewers`, тому що номер телефону є додатковою інформацією і для нового глядача може бути невідомим, тому замість порожнього значення встановлюється зрозуміле значення за замовчуванням.

## Контрольні питання

### 1. Чому в SQLite неможливо просто виконати ALTER TABLE ... ADD CONSTRAINT CHECK (...)?

SQLite має обмежені можливості команди `ALTER TABLE` і не підтримує додавання довільного обмеження `CONSTRAINT` до вже існуючого стовпця через `ALTER TABLE ... ADD CONSTRAINT`. Тому таблицю необхідно перейменувати, створити заново з потрібним обмеженням, перенести до неї дані та видалити стару таблицю.

### 2. Що станеться, якщо перестворити таблицю, додавши NOT NULL до стовпця, у якому серед наявних рядків уже є NULL?

Під час перенесення даних до нової таблиці виникне помилка `NOT NULL constraint failed`, оскільки існуючі `NULL`-значення не відповідають новому обмеженню `NOT NULL`.

### 3. Чим CHECK, доданий через перестворення таблиці, відрізняється від CHECK, оголошеного одразу при CREATE TABLE?

Функціонально вони не відрізняються: після перестворення таблиці `CHECK` діє так само, як і обмеження, оголошене під час початкового створення таблиці, тобто перевіряє нові та змінені значення.

### 4. Чому DEFAULT не можна перевірити тим самим способом, що й NOT NULL, UNIQUE та CHECK?

`DEFAULT` не забороняє певні значення, а автоматично підставляє значення, коли користувач не вказує відповідне поле, тому його перевіряють вставкою нового запису без цього поля та подальшим `SELECT`.

## Висновок

У ході практичної роботи було застосовано чотири основні обмеження цілісності даних SQLite: `NOT NULL`, `UNIQUE`, `CHECK` та `DEFAULT`. Оскільки SQLite не дозволяє додавати такі обмеження до вже існуючих таблиць звичайною командою `ALTER TABLE ... ADD CONSTRAINT`, таблиці було перестворено із збереженням наявних даних. Робота показала, що `NOT NULL` забороняє пропускати обов'язкові значення, `UNIQUE` не допускає дублювання унікальних значень, `CHECK` контролює допустимий діапазон даних, а `DEFAULT` автоматично встановлює значення, якщо користувач його не задав. Також було підтверджено, що обмеження `CHECK` працює як під час `INSERT`, так і під час `UPDATE`.

## Завдання 1. UPDATE у фактовій таблиці

Фактовою таблицею у варіанті є таблиця `tickets`, яка містить інформацію про придбані квитки. Для перевірки команди `UPDATE` було оновлено один конкретний запис за первинним ключем `id = 1`.

Було змінено час сеансу:

```sql
UPDATE tickets
SET showtime = '2026-09-20 18:30'
WHERE id = 1;
```

Оскільки умова `WHERE id = 1` використовує первинний ключ, команда змінює тільки один конкретний рядок.

## Завдання 2. UPDATE у таблиці-вимірі

У таблиці `viewers` було оновлено номер телефону одного конкретного глядача:

```sql
UPDATE viewers
SET phone = '+380671234567'
WHERE id = 1;
```

Команда `UPDATE` є доречною, оскільки номер телефону є змінною характеристикою вже існуючого глядача, тому немає потреби видаляти старий запис і створювати новий, адже сам глядач залишається тією самою особою.

## Завдання 3. DELETE одного рядка

Для перевірки видалення було використано таблицю `tickets`. Спочатку було визначено кількість записів:

```sql
SELECT COUNT(*) AS count_before_delete
FROM tickets;
```

Початкова кількість квитків становила:

```text
10
```

Після цього було видалено один конкретний квиток за первинним ключем:

```sql
DELETE FROM tickets
WHERE id = 10;
```

Після видалення повторно виконано:

```sql
SELECT COUNT(*) AS count_after_delete
FROM tickets;
```

Кількість записів після видалення становила:

```text
9
```

Отже, було видалено саме один рядок із таблиці `tickets`.

## Завдання 4. Перевірка ON DELETE на реальних даних

У таблиці `tickets` зовнішній ключ `viewer_id` пов'язаний із таблицею `viewers` таким правилом:

```sql
FOREIGN KEY (viewer_id)
    REFERENCES viewers(id)
    ON DELETE CASCADE
```

Перед видаленням було перевірено глядача з `id = 6` та пов'язаний із ним квиток.

Для глядача `id = 6` існує один пов'язаний квиток:

```text
ticket id = 6
viewer_id = 6
```

### Прогноз

Оскільки для зовнішнього ключа `viewer_id` встановлено `ON DELETE CASCADE`, прогнозувалося, що після видалення глядача з `id = 6` пов'язаний із ним запис у таблиці `tickets` також буде автоматично видалений.

Для перевірки було виконано:

```sql
DELETE FROM viewers
WHERE id = 6;
```

Після цього було виконано:

```sql
SELECT *
FROM tickets
WHERE viewer_id = 6;
```

Результат не містить жодного запису.

До видалення кількість пов'язаних квитків становила:

```text
tickets_before_cascade = 1
```

Після видалення:

```text
tickets_after_cascade = 0
```

### Фактичний результат

Фактичний результат повністю відповідає прогнозу: після видалення глядача `id = 6` пов'язаний із ним квиток був автоматично видалений завдяки `ON DELETE CASCADE`.

## Контрольні питання

### 1. Чим UPDATE ... SET колонка = колонка + 1 відрізняється від UPDATE ... SET колонка = конкретне число?

Конструкція `SET колонка = колонка + 1` змінює поточне значення відносно його попереднього стану, додаючи до нього одиницю, тоді як `SET колонка = конкретне число` повністю замінює поточне значення на вказане число.

### 2. Чому NOT NULL, UNIQUE і CHECK завжди перевіряються при UPDATE, тоді як FOREIGN KEY залежить від PRAGMA foreign_keys = ON?

`NOT NULL`, `UNIQUE` і `CHECK` є вбудованими обмеженнями самої таблиці, тому SQLite перевіряє їх під час зміни даних, а контроль зовнішніх ключів у SQLite потрібно явно увімкнути за допомогою `PRAGMA foreign_keys = ON`.

### 3. Якби FOREIGN KEY мав ON DELETE CASCADE замість RESTRICT, як змінилися б наслідки?

При `ON DELETE CASCADE` видалення рядка з таблиці-виміру автоматично призвело б до видалення всіх пов'язаних рядків фактової таблиці, тоді як `ON DELETE RESTRICT` забороняє видалення батьківського рядка, якщо на нього існують посилання.

### 4. Чому DELETE без WHERE небезпечніший?

Команда `DELETE` без `WHERE` видаляє всі рядки таблиці, тому одна помилка в команді може призвести до втрати всіх даних, тоді як використання умови `WHERE` дозволяє обмежити видалення конкретними записами.

## Висновок

У ході практичної роботи було застосовано команди `UPDATE` та `DELETE` до фактової таблиці `tickets` і таблиці-виміру `viewers`. Було оновлено конкретний квиток, змінено номер телефону глядача та видалено один квиток із перевіркою кількості записів до і після операції. Також на реальних даних було перевірено дію `ON DELETE CASCADE`: після видалення глядача автоматично видалився пов'язаний із ним квиток. Це підтвердило фактичну роботу зовнішнього ключа та каскадного видалення в SQLite.

## Завдання 1. Увімкнення зовнішніх ключів

Для забезпечення контролю зв'язків між таблицями було увімкнено підтримку зовнішніх ключів за допомогою команди:

```sql
PRAGMA foreign_keys = ON;
```

Команда виконана успішно.

## Завдання 2. Створення таблиці глядачів

Було створено таблицю `viewers`, яка містить інформацію про глядачів кінотеатру.

Структура таблиці:

| Поле       | Тип     | Обмеження   |
| ---------- | ------- | ----------- |
| id         | INTEGER | PRIMARY KEY |
| last_name  | TEXT    | NOT NULL    |
| first_name | TEXT    | NOT NULL    |
| email      | TEXT    | NOT NULL    |
| phone      | TEXT    |             |

Первинним ключем таблиці є поле `id`, яке однозначно ідентифікує кожного глядача.

До таблиці було додано 6 записів.

## Завдання 3. Створення таблиці квитків та встановлення зв'язків

Було створено таблицю `tickets`, яка містить інформацію про придбані квитки.

Структура таблиці:

| Поле          | Тип     | Обмеження             |
| ------------- | ------- | --------------------- |
| id            | INTEGER | PRIMARY KEY           |
| movie_id      | INTEGER | NOT NULL, FOREIGN KEY |
| viewer_id     | INTEGER | NOT NULL, FOREIGN KEY |
| hall          | TEXT    | NOT NULL              |
| showtime      | TEXT    | NOT NULL              |
| price         | REAL    | NOT NULL              |
| seat          | TEXT    | NOT NULL              |
| purchase_date | TEXT    | NOT NULL              |

Для поля `movie_id` встановлено зовнішній ключ на `movies(id)` з правилом:

```sql
ON DELETE RESTRICT
```

Це правило не дозволяє видалити фільм, якщо для нього вже існують пов'язані квитки.

Для поля `viewer_id` встановлено зовнішній ключ на `viewers(id)` з правилом:

```sql
ON DELETE CASCADE
```

Це означає, що під час видалення глядача пов'язані з ним квитки будуть видалені автоматично.

Таким чином, таблиця `tickets` пов'язує таблиці `movies` та `viewers`.

## Завдання 5. Перевірка зовнішнього ключа

Для перевірки роботи обмежень цілісності було виконано спробу додати квиток із неіснуючим `viewer_id = 999`:

```sql
INSERT INTO tickets
    (movie_id, viewer_id, hall, showtime, price, seat, purchase_date)
VALUES
    (1, 999, 'Зал 1', '2026-09-26 18:00', 180.00, 'E1', '2026-09-22');
```

У результаті SQLite відхилив операцію та вивів повідомлення:

```text
FOREIGN KEY constraint failed
```

Це підтверджує, що зовнішні ключі працюють і база даних не дозволяє створювати записи з посиланням на неіснуючого глядача.

## Завдання 6. Порівняння з ER-діаграмою

Фактична структура бази даних відповідає ER-діаграмі, створеній у Практичній роботі №3 для предметної області «Кінотеатр».

У базі даних присутні три основні таблиці: `movies`, `viewers` та `tickets`. Таблиця `movies` містить інформацію про фільми та має первинний ключ `id`. Таблиця `viewers` містить інформацію про глядачів і також має первинний ключ `id`. Таблиця `tickets` є фактичною таблицею, яка пов'язує фільми та глядачів.

У таблиці `tickets` визначено два зовнішні ключі: `movie_id` посилається на `movies.id`, а `viewer_id` посилається на `viewers.id`. Таким чином, реалізовані зв'язки, передбачені ER-діаграмою: один фільм може мати багато квитків, а один глядач може придбати багато квитків.

Також у базі даних реалізовано правила видалення. Для зв'язку з таблицею `movies` використано `ON DELETE RESTRICT`, щоб не дозволити видалити фільм, якщо для нього вже існують квитки. Для зв'язку з таблицею `viewers` використано `ON DELETE CASCADE`, тому при видаленні глядача пов'язані з ним квитки видаляються автоматично.

Отже, фактична структура таблиць, первинні та зовнішні ключі, а також зв'язки між сутностями відповідають розробленій ER-діаграмі.

Під час практичної роботи було створено та заповнено таблиці `viewers` і `tickets`, встановлено первинні та зовнішні ключі, а також налаштовано правила видалення пов'язаних записів. Було додано 6 глядачів і 10 квитків. За допомогою навмисної спроби додавання некоректного запису перевірено роботу зовнішнього ключа та отримано повідомлення `FOREIGN KEY constraint failed`. Отримана структура бази даних відповідає ER-діаграмі, розробленій у попередній практичній роботі.

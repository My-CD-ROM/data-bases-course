# Практика 5. Обмеження цілісності даних: NOT NULL, UNIQUE, CHECK, DEFAULT

**Варіант 2 — Інтернет-магазин одягу**

Обидві таблиці-вимір з Практики 4 (`products`, `clients`) перестворено чотири рази поспіль — по одному обмеженню за раз, за рецептом `RENAME TO ... старе` → `CREATE TABLE` з новим обмеженням → `INSERT ... SELECT *` → `DROP TABLE`. Перед перестворенням увімкнено `PRAGMA legacy_alter_table = ON;`, інакше SQLite сам підмінює ім'я таблиці у `FOREIGN KEY` фактової таблиці `orders` на тимчасове `_old` — це ламало б зв'язок; після завершення pragma повернена в OFF.

## Завдання 1. NOT NULL

Обрано `products.category` — до цього колонка не мала жодного обмеження, а категорія товару в магазині одягу завжди повинна бути вказана (без неї товар не потрапляє в жоден розділ каталогу).

Спроба вставити товар без категорії:

```sql
INSERT INTO products (name, size, price, stock_quantity)
VALUES ('Шарф', 'один розмір', 199, 10);
```

Текст помилки:

```
NOT NULL constraint failed: products.category
```

## Завдання 2. UNIQUE

Обрано `clients.email` — email клієнта змістовно унікальний ідентифікатор облікового запису, дублікати означали б два акаунти на одну й ту саму людину.

Спроба вставити клієнта з email, що вже є в базі (`olena.k@mail.com`):

```sql
INSERT INTO clients (full_name, email, phone, registration_date)
VALUES ('Тест Клієнт', 'olena.k@mail.com', '0000000000', '2026-09-23');
```

Текст помилки:

```
UNIQUE constraint failed: clients.email
```

## Завдання 3. CHECK

Обрано `products.price` з умовою `CHECK (price > 0)` — ціна товару фізично не може бути нульовою чи від'ємною.

- Порушення: `INSERT INTO products (name, category, size, price, stock_quantity) VALUES ('Бракований товар', 'Тест', 'M', -50, 5);` → помилка:
  ```
  CHECK constraint failed: price > 0
  ```
- Коректна вставка (без помилок): `INSERT INTO products (name, category, size, price, stock_quantity) VALUES ('Шарф вовняний', 'Аксесуари', 'один розмір', 220, 15);` — виконано успішно, рядок додано.

## Завдання 4. DEFAULT

Обрано `clients.registration_date` з `DEFAULT (date('now'))` та `NOT NULL` — якщо дату реєстрації не вказали вручну, система повинна сама проставити поточну дату, а не залишати клієнта без дати реєстрації.

Вставка без цієї колонки:

```sql
INSERT INTO clients (full_name, email, phone)
VALUES ('Дмитро Литвин', 'dmytro.l@mail.com', '0631112233');
```

Підтверджене значення через `SELECT`:

```sql
SELECT registration_date FROM clients WHERE full_name = 'Дмитро Литвин';
-- 2026-09-23
```

Підставилась саме поточна дата — рівно те значення, яке й очікувалось.

## Завдання 5. Перевірка через UPDATE

Обрано обмеження CHECK із Завдання 3. Замість нового INSERT порушено вже наявний рядок командою:

```sql
UPDATE products SET price = -100 WHERE id = 1;
```

Текст помилки:

```
CHECK constraint failed: price > 0
```

Обмеження CHECK діє однаково і при вставці нового рядка, і при оновленні вже наявного — SQLite перевіряє його на кожну зміну значення колонки, незалежно від того, яким запитом ця зміна виконується.

## Завдання 6. Письмовий висновок

- **NOT NULL (`products.category`)** — без категорії товар не можна коректно показати покупцю в каталозі магазину одягу, тому це поле не може лишатись порожнім.
- **UNIQUE (`clients.email`)** — email слугує унікальним ідентифікатором клієнта в системі, і дозволити дублікати означало б втратити однозначний зв'язок "один email — один клієнт".
- **CHECK (`products.price > 0`)** — ціна товару за визначенням додатна величина, і допущення нуля чи від'ємних значень зробило б неможливими коректні розрахунки суми замовлення.
- **DEFAULT (`clients.registration_date`)** — дата реєстрації потрібна для аналітики клієнтської бази (скільки часу клієнт у програмі), і природно, що якщо оператор її не вказав вручну, система підставляє поточну дату, а не залишає поле незаповненим.

# Практика 19. Створення бази даних у PostgreSQL (варіант 2, інтернет-магазин одягу)

## Що зроблено
Створено базу `clothing_store_db` із таблицями `products`, `clients` (виміри) та `orders` (факти). Дані перенесено з `lab_work_18.db` через CSV: 24, 5 і 10 рядків відповідно.

Зміни під час перекладу структури:
- `INTEGER PRIMARY KEY` замінено на `INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY`;
- дати `registration_date` та `order_date` оголошено типом `DATE` замість `TEXT`, а `date('now')` замінено на `CURRENT_DATE`;
- згенеровані стовпці з практики 18 оголошено як `STORED` (у SQLite вони були `VIRTUAL`), прапорець `low_stock` отримав тип `BOOLEAN`;
- обмеження `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT` і правила `ON DELETE` збережено.

## Контрольні питання

### 1. Чим PostgreSQL відрізняється від SQLite і яка в ньому ієрархія об'єктів?
SQLite зберігає всю базу в одному файлі й працює без окремого сервера: програма сама читає та змінює файл. PostgreSQL є клієнт-серверною СУБД: серверний процес працює постійно, приймає з'єднання від багатьох клієнтів одночасно й сам керує доступом до даних. Ієрархія об'єктів: сервер → база даних → схема → таблиця (за замовчуванням схема `public`).

### 2. Чому обрано `GENERATED ALWAYS AS IDENTITY`, а не `SERIAL`?
`IDENTITY` є стандартним синтаксисом SQL. `SERIAL` є лише скороченням PostgreSQL: він створює колонку `INTEGER`, окрему послідовність і `DEFAULT nextval(...)`. Для `SERIAL` явно вказане значення `id` мовчки замінює значення за замовчуванням, тому легко отримати конфлікт. `GENERATED ALWAYS` відхиляє звичайний `INSERT` з явним `id` (потрібне `OVERRIDING SYSTEM VALUE`; команда `COPY`, якою користується імпорт, записує значення з файлу). Крім того, послідовність identity-колонки є її невід'ємною частиною.

### 3. Чому таблиці-виміри переносять перед фактовою?
`orders` має зовнішні ключі на `products` і `clients`. Її неможливо створити, поки не існують таблиці, на які вона посилається. Під час імпорту кожне значення `product_id` і `client_id` (крім `NULL`) перевіряється, тому відповідні рядки вимірів уже мають бути в базі. Інакше імпорт завершиться помилкою зовнішнього ключа й жоден рядок не додасться.

### 4. Що сталося б без завдання 4?
Створення таблиць та імпорт CSV пройшли б без помилок. Проблема виникла б на першому `INSERT` без явного `id`: лічильник не знає про імпортовані значення й видав би `id = 1`, який уже зайнятий. Результат: `duplicate key value violates unique constraint "products_pkey"`, `Key (id)=(1) already exists.` (для інших таблиць аналогічно).

### 5. Для чого потрібні pgAdmin і Query Tool?
pgAdmin є графічним інструментом для керування сервером PostgreSQL: створення баз і таблиць, перегляд даних, імпорт та експорт. Це аналог програми DB Browser for SQLite. Query Tool призначений для написання й виконання SQL-запитів і відповідає вкладці Execute SQL у DB Browser.

### 6. Чому більше не потрібна `PRAGMA foreign_keys`?
У SQLite перевірка зовнішніх ключів за замовчуванням вимкнена, і її вмикають командою `PRAGMA foreign_keys = ON` для кожного з'єднання. У PostgreSQL обмеження `FOREIGN KEY` перевіряються завжди. Команди `PRAGMA` в ньому взагалі немає.

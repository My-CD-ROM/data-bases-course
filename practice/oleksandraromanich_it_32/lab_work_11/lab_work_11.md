## Завдання 1. Проєктування й створення нової таблиці

Для потреб варіанта «Бібліотека» створено **таблицю зв'язку «багато-до-багатьох»** між `books` і `readers` під назвою `reservations` (бронювання). Це окрема дія, відмінна від позики `loans` — бронь оформлюють **наперед**, навіть на книгу, яку ще нікому не видавали.

**Структура таблиці:**

```sql
CREATE TABLE reservations (
    id             INTEGER PRIMARY KEY,
    book_id        INTEGER NOT NULL,
    reader_id      INTEGER NOT NULL,
    reserved_date  TEXT NOT NULL,
    status         TEXT NOT NULL DEFAULT 'активне'
                   CHECK (status IN ('активне', 'скасоване', 'виконане')),
    FOREIGN KEY (book_id)   REFERENCES books(id)   ON DELETE CASCADE,
    FOREIGN KEY (reader_id) REFERENCES readers(id) ON DELETE CASCADE
);
```

**Обґрунтування колонок:**

- `id INTEGER PRIMARY KEY` — сурогатний первинний ключ, стандарт для таблиць зв'язку.
- `book_id INTEGER NOT NULL` — FK на `books.id`. Бронь без книги безглузда.
- `reader_id INTEGER NOT NULL` — FK на `readers.id`. Бронь без читача безглузда.
- `reserved_date TEXT NOT NULL` — дата оформлення броні. Потрібна для фільтрації у Завданні 4.
- `status TEXT NOT NULL DEFAULT 'активне'` — стан броні (`активне`/`скасоване`/`виконане`). `DEFAULT 'активне'` — нова бронь за замовчуванням активна (найпоширеніший випадок). `CHECK` обмежує статус трьома дозволеними значеннями, не дає вписати довільний текст.

**Обмеження `ON DELETE CASCADE`** для обох FK — при видаленні книги або читача його броні автоматично зникають.

**Наповнення (12 рядків):**

```sql

    (1,  1, '2025-03-01', 'активне'),
    (1,  3, '2025-03-02', 'активне'),
    (1,  4, '2025-03-03', 'активне'),
    (2,  2, '2025-03-05', 'активне'),
    (2,  5, '2025-03-06', 'активне'),
    (5,  2, '2025-03-10', 'активне'),
    (5,  3, '2025-03-11', 'активне'),
    (5,  4, '2025-03-12', 'активне'),
    (5,  5, '2025-03-13', 'активне'),
    (6,  1, '2025-03-15', 'активне'),
    (7,  2, '2025-03-16', 'скасоване'),

```

Розподіл за книгами:
- `book_id = 1` (Кобзар) — 3 броні

## Завдання 2. JOIN + GROUP BY

```sql
SELECT books.id, books.title, COUNT(reservations.id) AS reservations_count
FROM books
JOIN reservations ON reservations.book_id = books.id
GROUP BY books.id;
```

**Результат:**

```
id | title                                   | reservations_count
---+-----------------------------------------+-------------------
1  | Кобзар                                  | 3
2  | Місто                                   | 2
5  | Гаррі Поттер і філософський камінь      | 4
6  | Чорний обеліск                          | 2
7  | Відьмак. Останнє бажання                | 1
```

Групування — за `books.id`, а не за `books.title` (щоб уникнути пастки «однакова назва в різних книгах»).

## Завдання 3. Додаємо HAVING

```sql
SELECT books.id, books.title, COUNT(reservations.id) AS reservations_count
FROM books
JOIN reservations ON reservations.book_id = books.id
GROUP BY books.id
HAVING COUNT(reservations.id) >= 3;
```

**Результат:**

```
id | title                                   | reservations_count
---+-----------------------------------------+-------------------
1  | Кобзар                                  | 3
5  | Гаррі Поттер і філософський камінь      | 4
```

Поріг `>= 3` обрано так, щоб **відсіялися** книги «Місто» (2), «Чорний обеліск» (2) і «Відьмак» (1), але **не всі** — залишилися дві групи-лідери. Якби взяли `>= 4`, залишився б лише «Гаррі Поттер». Якби `>= 2` — усі 5 груп пройшли б, і `HAVING` нічого не змінив би.

## Завдання 4. WHERE + JOIN + GROUP BY + HAVING

```sql
SELECT books.id, books.title, COUNT(reservations.id) AS active_count
FROM books
JOIN reservations ON reservations.book_id = books.id
WHERE reservations.status = 'активне'
GROUP BY books.id
HAVING COUNT(reservations.id) >= 3;
```

**Результат:**

```
id | title                                   | active_count
---+-----------------------------------------+-------------
1  | Кобзар                                  | 3
5  | Гаррі Поттер і філософський камінь      | 4
```

**Що робить WHERE:** відсіює **окремі броні** зі статусом `'скасоване'` або `'виконане'`. Наприклад, скасована бронь «Відьмака» від читача Коваленко — зникає. Виконане бронювання «Чорного обеліска» — теж зникає.

**Що робить HAVING:** відсіює **цілі книги (групи)** за кількістю **активних** броней після `WHERE`. Наприклад, «Чорний обеліск» має 2 броні, але після `WHERE` залишилася лише 1 активна — тому він не проходить `HAVING >= 3`.

**Різниця:**
- `WHERE` фільтрує **окремі рядки `reservations`** за статусом.
- `HAVING` фільтрує **книги (групи)** за кількістю броней, що залишилися після `WHERE`.

Це дві різні дії на різних етапах конвеєра (`FROM → WHERE → GROUP BY → HAVING → SELECT`).

## Завдання 5. Два експерименти і письмовий висновок

### (а) Пастка групування

Додано книгу-«двійник» із тією самою назвою «Кобзар», але іншим `id` і автором:

```sql
INSERT INTO books (title, author, publication_year, genre, copies_count)
VALUES ('Кобзар', 'Інший автор', 1900, 'поезія', 1);

INSERT INTO reservations (book_id, reader_id, reserved_date, status) VALUES
    (24, 1, '2025-03-20', 'активне'),
    (24, 2, '2025-03-21', 'активне');
```

**Запит із групуванням за `title` (неправильно):**

```sql
SELECT books.title, COUNT(reservations.id) AS reservations_count
FROM books
JOIN reservations ON reservations.book_id = books.id
GROUP BY books.title;
```

**Результат:**

```
title                                   | reservations_count
----------------------------------------+-------------------
Кобзар                                  | 5
Місто                                   | 2
Гаррі Поттер і філософський камінь      | 4
Чорний обеліск                          | 2
Відьмак. Останнє бажання                | 1
```

**Порівняння з правильним запитом (групування за `id`):**

```
id | title                                   | reservations_count
---+-----------------------------------------+-------------------
1  | Кобзар                                  | 3
24 | Кобзар                                  | 2
2  | Місто                                   | 2
5  | Гаррі Поттер і філософський камінь      | 4
6  | Чорний обеліск                          | 2
7  | Відьмак. Останнє бажання                | 1
```

**Висновок:** групування за `title` помилково **об'єднало дві різні книги з однаковою назвою** в одну групу з 5 бронюваннями. Це виглядає так, ніби «Кобзар» — найпопулярніша книга з 5 бронями, хоча насправді їх дві: перша (справжня, Тарас Шевченко) має 3 броні, друга (`id = 24`) — 2. Групування за `id` дає **правильний результат** — кожна книга окремо.

**Мораль:** завжди групуйте за **первинним ключем** (`id`), а не за текстовою колонкою. Назви можуть збігатися у різних об'єктів — і тоді групування за назвою «зливає» їхні дані в одну групу.

### (б) LEFT JOIN замість JOIN у Завданні 4

```sql
SELECT books.id, books.title, COUNT(reservations.id) AS active_count
FROM books
LEFT JOIN reservations ON reservations.book_id = books.id
WHERE reservations.status = 'активне'
GROUP BY books.id
HAVING COUNT(reservations.id) >= 3;
```

**Результат:**

```
id | title                                   | active_count
---+-----------------------------------------+-------------
1  | Кобзар                                  | 3
5  | Гаррі Поттер і філософський камінь      | 4
```

**Результат не змінився** — ті самі 2 рядки, що й у Завданні 4 з `INNER JOIN`.

**Чому:** хоча LEFT JOIN мав би додати в результат книги **без жодної броні** (наприклад, «Тіні забутих предків» з `id = 3`), умова `WHERE reservations.status = 'активне'` **відсіює** рядки з `NULL` у колонках `reservations` (бо `NULL = 'активне'` дає `NULL`, не `TRUE`). Тобто книги без бронювань **не доходять** до `GROUP BY` і не можуть потрапити в результат, незважаючи на LEFT JOIN.

**Щоб побачити справжню різницю**, треба було б **перенести умову в ON**:

```sql
SELECT books.id, books.title, COUNT(reservations.id) AS active_count
FROM books
LEFT JOIN reservations 
    ON reservations.book_id = books.id 
    AND reservations.status = 'активне'
GROUP BY books.id
HAVING COUNT(reservations.id) >= 3;
```

Тоді книги без **активних** броней залишились би в результаті з `active_count = 0` (але `HAVING >= 3` їх усе одно відсіяв би).

**Висновок:** LEFT JOIN з `WHERE` на колонці правої таблиці еквівалентний INNER JOIN, бо `WHERE` відсіює `NULL`-рядки. Саме тому в Завданні 4 обидва варіанти дають однаковий результат.

### (в) Відповідь на дослідницьке питання

**Питання:** які книги мають найдовшу чергу бронювань серед читачів, і отже, потребують додаткових примірників?

**Відповідь:** найбільше **активних** бронювань мають дві книги:

1. **«Гаррі Поттер і філософський камінь»** (`id = 5`) — **4 активні броні**.
2. **«Кобзар»** (`id = 1`) — **3 активні броні**.

Саме ці дві книги — кандидати на **дозамовлення додаткових примірників**, бо на них уже сформувалася черга, яка перевищує типовий попит. Решта книг (Місто, Чорний обеліск, Відьмак) мають меншу кількість активних броней і не потребують негайних закупівель. При цьому «Чорний обеліск» має 2 броні, але одна з них уже **виконана** — тому фактично залишається лише 1 активна, і книга не входить до списку першочергових.

## Контрольне питання

**У Завданні 2 ви об'єднали нову таблицю з тими, до яких вона прив'язана, через JOIN. Якби автор мав дві книги, кожна з яких продавалася тричі, скільки рядків для нього дасть JOIN до GROUP BY, і чому COUNT(*) для такого автора покаже не те число книг, яке ви очікували?**

Якби автор мав **дві книги**, кожна з яких мала **три рядки продажів** (у таблиці `sales`), то `JOIN authors → books → sales` дав би **6 рядків** для цього автора:

```
(author, book1, sale1)
(author, book1, sale2)
(author, book1, sale3)
(author, book2, sale1)
(author, book2, sale2)
(author, book2, sale3)
```

Кожен рядок продажу поєднується з відповідною книгою, а кожна книга — з автором. Разом **2 книги × 3 продажі = 6 рядків**.

**Чому `COUNT(*)` покаже не те число книг:** `COUNT(*)` рахує **рядки в результаті JOIN**, а не унікальні книги. Для автора з двома книгами, кожна з яких продавалася тричі, `COUNT(*)` дасть **6**, а не **2**. Якщо мета — порахувати **кількість книг у автора**, треба використовувати `COUNT(DISTINCT books.id)`, а не `COUNT(*)`.

Якщо ж мета — **сума продажів** (як у прикладі з книгарнею), тоді `SUM(sales.quantity)` дасть правильне число (2 × 3 = 6 примірників продано). Але `COUNT(*)` для агрегації продажів теж не підходить: він порахує рядки, а не продані примірники. Для продажів треба саме `SUM(sales.quantity)`, а для кількості книг — `COUNT(DISTINCT books.id)`.І

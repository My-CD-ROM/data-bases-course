**Варіант № 1 — Бібліотека**

**Схема:** `books` (вимір 1, з Практики 1), `readers` (вимір 2), `loans` (фактова з двома FK)

## Завдання 1. Увімкнення перевірки і таблиця-вимір 2

Першим рядком сеансу виконано `PRAGMA foreign_keys = ON;` — це вмикає перевірку цілісності зовнішніх ключів на поточному з'єднанні. Без цієї команди SQLite не блокує вставку рядків із «мертвими» FK, навіть якщо `FOREIGN KEY` оголошений у `CREATE TABLE`.

Створено таблицю-вимір 2 `readers` зі стовпцями:

- `id INTEGER PRIMARY KEY` — сурогатний первинний ключ, унікально ідентифікує кожного читача;
- `last_name TEXT NOT NULL`, `first_name TEXT NOT NULL` — обов'язкові текстові поля (у кожного читача є прізвище та ім'я);
- `email TEXT` — необов'язкове поле (у деяких читачів може не бути email);
- `registration_date TEXT` — дата реєстрації у форматі ISO 8601 (`YYYY-MM-DD`).

Для дат використано `TEXT`, а не окремий тип `DATE` — у SQLite такого типу немає, а `TEXT` у форматі ISO коректно сортується лексикографічно (тобто `'2024-09-01' < '2024-09-15'`) і підтримує вбудовані функції `date()`, `datetime()`. Це стандартний підхід у SQLite.

## Завдання 2. Фактова таблиця з двома FOREIGN KEY

Створено фактову (журнальну) таблицю `loans` із двома зовнішніми ключами та явно обраними діями `ON DELETE`:

```sql
CREATE TABLE loans (
    id           INTEGER PRIMARY KEY,
    book_id      INTEGER NOT NULL,
    reader_id    INTEGER NOT NULL,
    loan_date    TEXT,
    return_date  TEXT,
    FOREIGN KEY (book_id)   REFERENCES books (id)   ON DELETE RESTRICT,
    FOREIGN KEY (reader_id) REFERENCES readers (id) ON DELETE CASCADE
);
```

### Обґрунтування `ON DELETE RESTRICT` для зв'язку `loans.book_id → books.id`

Книга в бібліотеці — це **матеріальний об'єкт обліку**, який не можна безслідно видалити з каталогу, якщо за нею вже є історія видач. Якщо хтось спробує видалити книгу, яку хоч раз видавали читачам, бібліотека втратить частину своєї історії — а це суперечить принципам бібліотечного обліку: кожен факт видачі має зберігатися незалежно від подальшої долі примірника.

Тому `RESTRICT` **блокує видалення** книги, поки є хоч один пов'язаний запис у `loans`. Це змушує адміністратора спочатку свідомо розібратися з історією (наприклад, списати книгу через окремий прапорець `is_archived`, а не видаляти рядок). Така поведінка відображає реальне бізнес-правило бібліотеки: **книга не зникає з каталогу безслідно**.

### Обґрунтування `ON DELETE CASCADE` для зв'язку `loans.reader_id → readers.id`

Читач — це **суб'єкт**, який має право користуватися бібліотекою; якщо читач видаляється з бази (наприклад, за власним запитом про видалення персональних даних, при переїзді, після тривалої неактивності), то його **персональна історія видач втрачає сенс** — вона більше не має сенсу без самого читача. Крім того, залишати записи з посиланням на неіснуючого читача означало б порушувати принципи захисту персональних даних (зберігати зв'язок між книгою та особою, якої вже немає в системі).

Тому при видаленні читача `CASCADE` **автоматично видаляє всі його `loans`**. Це відповідає бізнес-правилу: **немає читача — немає його історії**.

### Чому дії різні

Книга — об'єкт **матеріального обліку**, її історія видач має зберігатися завжди (`RESTRICT`). Читач — **суб'єкт**, його персональна історія втрачає сенс без нього (`CASCADE`). Однакова дія для обох зв'язків тут була б помилкою, бо семантика видалення різна: книгу «списують, але пам'ятають», читача «видаляють разом з усім».

Жодне значення зовнішнього ключа не вигадане — усі відповідають реальним рядкам у таблицях-вимірах. Рядки з `return_date = NULL` — це книги, ще не повернуті читачами.

Перевірка зв'язків через `JOIN`:

```sql
SELECT loans.id, readers.last_name, books.title, loans.loan_date, loans.return_date
FROM loans
JOIN readers ON readers.id = loans.reader_id
JOIN books   ON books.id   = loans.book_id;
```

Повертає 10 рядків — повний журнал видач із прізвищами читачів і назвами книг.

## Завдання 4. Навмисна помилка зовнішнього ключа

Спроба вставити рядок із неіснуючим `book_id = 9999`:

```sql
INSERT INTO loans (book_id, reader_id, loan_date, return_date)
VALUES (9999, 1, '2025-02-01', NULL);
```

**Точне повідомлення про помилку:**

```
Execution finished with errors.
Result: FOREIGN KEY constraint failed
At line 40:
INSERT INTO loans (book_id, reader_id, loan_date, return_date)
VALUES (9999, 1, '2025-02-01', NULL);
```

Ключовий рядок — **`Error: FOREIGN KEY constraint failed`**. Це підтверджує, що `PRAGMA foreign_keys = ON;` справді працює на цьому з'єднанні: SQLite не пропустив рядок із посиланням на неіснуючу книгу.

Якби `PRAGMA` була вимкнена, цей самий `INSERT` виконався б без жодної помилки — і в `loans` з'явився б «запис-привид» із посиланням на книгу, якої не існує. Саме тому важливо тримати `PRAGMA foreign_keys = ON;` у кожному сеансі роботи з базою.

## Завдання 5. Звірка з ER-діаграмою Практики 3

Порівняння фактично створеної структури з ER-діаграмою з Практики 3:

| Елемент | На діаграмі (Практика 3) | У базі (Практика 4) | Збіг? |
|---|---|---|---|
| Таблиця-вимір 1 | `books(id, title, author, publication_year, genre, copies_count)` | Ідентично | ✅ |
| Таблиця-вимір 2 | `readers(id, last_name, first_name, email, registration_date)` | Ідентично | ✅ |
| Фактова таблиця | `loans(id, book_id FK, reader_id FK, loan_date, return_date)` | Ідентично | ✅ |
| Напрямок FK 1 | `loans.book_id → books.id` | `FOREIGN KEY (book_id) REFERENCES books (id)` | ✅ |
| Напрямок FK 2 | `loans.reader_id → readers.id` | `FOREIGN KEY (reader_id) REFERENCES readers (id)` | ✅ |
| Кардинальність | обидва зв'язки 1:N | Фактично 1:N (кожен loan — одна книга, один читач) | ✅ |
| PK у кожній таблиці | `id` у всіх трьох | `id INTEGER PRIMARY KEY` у всіх трьох | ✅ |

**Змін у структурі не було** — усе, що спроєктовано на діаграмі Практики 3, реалізовано в базі Практики 4 один-в-один.

Єдине, що додалося порівняно з діаграмою — конкретні дії `ON DELETE` для кожного зовнішнього ключа (`RESTRICT` для книги, `CASCADE` для читача). На діаграмі mermaid ці деталі не позначаються, бо стосуються поведінки при видаленні, а не самої структури зв'язку. Діаграма показує **структуру** (які таблиці, які стовпці, куди ведуть FK), а `ON DELETE` — це вже **поведінкове налаштування**, яке додається на етапі реалізації.

## Контрольні питання

### 1. Навіщо потрібна `PRAGMA foreign_keys = ON;`, якщо `FOREIGN KEY` уже оголошений у `CREATE TABLE`, і чому цю команду доводиться повторювати на кожному новому з'єднанні?

Оголошення `FOREIGN KEY (...)` у `CREATE TABLE` — це лише **декларація наміру**: воно описує, який стовпець на яку таблицю посилається. Сама SQLite за замовчуванням **не перевіряє** ці обмеження при `INSERT`/`UPDATE`/`DELETE` — історично, заради сумісності зі старими версіями, перевірка вимкнена. Щоб SQLite реально почав захищати цілісність даних і блокувати вставку рядків із «мертвими» FK, треба явно виконати `PRAGMA foreign_keys = ON;`.

Команда діє **тільки на поточне з'єднання**. Кожен новий сеанс `sqlite3` або кожне нове відкриття бази в DB Browser — це окреме з'єднання, і SQLite скидає всі `PRAGMA` до типових значень (`OFF` для `foreign_keys`). Тому в кожному скрипті, який має працювати з FK, `PRAGMA foreign_keys = ON;` пишуть на самому початку — інакше наступного разу, коли відкриєте базу, перевірка мовчки не спрацює, і ви не помітите, що вставляєте некоректні FK.

### 2. Яка принципова різниця між `PRIMARY KEY` і `FOREIGN KEY` — що кожен із них ідентифікує чи на що посилається?

**`PRIMARY KEY`** — це **унікальний ідентифікатор рядка всередині своєї таблиці**. Він відповідає на питання «як відрізнити цей рядок від будь-якого іншого в цій самій таблиці?». Властивості PK:
- значення **унікальне** в межах таблиці;
- **не може бути `NULL`**;
- на таблицю може бути **лише один** PK (хоча він може складатися з кількох стовпців — складений ключ);
- у SQLite `INTEGER PRIMARY KEY` стає аліасом внутрішнього `rowid` і автоматично зростає.

**`FOREIGN KEY`** — це **посилання на PK іншої (або тієї ж) таблиці**. Він відповідає на питання «на який рядок в іншій таблиці вказує цей рядок?». Властивості FK:
- значення FK **не обов'язково унікальне** — багато рядків можуть посилатися на один і той самий PK;
- може бути `NULL`, якщо зв'язок необов'язковий (у нашій схемі — ні, обидва FK мають `NOT NULL`);
- у таблиці може бути **скільки завгодно** FK (у `loans` — два);
- FK **того самого типу**, що й PK, на який він посилається (обидва `INTEGER`).

Коротко: PK **ідентифікує рядок у своїй таблиці** («хто я»), FK **посилається на рядок в іншій таблиці** («на кого я вказую»).

### 3. Чим `ON DELETE CASCADE` відрізняється від `ON DELETE RESTRICT` за наслідками для залежних рядків, і чому для одного й того самого зв'язку різні студенти можуть обґрунтовано обрати різну дію?

**`ON DELETE CASCADE`** — при спробі видалити рядок у **батьківській** таблиці SQLite **автоматично видалить усі залежні рядки** в **дочірній** таблиці. Наприклад: `DELETE FROM readers WHERE id = 5` → усі `loans`, де `reader_id = 5`, теж зникнуть.

**`ON DELETE RESTRICT`** — при спробі видалити рядок у **батьківській** таблиці SQLite **заблокує операцію** й поверне помилку `FOREIGN KEY constraint failed`. Видалення стане можливим тільки після того, як користувач вручну видалить усі залежні рядки або змінить їхній FK на інший.

Різні студенти можуть обрати різні дії для **одного й того самого** зв'язку, бо обидва варіанти логічно обґрунтовані — просто вони відображають **різні бізнес-правила**:

- Для зв'язку `loans.book_id → books.id` можна обрати `RESTRICT` — «книга не зникає з каталогу, поки є її історія видач» (збереження обліку). Але можна обрати й `CASCADE` — «якщо книгу списують і видаляють із бази, то й історію її видач теж видаляють разом із нею» (у деяких бібліотеках таке спрощення припустиме).
- Для зв'язку `loans.reader_id → readers.id` можна обрати `CASCADE` — «немає читача — немає його персональної історії» (принцип мінімізації даних). Але можна обрати й `RESTRICT` — «не можна видалити читача, поки в нього є не повернуті книги» (захист від втрати обліку заборгованостей).

Обидва вибори логічно валідні — вони відображають **різні доменні правила**. Головне не «яка дія простіша», а **яка відповідає бізнес-логіці саме вашої бібліотеки**.

## Завдання 1. INNER JOIN факт + вимір 1

**Запит:**

```sql
SELECT books.title, books.author, loans.loan_date, loans.return_date
FROM loans
JOIN books ON loans.book_id = books.id
ORDER BY loans.loan_date;
```

**Що робить:** з'єднує фактову таблицю `loans` із таблицею-виміром `books` за зовнішнім ключем `book_id`. Замість числового `book_id` виводиться назва книги й автор. Сортування за датою видачі — щоб було видно хронологію.

**Результат (фрагмент):**

```
Кобзар|Тарас Шевченко|2025-01-10|2025-01-20
Місто|Валер'ян Підмогильний|2025-01-12|2025-01-25
1984|Джордж Орвелл|2025-01-15|2025-02-12
...
```

**Обґрунтування вибору INNER JOIN:** для звіту потрібні лише ті рядки `loans`, які мають відповідну книгу. У нашій схемі `loans.book_id` має `NOT NULL` і `FOREIGN KEY`, тому «сирітських» рядків бути не може — INNER JOIN і LEFT JOIN дали б однаковий результат. Але семантично правильніше INNER: ми свідомо хочемо бачити **тільки** ті видачі, для яких книга існує. Якби використали LEFT JOIN, результат не змінився б (усі видачі мають книгу), але запит виглядав би так, ніби ми очікуємо книги без видач, чого тут немає.

## Завдання 2. INNER JOIN усіх трьох таблиць

**Запит:**

```sql
SELECT books.title AS книга, readers.last_name AS читач, loans.loan_date AS дата_видачі, loans.return_date AS дата_повернення
FROM loans
JOIN books   ON loans.book_id   = books.id
JOIN readers ON loans.reader_id = readers.id
ORDER BY loans.loan_date;
```

**Що робить:** з'єднує `loans` із `books` і `readers` — три таблиці разом. У результаті один рядок показує три людяні значення (назва книги, прізвище читача, дата видачі) — без жодного `id`.

**Результат (фрагмент):**

```
Кобзар|Шевченко|2025-01-10|2025-01-20
Місто|Коваленко|2025-01-12|2025-01-25
1984|Шевченко|2025-01-15|2025-02-12
...
```

**Обґрунтування вибору INNER JOIN:** потрібні лише ті видачі, де є **і книга, і читач**. Оскільки обидва стовпці `book_id` і `reader_id` мають `NOT NULL` і `FOREIGN KEY`, «сирітських» рядків немає — INNER і LEFT тут еквівалентні. Але INNER точніше передає намір: «показати зв'язані дані». Якби використали LEFT JOIN для `readers`, ми б побачили видачі навіть для неіснуючих читачів (з порожньою колонкою `читач`) — але таких у базі немає, тож результат не змінився б.

## Завдання 3. LEFT JOIN — рядки таблиці-виміру без жодної пари

**Запит:**

```sql
SELECT books.id, books.title
FROM books
LEFT JOIN loans ON loans.book_id = books.id
WHERE loans.id IS NULL;
```

**Що робить:** знаходить книги, на які **не посилається жоден** рядок у `loans`. Класичний прийом: `LEFT JOIN` + `WHERE <права_таблиця>.id IS NULL`. Якщо у книги немає видач, то при `LEFT JOIN` у колонках `loans` буде `NULL` — і `WHERE loans.id IS NULL` вибереме саме такі.

**Перший запуск:** запит повернув **0 рядків** — усі книги в базі мали хоч одну видачу.

**Що додано для демонстрації:** щоб запит повернув хоч один результат, додано нову книгу, яку ще ніхто не брав:

```sql
INSERT INTO books (title, author, publication_year, genre, copies_count)
VALUES ('Чорний обеліск', 'Еріх Марія Ремарк', 1956, 'роман', 1);
```

**Повторний запуск запиту:**

```
id | title
---+-----------------
23 | Чорний обеліск
```

**Обґрунтування вибору LEFT JOIN:** тут **не можна** використати INNER JOIN — він за визначенням повертає лише ті рядки, де є **збіг з обох сторін**. INNER JOIN `books JOIN loans ON books.id = loans.book_id` виключив би з результату всі книги без видач (їх просто немає в «з'єднанні»). А мета запиту — **знайти саме такі книги**. Тому потрібен LEFT JOIN: він зберігає **усі** рядки з лівої таблиці (`books`), навіть якщо в правій (`loans`) немає відповідника. І вже потім фільтр `WHERE loans.id IS NULL` залишає тільки ті, де відповідника не знайшлося.

## Завдання 4. Свідома пастка CROSS JOIN

**Запити:**

```sql
SELECT COUNT(*) FROM books;
SELECT COUNT(*) FROM readers;
SELECT COUNT(*) FROM books, readers;
```

**Результати:**

- `SELECT COUNT(*) FROM books;` → **23**
- `SELECT COUNT(*) FROM readers;` → **5**
- `SELECT COUNT(*) FROM books, readers;` → **115**

**Чому саме 115 = 23 × 5, а не 23 + 5 = 28:**

Кома-синтаксис `FROM books, readers` — це **CROSS JOIN**. Він створює **декартів добуток** двох таблиць: кожен рядок `books` поєднується з **кожним** рядком `readers`. Тобто для книги «Кобзар» буде 5 рядків — по одному на кожного читача: `(Кобзар, Шевченко)`, `(Кобзар, Коваленко)`, `(Кобзар, Бондаренко)` тощо. Для кожної з 23 книг — теж по 5 рядків. Разом **23 × 5 = 115**.

**Чому в реальному звіті це майже завжди помилка:**

CROSS JOIN майже ніколи не потрібен у звітах — він дає **безглузді комбінації** рядків, які не мають бізнес-сенсу. У нашому прикладі: «Кобзар + Коваленко» — не має сенсу, бо Коваленко жодного разу не брав Кобзаря. Реальні зв'язки між книгами і читачами описуються **фактовою таблицею `loans`**, тому правильний запит:

```sql
SELECT books.title, readers.last_name
FROM loans
JOIN books   ON loans.book_id   = books.id
JOIN readers ON loans.reader_id = readers.id;
```

Це дає лише **реальні** пари «книга — читач», ті, які справді мали місце.

**Коли CROSS JOIN виправданий:** майже ніколи в OLTP-звітах. Іноді — у специфічних задачах (наприклад, згенерувати «календарний стовпець» для кожного товару, або побудувати повну матрицю комбінацій для A/B-тесту). Але в 99% випадків кома-синтаксис — це забутий `WHERE` або забутий `JOIN ... ON`, що випадково перетворив звичайний запит на декартів добуток.

**Особливо небезпечно** це на великих таблицях: якщо в `books` 10 000 рядків, а в `readers` 100 000, то `FROM books, readers` без умови з'єднання спробує повернути **1 000 000 000** рядків — це мільярд. Запит може «підвісити» сервер надовго або взагалі вбити його по пам'яті.

## Завдання 5. Обґрунтування вибору JOIN

**Завдання 1 (INNER JOIN `loans` + `books`):** обрано INNER, бо звіт має показати лише ті видачі, для яких **існує** книга; якби використали LEFT JOIN — теоретично з'явилися б рядки з порожньою назвою книги (для «сирітських» видач), чого ми не хочемо (таких у базі й немає завдяки FK).

**Завдання 2 (INNER JOIN `loans` + `books` + `readers`):** обрано INNER для обох JOIN, бо звіт має показати лише ті видачі, де є **і книга, і читач**; якби один із JOIN зробили LEFT — у результаті могли б з'явитися рядки з `NULL` у відповідній колонці (наприклад, видача з порожнім прізвищем читача), що не має сенсу для звіту.

**Завдання 3 (LEFT JOIN `books` + `loans`):** обрано LEFT, бо мета — знайти книги **без видач**; якби використали INNER JOIN — такі книги взагалі зникли б із результату, і ми б ніколи не дізналися, що вони є (запит просто повернув би 0 рядків, або тільки книги з видачами).

## Контрольні питання

### 1. Чому рядок з `NULL` у зовнішньому ключі ніколи не з'явиться в результаті INNER JOIN за цим ключем, а в LEFT JOIN — з'явиться?

**INNER JOIN** залишає в результаті лише ті рядки, де **умова `ON` істинна для обох сторін**. Якщо в лівій таблиці `FK = NULL`, то умова `ON left.fk = right.id` дає `NULL = <щось>` → результат **`NULL`** (не `TRUE`). SQLite трактує `NULL` у `WHERE`/`ON` як «не істина» і **відкидає** такий рядок.

**LEFT JOIN** залишає **усі** рядки з лівої таблиці, навіть якщо для них не знайшлося відповідника в правій. Якщо `FK = NULL` (або просто немає збігу), SQLite підставляє замість колонок правої таблиці `NULL`. Тому рядок з'являється в результаті — просто з порожніми значеннями з правої сторони.

**Приклад:**
- `loans.reader_id = NULL` (теоретично) — INNER JOIN з `readers` його **відкине** (бо `NULL = id` не істинне); LEFT JOIN **залишить** рядок у результаті, але з `readers.last_name = NULL`.

У нашій схемі `reader_id` має `NOT NULL`, тому на практиці цей випадок не виникає — але якби обмеження не було, різниця б проявилася.

### 2. Що станеться з результатом Завдання 2, якщо один JOIN замінити на LEFT JOIN, а решту лишити INNER JOIN?

Розглянемо два варіанти:

**Варіант A: `loans JOIN books` (INNER) + `LEFT JOIN readers`:**

```sql
SELECT books.title, readers.last_name, loans.loan_date
FROM loans
JOIN books   ON loans.book_id   = books.id
LEFT JOIN readers ON loans.reader_id = readers.id;
```

Результат: усі видачі, для яких **існує книга** (INNER умова), плюс — якщо для видачі немає читача, рядок усе одно потрапляє в результат із `readers.last_name = NULL`.

**Варіант B: `LEFT JOIN books` + `JOIN readers` (INNER):**

```sql
SELECT books.title, readers.last_name, loans.loan_date
FROM loans
LEFT JOIN books   ON loans.book_id   = books.id
JOIN readers ON loans.reader_id = readers.id;
```

Результат: усі видачі, для яких **існує читач**, плюс — якщо для видачі немає книги, рядок потрапляє з `books.title = NULL`. **Але**: після `LEFT JOIN` на `books` іде **INNER JOIN на `readers`** — і цей INNER може **відкинути** ті рядки, де `reader_id` не знайшов читача. Тобто «ефект LEFT на books» частково знівелюється INNER'ом далі.

**У нашій практичній базі це нічого не змінить** — бо обидва FK мають `NOT NULL`, і всі видачі мають і книгу, і читача. Результати всіх трьох варіантів (обидва INNER, INNER+LEFT, LEFT+INNER) будуть **однакові**. Але в базі без `NOT NULL` на FK різниця була б видимою: LEFT JOIN додав би рядки з `NULL` там, де відповідник відсутній.

**Висновок:** заміна JOIN типу в ланцюжку завжди додає рядки (LEFT робить результат «ширшим»), але наступний INNER JOIN може відфільтрувати частину цих доданих рядків.

### 3. Чим `FROM a, b WHERE a.id = b.a_id` (старий кома-синтаксис із умовою у WHERE) відрізняється від `a JOIN b ON a.id = b.a_id` за результатом, і чим — за ризиком помилки?

**За результатом — нічим.** Обидва запити дають **однаковий результат**:

```sql
SELECT a.id, b.id
FROM a, b
WHERE a.id = b.a_id;
```

```sql
SELECT a.id, b.id
FROM a
JOIN b ON a.id = b.a_id;
```

Це **еквівалентні запити** — перший використовує «старий» (SQL-89) синтаксис, другий — «сучасний» (SQL-92). SQLite компілює їх однаково, і швидкість виконання однакова.

**За ризиком помилки — принципово різні.**

**Кома-синтаксис безпечний ЛИШЕ тоді, коли є `WHERE` з умовою з'єднання.** Якщо забути `WHERE`:

```sql
SELECT a.id, b.id
FROM a, b;   -- ← без WHERE
```

— це **CROSS JOIN**, декартів добуток. Отримаємо `COUNT(a) × COUNT(b)` рядків замість очікуваної кількості. На великих таблицях це може «вбити» запит.

**Сучасний `JOIN ... ON` синтаксис** має вбудовану вимогу: умова з'єднання **пишеться прямо в JOIN**, і без неї запит майже завжди видасть синтаксичну помилку (крім `CROSS JOIN`, де `ON` не потрібен). Забути `ON` складніше, бо воно йде відразу після `JOIN table_name` — це частина синтаксису.

**Додаткові переваги сучасного синтаксису:**

1. **Читабельність.** `JOIN ... ON` показує **логіку з'єднання** поруч із таблицею, а умова у `WHERE` змішує з'єднання й фільтрацію. У великих запитах з 4-5 таблицями кома-синтаксис перетворюється на «кашу» з умов у `WHERE`.
2. **Різні типи JOIN.** `LEFT JOIN`, `RIGHT JOIN` у кома-синтаксисі неможливо записати взагалі — потрібен саме `JOIN ... ON`.
3. **Безпека від помилок.** Якщо забути одну умову у `WHERE` — запит перетвориться на частковий CROSS JOIN. У сучасному синтаксисі таке забути важче.

**Висновок:** для нового коду завжди використовуйте `JOIN ... ON`. Кома-синтаксис — історична спадщина, яку іноді зустрічаєте в старому коді, але не варто використовувати в нових проєктах.

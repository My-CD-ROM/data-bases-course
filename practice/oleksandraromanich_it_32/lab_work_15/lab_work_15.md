## Завдання 1. EXPLAIN QUERY PLAN до індексу

**Запит:**

```sql
EXPLAIN QUERY PLAN
SELECT * FROM loans WHERE book_id = 1;
```

**План до створення індексу:**

```
SCAN loans
```

**Що це означає:** SQLite **сканує всю таблицю `loans`** рядок за рядком, щоб знайти ті, де `book_id = 1`. Для маленької таблиці це швидко, але якби в `loans` було 100 000 записів, SQLite перевірив би всі 100 000 — і лише кілька з них задовольнили б умову.

## Завдання 2. CREATE INDEX на зовнішньому ключі

**Створення індексу:**

```sql
CREATE INDEX idx_loans_book ON loans(book_id);
```

**Той самий запит після індексу:**

```sql
EXPLAIN QUERY PLAN
SELECT * FROM loans WHERE book_id = 1;
```

**План після створення індексу:**

```
SEARCH loans USING INDEX idx_loans_book (book_id=?)
```

**Що змінилося:**
- Було `SCAN loans` — повний перебір усіх рядків.
- Стало `SEARCH loans USING INDEX idx_loans_book (book_id=?)` — SQLite використовує індекс для **швидкого пошуку**. Замість сканування всієї таблиці він йде по «покажчику» (B-tree) і знаходить лише ті рядки, де `book_id = 1`, практично одразу.

**Різниця:** на маленькій таблиці (7 рядків) різниця в часі мікроскопічна. Але на великій таблиці (наприклад, 1 мільйон видач) `SEARCH` через індекс може бути **у тисячі разів швидшим** за `SCAN`.

## Завдання 3. Композитний індекс

**Запит із двома умовами:**

```sql
SELECT * FROM loans WHERE reader_id = 2 AND book_id = 1;
```

**План до композитного індексу:**

```
SEARCH loans USING INDEX idx_loans_book (book_id=?)
```
*(SQLite використав наявний одноколонковий індекс `idx_loans_book` на `book_id`, а `reader_id = 2` перевіряє вже після знайдення рядків)*.

**Створення композитного індексу:**

```sql
CREATE INDEX idx_loans_reader_book ON loans(reader_id, book_id);
```

**План після створення композитного індексу:**

```
SEARCH loans USING INDEX idx_loans_reader_book (reader_id=? AND book_id=?)
```

**Що змінилося:**
- **До:** SQLite використовував лише **один** індекс (на `book_id`), а `reader_id = 2` перевіряв **після** знайдення рядків. Це давало проміжний результат.
- **Після:** SQLite використовує **композитний** індекс, який містить обидві колонки. Пошук відбувається **одразу за двома умовами** — SQLite йде по індексу за `reader_id = 2`, а потім у межах цієї групи ще й фільтрує за `book_id = 1`. Це ефективніше, бо SQLite не витрачає час на «зайві» рядки, які не задовольняють другу умову.

**Чому одноколонковий індекс на `reader_id` (якби він був) дав би менший ефект:** він знайшов би **усі** видачі цього читача (наприклад, 1000), а потім SQLite ще раз фільтрував би за `book_id` — тобто перевіряв 1000 рядків замість кількох. Композитний індекс робить **одну** операцію пошуку за двома умовами.

## Завдання 4. Індекс і ORDER BY

**Запит:**

```sql
EXPLAIN QUERY PLAN
SELECT * FROM loans ORDER BY loan_date;
```

**План до індексу:**

```
SCAN loans
USE TEMP B-TREE FOR ORDER BY
```

**Що це означає:** SQLite спочатку **сканує всі рядки** таблиці, а потім **сортує їх у тимчасовій структурі** (TEMP B-TREE) за `loan_date`. Це дві окремі операції: читання + сортування.

**Створення індексу:**

```sql
CREATE INDEX idx_loans_date ON loans(loan_date);
```

**План після створення індексу:**

```
SCAN loans USING INDEX idx_loans_date
```

**Що змінилося:**
- Зникло **`USE TEMP B-TREE FOR ORDER BY`** — SQLite більше не сортує в тимчасовій структурі.
- Замість `SCAN loans` (з сортуванням) став `SCAN loans USING INDEX idx_loans_date` — SQLite **читає рядки вже в потрібному порядку** (бо індекс фізично зберігається відсортованим за `loan_date`). Окремий крок сортування **більше не потрібен**.

**Різниця:** без індексу — **2 кроки** (сканувати + сортувати). З індексом — **1 крок** (читати вже впорядковане). На великих таблицях економія значна, бо сортування — дорога операція.

## Завдання 5. DROP INDEX і повторна перевірка

**Видалення індексу:**

```sql
DROP INDEX idx_loans_book;
```

**Запит після видалення:**

```sql
EXPLAIN QUERY PLAN
SELECT * FROM loans WHERE book_id = 1;
```

**План після видалення:**

```
SCAN loans USING INDEX idx_loans_reader_book (book_id=?)
```

**Що сталося:** індекс `idx_loans_book` **видалено**, і SQLite більше не може використовувати його напряму. Але залишився **композитний** індекс `idx_loans_reader_book` (на `reader_id, book_id`), який **теж містить `book_id`** — хоч і на другій позиції. SQLite розуміє це й використовує `idx_loans_reader_book` як «покриттєвий» для пошуку за `book_id` (бо `book_id` входить у композитний індекс). Тому план не повернувся до чистого `SCAN loans` — він використовує залишковий індекс.

**Перевірка через `sqlite_master`:**

```sql
SELECT name FROM sqlite_master WHERE type='index' AND tbl_name='loans';
```

**Результат:**

```
idx_loans_reader_book
idx_loans_date
```

**Висновок:** індекс `idx_loans_book` **справді видалено** — його немає в списку. Залишилися два інші індекси: `idx_loans_reader_book` (композитний) і `idx_loans_date` (на дату).

## Контрольні питання

### 1. Чому EXPLAIN QUERY PLAN показує саме план, а не результат запиту, і навіщо перевіряти план окремо від того, що запит просто «працює»?

**`EXPLAIN QUERY PLAN`** — це **не звичайний запит**. Вона не виконує `SELECT` і не повертає дані — вона **показує, як SQLite планує виконати** цей запит: які таблиці скануватиме, які індекси використовуватиме, у якому порядку з'єднуватиме.

**Чому перевіряти план окремо:**
- **Запит може «працювати» й повертати правильний результат, але бути повільним.** Наприклад, `SELECT * FROM loans WHERE book_id = 1` поверне правильні рядки й без індексу — але на великій таблиці це займе секунди або хвилини замість мілісекунд. План показує, що запит робить `SCAN` замість `SEARCH`.
- **План показує, чи використовуються індекси.** Якщо ви створили індекс, але SQLite його не використовує (наприклад, через функцію в `WHERE`), план це покаже — і ви зрозумієте, що індекс «не працює».
- **План показує порядок з'єднання таблиць.** Для JOIN-запитів план каже, яку таблицю SQLite читатиме першою — це впливає на швидкість.
- **План — це «рентген» запиту.** Він дозволяє знайти вузькі місця **до** того, як запит почне гальмувати на реальних даних.

**Аналогія:** запит «працює» — це як автомобіль, який їде. Але якщо він їде зі швидкістю 10 км/год, ви не будете задоволені. `EXPLAIN QUERY PLAN` — це «діагностика двигуна»: показує, чому машина їде повільно, і що треба змінити.

### 2. У Завданні 3: чому індекс лише на першій із двох колонок умови дає менший ефект, ніж композитний індекс на обох?

**Одноколонковий індекс** на першій колонці (наприклад, `idx_loans_book` на `book_id`) дозволяє SQLite швидко знайти **усі рядки**, де `book_id = 1`. Але якщо умова ще й `reader_id = 2`, SQLite після знайдення рядків за першою умовою **додатково перевіряє** кожен із них на другу умову.

**Приклад:** якщо `book_id = 1` має 1000 видач, а `reader_id = 2` серед них лише 3, то:
- Одноколонковий індекс: SQLite знаходить 1000 рядків за `book_id = 1`, а потім перевіряє кожен із 1000 на `reader_id = 2` → **1000 перевірок**.
- Композитний індекс: SQLite знаходить одразу 3 рядки, де `book_id = 1 AND reader_id = 2` → **3 перевірки**.

**Композитний індекс** — це B-tree, який сортує рядки **спочатку за першою колонкою, потім за другою**. Тому SQLite може шукати одразу за **двома** умовами (наприклад, якщо `reader_id = 2`, то він переходить у «підрозділ» цього `reader_id` і шукає вже `book_id = 1` серед них). Це значно швидше, ніж «знайти за першою, перевірити другу».

**Коли композитний індекс дає перевагу:**
- Коли обидві колонки використовуються в `WHERE` разом (як у Завданні 3).
- Коли перша колонка має багато різних значень, а друга — багато для кожного значення першої (тобто обидві «селективні»).

**Коли одноколонкового достатньо:**
- Коли запити фільтрують тільки за однією колонкою.
- Коли друга колонка не використовується в `WHERE`.

### 3. Яка ціна створення індексу (лекція 13, розділ 15) і чому не варто індексувати кожну колонку таблиці «про всяк випадок»?

**Індекс — це не «безкоштовне покращення».** Він дає швидший пошук, але має реальну ціну:

1. **Місце на диску.** Кожен індекс — це окрема структура (B-tree), яка займає місце. Для таблиці з мільйоном рядків і 5 індексів — це 5 додаткових структур, кожна з яких може займати сотні мегабайт.

2. **Повільнення INSERT/UPDATE/DELETE.** Коли ви додаєте новий рядок у таблицю з індексами, SQLite має **оновити всі індекси** цієї таблиці. Наприклад, таблиця з 10 індексами: кожен `INSERT` оновлює 10 B-tree замість одного. Це може **уповільнити вставку в 5–10 разів**.

3. **Додаткова робота при кожному UPDATE.** Якщо ви оновлюєте колонку, на якій є індекс, SQLite має **перебудувати** індекс. Якщо колонка не в індексі — нічого перебудовувати не треба.

4. **Підтримка та складність.** Більше індексів — складніше розуміти план запитів, важче адмініструвати базу.

**Чому не варто індексувати «про всяк випадок»:**
- Індекс **допомагає лише тим запитам**, які **справді використовують** цю колонку в `WHERE`, `JOIN` або `ORDER BY`. Якщо ви створили індекс на `copies_count`, але ніколи не фільтруєте за ним — ви просто **з'їли диск** і **уповільнили INSERT/UPDATE** без жодної користі.
- Кожен індекс треба **обґрунтувати конкретними запитами**. У нашій практиці ми створили три індекси — під конкретні запити: `WHERE book_id = ...`, `WHERE reader_id = ... AND book_id = ...`, `ORDER BY loan_date`. Це **цілеспрямовані** індекси, а не «на кожну колонку».

**Правило:** індекси створюють **під конкретні запити**, а не «на всяк випадок». Спочатку — аналіз `EXPLAIN QUERY PLAN`, потім — індекс на колонку, яка **справді** бере участь у фільтрації.

Загальний підхід
SQLite використовує не класичну строгу типізацію стовпців, а type affinity — «схильність» стовпця до певного класу зберігання. Існує п'ять класів зберігання (INTEGER, REAL, TEXT, BLOB, NULL) і п'ять категорій affinity (INTEGER, TEXT, REAL, NUMERIC, BLOB). Коли я оголошую стовпцю тип INTEGER, SQLite призначає йому INTEGER-affinity: значення, які виглядають як цілі числа, зберігаються саме як цілі, а не як рядки. Це важливо для коректного сортування, порівняння та математичних операцій. Нижче — обґрунтування для кожного стовпця.

id INTEGER PRIMARY KEY
Стовпець-ідентифікатор рядка. Обрано INTEGER, бо INTEGER PRIMARY KEY у SQLite — особливий випадок: він стає аліасом для внутрішнього rowid (64-бітного цілого). Це означає автоматичне зростання при вставці без явного вказування значення, швидкий доступ і унікальність. Якби я оголосив TEXT PRIMARY KEY, SQLite створив би окремий індекс, а rowid існував би паралельно — це повільніше й менш природно для сурогатного ключа. Тому для id використовують саме INTEGER PRIMARY KEY — це ідіоматичний спосіб у SQLite.

title TEXT NOT NULL
Назва книги — це текст довільної довжини з літерами, пробілами, апострофами («Валер'ян Підмогильний», «Гаррі Поттер…»). Жоден числовий тип тут не підходить. TEXT — це клас зберігання для рядків у кодуванні UTF-8/UTF-16. NOT NULL додано, бо книга без назви не має сенсу — обмеження цілісності не дасть вставити порожнє значення. Альтернативи (VARCHAR(255)) у SQLite не дають жодної переваги: довжина в дужках ігнорується, а affinity все одно буде TEXT-affinity.

author TEXT NOT NULL
Прізвище та ім'я автора — так само текст. Може містити літери, пробіли, апострофи, ініціали. NOT NULL тут доречний, бо кожна книга має автора (навіть якщо це «Народна творчість» — це все одно текст). Якби я обрав INTEGER, SQLite спробував би перетворити рядок на число — і зберіг би його як текст лише тому, що перетворення неможливе; але це було б семантично неправильно і плутало б майбутні запити (наприклад, WHERE author = 'Тарас Шевченко').

publication_year INTEGER
Рік видання — ціле число (1840, 1928, 1997). Обрано INTEGER, а не TEXT, бо:

за ним можна робити числові порівняння: WHERE publication_year > 1900;

сортування буде числовим (1928 < 1997), а не лексикографічним;

можна обчислювати вік книги: 2024 - publication_year.

Якби я обрав TEXT, то «1997» і «999» сортувалися б як рядки, і WHERE publication_year > 1900 порівнювало б рядки з числом, що дало б непередбачуваний результат. NOT NULL не ставлю: трапляються книги без точної дати видання, тому поле може бути порожнім (NULL).

genre TEXT
Жанр («поезія», «роман», «фентезі») — це категоріальне текстове значення. TEXT тут природний. Альтернативою був би окремий довідник genres(id, name) зі зв'язком — і в нормалізованій схемі це правильніше. Але на цьому етапі (таблиця-вимір 1) жанр зберігається прямо в рядку, і TEXT — єдиний відповідний тип. NOT NULL не ставлю, бо жанр може бути невідомий або змішаний.

copies_count INTEGER
Кількість примірників у фонді — ціле невід'ємне число (12, 7, 20). Обрано INTEGER, а не TEXT, хоча SQLite технічно дозволив би записати туди й 'дванадцять'. Причини:

це лічильник, за ним виконуються арифметичні операції (copies_count - 1 при видачі книги, SUM(copies_count) по жанрах);

числове порівняння (WHERE copies_count < 5 для пошуку дефіцитних книг) працює лише з INTEGER-affinity;

TEXT зламав би сортування: '10' < '9' лексикографічно, але 10 > 9 числово.

Якби я оголосив copies_count TEXT, SQLite застосував би TEXT-affinity: навіть якщо я вставлю число 12, воно збереглося б як рядок '12', і SUM() повернув би 0 (SQLite не перетворює текст на число в агрегатах автоматично). Це класична пастка type affinity, якої тут вдалося уникнути.

Чому не використано інші типи
REAL — не потрібен жодному стовпцю: немає дробових величин (ціни, ваги, координати). Якби в бібліотечній схемі з'явилася, наприклад, ціна штрафу за прострочення, там був би REAL.

BLOB — не потрібен: немає бінарних даних (зображень обкладинок, PDF). Якби обкладинки зберігалися в БД, це був би BLOB.

NUMERIC — надлишковий: він поводиться як INTEGER, якщо значення ціле, і як REAL, якщо дробове. Для наших стовпців достатньо явних INTEGER/TEXT.

Висновок
Кожен стовпець отримав тип, що відповідає семантиці даних і майбутнім операціям над ними: текст — для назв, імен і жанрів; цілі числа — для року й кількості примірників. Це не просто «щоб SQLite дозволив», а щоб запити Практики 2 (фільтри, сортування, агрегати) давали очікувані результати без прихованих перетворень типів.

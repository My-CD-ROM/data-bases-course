# Практика 6. Робота з командами оновлення та видалення у SQLite

**Варіант № 1 — Бібліотека**

**Файл бази:** `lab_work_6.db` (на основі `lab_work_5.db` — трьохтаблична схема `books`, `readers`, `loans` з обмеженнями `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT` із Практики 5).

Усі команди виконано з `PRAGMA foreign_keys = ON;` на початку сесії — це обов'язкова умова для того, щоб SQLite перевіряв обмеження зовнішніх ключів (за замовчуванням вони вимкнені).

## Завдання 1. UPDATE у фактовій таблиці `loans`

**Команда:**

```sql
UPDATE loans SET return_date = '2025-02-12' WHERE id = 3;
```

**Що змінилося:** рядок `id = 3` раніше мав `return_date = NULL` — це була книга «1984» (book_id = 4), взята читачем Шевченко Олена (reader_id = 1) 15 січня 2025 року. Книга ще не була повернута, тому `return_date` залишалося порожнім. Після `UPDATE` дата повернення встановлена у `2025-02-12`.

**Перевірка:**

```sql
SELECT id, book_id, reader_id, loan_date, return_date FROM loans WHERE id = 3;
```

**Результат:**

```
id | book_id | reader_id | loan_date   | return_date
---+---------+-----------+-------------+-------------
3  | 4       | 1         | 2025-01-15  | 2025-02-12
```

Умова `WHERE id = 3` (за первинним ключем) гарантує, що оновлено рівно один рядок.

## Завдання 2. UPDATE у таблиці-вимірі `books`

**Команда:**

```sql
UPDATE books SET copies_count = copies_count + 3 WHERE id = 5;
```

**Що змінилося:** кількість примірників книги «Гаррі Поттер і філософський камінь» зросла з 20 до 23 — бібліотека придбала ще 3 примірники цієї книги.

**Перевірка:**

```sql
SELECT id, title, copies_count FROM books WHERE id = 5;
```

**Результат:**

```
id | title                                       | copies_count
---+---------------------------------------------+-------------
5  | Гаррі Поттер і філософський камінь         | 23
```

### Пояснення (одне речення)

**Тут доречний саме `UPDATE`, а не видалення рядка й вставка нового, тому що книга вже існує в базі зі своїм `id`, на неї посилаються записи в `loans` (FK `book_id → books.id`), і видалення з наступною вставкою зламало б ці зв'язки або взагалі було б заблоковане `ON DELETE RESTRICT` — а `UPDATE` точково змінює лише один показник, зберігаючи ідентифікатор і всю історію видач.**

## Завдання 3. DELETE одного рядка з фактової таблиці

**Команди:**

```sql
SELECT COUNT(*) AS loans_before FROM loans;

DELETE FROM loans WHERE id = 7;

SELECT COUNT(*) AS loans_after FROM loans;
```

**Результати:**

До видалення:
```
loans_before
------------
10
```

Після видалення:
```
loans_after
-----------
9
```

**Що сталося:** видалено рядок `id = 7` — це була видача книги «Місто» (book_id = 2) читачу Коваленко Ігор (reader_id = 2) від 22 січня 2025 року, повернення ще не було (`return_date = NULL`). Ймовірно, запис скасовано через помилку оформлення.

**Перевірка, що зник рівно один рядок, а не більше:**
`COUNT(*)` зменшився рівно на 1 (з 10 до 9). Умова `WHERE id = 7` гарантує точкове видалення саме одного рядка.

## Завдання 4. Перевірка `ON DELETE` на реальних даних

### Нагадування: обрані в Практиці 4 дії `ON DELETE`

У Практиці 4 для двох зовнішніх ключів фактової таблиці `loans` я обґрунтував такі дії:

- **`loans.book_id → books.id` — `ON DELETE RESTRICT`** (книга не видаляється, поки є хоч одна пов'язана видача — це захищає історію бібліотечного обліку).
- **`loans.reader_id → readers.id` — `ON DELETE CASCADE`** (при видаленні читача всі його видачі автоматично зникають — персональна історія втрачає сенс без читача).

### Прогноз (записаний ДО видалення)

Обираю видалити **читача з `id = 1` (Шевченко Олена)**. За даними таблиці `loans`, на цього читача посилаються **3 записи** (id = 1, 3, 8).

**Прогноз, виходячи з обраної дії `ON DELETE CASCADE` для `loans.reader_id`:**

1. `DELETE FROM readers WHERE id = 1;` **виконається успішно**.
2. Усі три рядки в `loans`, де `reader_id = 1`, **автоматично видаляться** (`CASCADE`).
3. У `books` **нічого не зміниться** — книги залишаються в каталозі, вони не залежать від того, хто їх брав.
4. Загальна кількість `loans` зменшиться на 3 — було 9 (після Завдання 3), стане **6**.

### Фактичний результат

**До видалення — скільки видач у Шевченко Олени:**

```sql
SELECT COUNT(*) AS loans_with_reader_1 FROM loans WHERE reader_id = 1;
```

Результат:
```
loans_with_reader_1
-------------------
3
```

**Видалення:**

```sql
DELETE FROM readers WHERE id = 1;
```

Результат:
```
Execution finished without errors.
Result: query executed successfully. Took 0ms, 1 рядків постражджало
```

**Після видалення — скільки видач залишилося у Шевченко Олени:**

```sql
SELECT COUNT(*) AS loans_with_reader_1_after FROM loans WHERE reader_id = 1;
```

Результат:
```
loans_with_reader_1_after
-------------------------
0
```

**Перевірка загальної кількості `loans`:**

```sql
SELECT COUNT(*) FROM loans;
```

Результат — **6** (було 9, зменшилось рівно на 3 — усі видачі Шевченко Олени).

**Перевірка, що книги в `books` залишилися недоторканими:**

```sql
SELECT COUNT(*) FROM books;
```

Результат — **22** (як і було).

### Порівняння прогнозу з фактичним результатом

| Пункт прогнозу | Прогноз | Факт | Збіг? |
|---|---|---|---|
| `DELETE FROM readers` виконається | успішно | успішно | ✅ |
| Видачі з `reader_id = 1` зникнуть | усі 3 | усі 3 | ✅ |
| Книги в `books` залишаться | незмінні (22) | незмінні (22) | ✅ |
| Загальна кількість `loans` | 6 | 6 | ✅ |

**Висновок:** прогноз повністю збігся з фактичним результатом. Це підтверджує, що:

1. **`PRAGMA foreign_keys = ON;` справді працює.** Якби його не було, `DELETE FROM readers` теж виконався б успішно, але рядки в `loans` залишилися б із посиланням на неіснуючого читача (`reader_id = 1`) — «сирітські» записи.
2. **`ON DELETE CASCADE`** для `loans.reader_id` коректно реалізовано й діє на реальних даних.
3. **`ON DELETE RESTRICT`** для `loans.book_id` не заважав — він стосується видалення **книг**, а не читачів, тому видалення читача не блокувалося.

### Додаткова перевірка `RESTRICT` на книзі

Щоб переконатися, що `RESTRICT` для книги також працює, спробуємо видалити книгу, яку хтось брав:

```sql
DELETE FROM books WHERE id = 1;
```

**Очікуваний результат:**

```
Execution finished with errors.
Result: FOREIGN KEY constraint failed
```

**Фактичний результат:**

```
Execution finished with errors.
Result: FOREIGN KEY constraint failed
```

**Висновок:** `RESTRICT` спрацював — книгу «Кобзар» (id = 1) не можна видалити, поки є хоч одна видача з посиланням на неї. Щоб видалити цю книгу, спочатку треба прибрати всі пов'язані рядки в `loans`. Це саме та поведінка, яку я обґрунтував у Практиці 4: книга — матеріальний об'єкт обліку, її історія видач має зберігатися навіть після списання примірника.

## Контрольні питання

### 1. Чим `UPDATE ... SET колонка = колонка + 1` відрізняється від `UPDATE ... SET колонка = <конкретне число>`?

**`SET колонка = колонка + 1`** — це **відносна зміна**: нове значення обчислюється на основі **поточного** значення рядка. Кожен рядок отримає своє нове значення, залежно від того, скільки в нього було. Наприклад, якщо у двох книг було 20 і 5 примірників, після `copies_count = copies_count + 3` стане 23 і 8.

**`SET колонка = <конкретне число>`** — це **абсолютна зміна**: усі рядки, які потрапили під `WHERE`, отримають **однакове** значення. Наприклад, `SET copies_count = 10` зробить однакову кількість — 10 — у всіх вибраних рядків.

**Практичний сенс:**
- `SET колонка = колонка + 1` використовують для **інкрементальних оновлень**: додався примірник, зросла ціна, збільшився лічильник, минув ще один рік стажу. Зберігає відносну різницю між рядками.
- `SET колонка = <число>` використовують для **уніфікації**: усім книгам категорії X встановити кількість 10, усім статусам «на перевірці» змінити на «доступно».

**Приклад із практики:**
```sql
UPDATE books SET copies_count = copies_count + 3 WHERE id = 5;
```
Оновлено рівно один рядок: 20 стане 23.

Якби було написано:
```sql
UPDATE books SET copies_count = 23 WHERE id = 5;
```
Результат був би той самий (бо ми точно знали поточне значення), але код менш «стійкий» — якщо хтось паралельно змінив би `copies_count`, `SET ... = 23` перезаписав би це значення, а `SET ... = copies_count + 3` додав би 3 до актуального.

### 2. Чому обмеження `NOT NULL`/`UNIQUE`/`CHECK` (Практика 5) завжди перевіряються при `UPDATE`, тоді як `FOREIGN KEY` — лише за умови `PRAGMA foreign_keys = ON;`?

**`NOT NULL`, `UNIQUE`, `CHECK`** — це **вбудовані властивості стовпця або таблиці**. Вони зберігаються в схемі (у `sqlite_master`) і перевіряються рушієм **при кожній спробі змінити рядок** — незалежно від того, чи ввімкнено якусь `PRAGMA`. Це не «налаштування», а частина визначення таблиці. Якщо стовпець оголошений `NOT NULL`, будь-який `INSERT` або `UPDATE`, який спробує записати туди `NULL`, буде відхилено **завжди**.

**`FOREIGN KEY`** — історично реалізований в SQLite **інакше**. Коли SQLite тільки з'являвся (2000 рік), обмеження зовнішніх ключів у ньому **не перевірялись**. Це було свідоме рішення:
- для сумісності зі старими версіями;
- щоб дати застосункам можливість самостійно контролювати цілісність (наприклад, під час масового імпорту даних).

Пізніше (з версії 3.6.19, 2009 рік) FK-перевірку додали, але **залишили вимкненою за замовчуванням** — щоб старі застосунки, які зберігали «сирітські» рядки, не ламалися після оновлення.

Тому щоб SQLite реально перевіряв FK, треба **явно увімкнути** це на кожному з'єднанні:

```sql
PRAGMA foreign_keys = ON;
```

Команда діє **тільки на поточне з'єднання**: кожен новий сеанс `sqlite3` або кожне нове відкриття бази в DB Browser — це окреме з'єднання, і SQLite скидає `PRAGMA` до типових значень (`OFF` для `foreign_keys`). Саме тому в кожному скрипті, який працює з FK, `PRAGMA foreign_keys = ON;` пишуть на самому початку.

**Коротко:** `NOT NULL`/`UNIQUE`/`CHECK` — «жорстко вбудовані» обмеження, які перевіряються завжди; `FOREIGN KEY` — «м'яке» обмеження, яке треба вмикати вручну на кожному з'єднанні.

### 3. Якби на вашій фактовій таблиці FK було оголошено з `ON DELETE CASCADE` замість `RESTRICT` (Лекція 5), як це змінило б наслідки видалення рядка з таблиці-виміру, на яку та фактова таблиця посилається?

У моєму варіанті фактова таблиця `loans` має **два** FK — на `books` і на `readers`:

- `loans.book_id → books.id` — **`ON DELETE RESTRICT`**
- `loans.reader_id → readers.id` — **`ON DELETE CASCADE`**

У Завданні 4 ми перевірили обидві дії:

**`RESTRICT` на книзі:** спроба `DELETE FROM books WHERE id = 1` впала з `FOREIGN KEY constraint failed`. Книгу не можна видалити, поки на неї посилається хоч один рядок у `loans`.

**`CASCADE` на читачі:** `DELETE FROM readers WHERE id = 1` виконався успішно, і всі три пов'язані видачі автоматично зникли.

**Якби `RESTRICT` замінили на `CASCADE` для книги:**

1. `DELETE FROM books WHERE id = 1` виконався б **успішно**.
2. Усі `loans`, де `book_id = 1`, теж **автоматично видалилися б** — разом із книгою зникла б уся історія її видач.

**Наслідки для бібліотеки:** катастрофічні. Видаливши книгу з каталогу (наприклад, випадково через неправильний клік у GUI), ми б втратили інформацію про всі випадки її видачі: кому, коли, на скільки днів. Це порушило б принципи бібліотечного обліку — кожен факт видачі має зберігатися, навіть якщо примірник списано.

**Правильний підхід у бібліотеці:** книга не видаляється фізично, а логічно «списується» — через додатковий стовпець `is_archived = 1` або `status = 'списано'`. Сам рядок у `books` залишається, історія видач зберігається недоторканою. Саме тому `RESTRICT` тут є правильним вибором.

**Якби `CASCADE` замінили на `RESTRICT` для читача:**

1. `DELETE FROM readers WHERE id = 1` впав би з `FOREIGN KEY constraint failed`.
2. Адміністратор мусив би спочатку вручну видалити всі `loans` цього читача, а потім уже видаляти самого читача.

Це безпечніше з погляду «захисту від випадкового видалення», але суперечить принципам захисту персональних даних: якщо читач просить видалити його з системи (наприклад, за запитом на видалення персональних даних), ми не повинні зберігати його персональну історію. `CASCADE` тут дозволяє одним запитом прибрати і читача, і всі його сліди в системі.

**Отже, вибір `RESTRICT` для книги і `CASCADE` для читача — це усвідомлене рішення, яке відображає різні бізнес-правила:** книгу «пам'ятаємо» навіть після списання, а читача «забуваємо» разом з історією.

### 4. Чому `DELETE` без `WHERE` небезпечніший за помилку типу чи порушення обмеження цілісності?

**`DELETE FROM <таблиця>;`** (без `WHERE`) видаляє **УСІ рядки** таблиці. Це **не помилка синтаксису й не порушення обмеження** — SQLite виконає команду **успішно** й повідомить «N рядків постражджало». Але наслідки катастрофічні: втрачено всі дані таблиці, часто — незворотно.

Порівняймо з іншими помилками:

| Ситуація | Що станеться | Дані |
|---|---|---|
| Синтаксична помилка (`SELCT * FROM ...`) | Команда не виконається, поверне помилку | **Не постраждали** |
| Порушення `NOT NULL`/`UNIQUE`/`CHECK` | Рядок не буде вставлений/оновлений | **Не постраждали** |
| Порушення `FOREIGN KEY` | Рядок не буде вставлений/оновлений/видалений | **Не постраждали** |
| `DELETE` без `WHERE` | **Команда виконується успішно** | **УСІ дані знищено** |

**Чому `DELETE` без `WHERE` небезпечніший:**

1. **Немає захисного механізму.** Помилки типу й обмеження — це «вбудовані гальма»: SQLite відмовляється виконувати небезпечну операцію. А `DELETE` без `WHERE` — це синтаксично коректна команда, яку SQLite виконує без жодних попереджень.

2. **Незворотність.** У SQLite немає вбудованого механізму «відкату» після успішного `DELETE`. Якщо не робили резервну копію або не використовували транзакцію з `ROLLBACK`, дані зникли назавжди.

3. **Неочевидність.** Синтаксична помилка одразу впадає в око — її видно при виконанні. Порушення обмеження повертає зрозуміле повідомлення. А `DELETE FROM loans;` — виглядає «нормально», і якщо не перевірити `SELECT COUNT(*)` до і після, можна не одразу помітити, що таблиця спорожніла.

4. **Наслідки для зв'язків.** Якщо на таблицю посилаються інші таблиці через FK, `DELETE` без `WHERE` може каскадно знищити дані й у них (при `ON DELETE CASCADE`) — або взагалі впасти (при `RESTRICT`). У великій схемі це може призвести до ланцюгової реакції.

**Правила безпеки:**

- **Завжди** писати `WHERE` у `DELETE` — навіть якщо хочете видалити все, краще явно `WHERE 1=1`, щоб це було видно в коді.
- **Перед** `DELETE` виконати `SELECT * FROM <таблиця> WHERE <та сама умова>` — перевірити, які рядки будуть видалені.
- **Для критичних даних** — робити бекап файлу `.db` або використовувати транзакцію з можливістю `ROLLBACK`:

```sql
BEGIN;
DELETE FROM loans WHERE id = 7;
-- перевірити, що видалено правильний рядок
-- якщо все ок:
COMMIT;
-- якщо ні:
ROLLBACK;
```

У нашій практиці `DELETE` завжди супроводжувався `WHERE` за первинним ключем — це найнадійніший спосіб видалити рівно один конкретний рядок.

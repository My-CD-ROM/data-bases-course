# Практична робота 15. Створення індексів та аналіз ефективності запитів

## Завдання 1. EXPLAIN QUERY PLAN до індексу

Для перевірки використано таблицю `membership_sales` та зовнішній ключ `client_id`.

```sql
EXPLAIN QUERY PLAN
SELECT *
FROM membership_sales
WHERE client_id = 1;
```

До створення індексу SQLite виконує повне сканування таблиці.

**Очікуваний план:**

```text
SCAN membership_sales
```

`SCAN` означає, що SQLite переглядає записи таблиці для пошуку потрібних даних.

## Завдання 2. CREATE INDEX на зовнішньому ключі

Для прискорення пошуку за зовнішнім ключем `client_id` створено індекс:

```sql
CREATE INDEX idx_sales_client
ON membership_sales(client_id);
```

Після створення індексу повторно виконано запит:

```sql
EXPLAIN QUERY PLAN
SELECT *
FROM membership_sales
WHERE client_id = 1;
```

**Очікуваний план:**

```text
SEARCH membership_sales USING INDEX idx_sales_client (client_id=?)
```

План змінився з `SCAN` на `SEARCH`. SQLite тепер може використовувати індекс для пошуку записів за значенням `client_id`, замість повного сканування таблиці.

## Завдання 3. Композитний індекс

Для дослідження композитного індексу використано дві колонки: `client_id` і `purchase_date`.

Запит:

```sql
SELECT *
FROM membership_sales
WHERE client_id = 1
AND purchase_date = '2026-10-01';
```

До створення композитного індексу SQLite може використовувати індекс `idx_sales_client`, але він допомагає шукати записи лише за першою умовою.

Створено композитний індекс:

```sql
CREATE INDEX idx_sales_client_date
ON membership_sales(client_id, purchase_date);
```

Після створення індексу SQLite може використовувати обидві колонки для пошуку.

**Очікуваний план після створення:**

```text
SEARCH membership_sales USING INDEX idx_sales_client_date
(client_id=? AND purchase_date=?)
```

Композитний індекс ефективніший для цього запиту, оскільки охоплює обидві умови пошуку. Важливим є порядок колонок: SQLite ефективно використовує композитний індекс починаючи з його першої колонки.

## Завдання 4. Індекс і ORDER BY

Для перевірки сортування використано колонку `purchase_date`.

Запит до створення індексу:

```sql
EXPLAIN QUERY PLAN
SELECT *
FROM membership_sales
ORDER BY purchase_date;
```

До створення індексу SQLite може виконувати сортування за допомогою тимчасової структури.

**Очікуваний план до індексу:**

```text
SCAN membership_sales
USE TEMP B-TREE FOR ORDER BY
```

Створено індекс:

```sql
CREATE INDEX idx_sales_purchase_date
ON membership_sales(purchase_date);
```

Після цього повторно виконано запит із `ORDER BY`.

**Очікуваний план після індексу:**

```text
SCAN membership_sales USING INDEX idx_sales_purchase_date
```

Індекс дозволяє SQLite отримувати записи у порядку значень `purchase_date`. У результаті може зникнути необхідність використання тимчасової структури для сортування `USE TEMP B-TREE FOR ORDER BY`.

## Завдання 5. DROP INDEX і повторна перевірка

Для видалення композитного індексу використано команду:

```sql
DROP INDEX idx_sales_client_date;
```

Після видалення повторно виконано запит за двома умовами.

SQLite може продовжити використовувати індекс `idx_sales_client`, оскільки він залишається в базі та допомагає пошуку за `client_id`.

Таким чином, видалення композитного індексу не обов'язково призводить до повного сканування таблиці, якщо існує інший відповідний індекс.

Для перевірки видалення індексу використано:

```sql
SELECT name
FROM sqlite_master
WHERE type = 'index'
AND tbl_name = 'membership_sales'
ORDER BY name;
```

У результатах запиту індекс `idx_sales_client_date` більше не відображається, що підтверджує його видалення.

## Контрольні питання

### 1. Чому EXPLAIN QUERY PLAN показує план, а не результат запиту?

`EXPLAIN QUERY PLAN` призначений для аналізу способу виконання запиту. Він показує, як SQLite планує отримувати дані: сканувати таблицю, використовувати індекс або виконувати додаткове сортування.

Перевіряти план важливо, тому що запит може правильно виконуватися, але бути неефективним. Аналіз плану допомагає знайти можливості для оптимізації.

### 2. Чому індекс на першій колонці дає менший ефект, ніж композитний?

Індекс на `client_id` допомагає знаходити записи за клієнтом, але не охоплює другу умову `purchase_date`.

Композитний індекс на `(client_id, purchase_date)` дозволяє використовувати обидві колонки для пошуку. Тому для запитів із двома умовами він може бути ефективнішим.

### 3. Яка ціна створення індексу і чому не потрібно індексувати кожну колонку?

Індекс займає додаткове місце на диску та потребує ресурсів для створення й обслуговування.

Під час додавання, зміни або видалення записів SQLite повинен також оновлювати відповідні індекси. Це може сповільнювати операції запису.

Тому індекси доцільно створювати для колонок, які часто використовуються у `WHERE`, `JOIN` та `ORDER BY`, а не для кожної колонки таблиці.

## Висновок

Під час практичної роботи було досліджено створення одноколонкових і композитних індексів у SQLite. За допомогою `EXPLAIN QUERY PLAN` проаналізовано плани виконання запитів до та після створення індексів.

Встановлено, що індекси можуть змінювати план виконання з `SCAN` на `SEARCH ... USING INDEX`, прискорювати пошук та зменшувати необхідність додаткового сортування.

Також було перевірено видалення індексу за допомогою `DROP INDEX` і підтверджено його відсутність у `sqlite_master`.

Зроблено висновок, що індекси є важливим інструментом оптимізації запитів, але їх потрібно використовувати обґрунтовано, враховуючи додаткові витрати на зберігання та обслуговування.

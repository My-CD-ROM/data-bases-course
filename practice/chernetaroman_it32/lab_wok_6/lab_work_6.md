# Практика 6

## Завдання 2

Для зміни ціни абонемента використано UPDATE, оскільки потрібно змінити значення існуючого запису, зберігши його ідентифікатор та зв'язки з іншими таблицями. Видаляти старий рядок і створювати новий для цього не потрібно.

## Завдання 4

Для зовнішніх ключів таблиці membership_sales у Практиці 4 було встановлено ON DELETE RESTRICT.

Перед виконанням DELETE прогноз був таким: видалення абонемента з id = 1 буде відхилено, оскільки на цей абонемент посилаються записи таблиці membership_sales. Пов'язані записи фактової таблиці не повинні бути видалені.

Фактичний результат: SQLite відхиляє видалення через обмеження FOREIGN KEY. Записи membership_sales з membership_id = 1 залишаються без змін.

Прогноз відповідає фактичному результату: ON DELETE RESTRICT забороняє видалення запису з таблиці memberships, якщо на нього існують посилання з membership_sales.

## Контрольні питання

### 1. Чим UPDATE ... SET колонка = колонка + 1 відрізняється від UPDATE ... SET колонка = конкретне число?

`колонка = колонка + 1` змінює поточне значення відносно його попереднього значення, а встановлення конкретного числа замінює значення на вказане число незалежно від попереднього.

### 2. Чому NOT NULL, UNIQUE і CHECK перевіряються при UPDATE, а FOREIGN KEY залежить від PRAGMA foreign_keys?

NOT NULL, UNIQUE і CHECK є обмеженнями самої таблиці та перевіряються SQLite під час зміни даних. Перевірка FOREIGN KEY у SQLite виконується лише тоді, коли увімкнено `PRAGMA foreign_keys = ON`.

### 3. Що змінилося б при ON DELETE CASCADE?

При ON DELETE CASCADE видалення абонемента з таблиці memberships автоматично видалило б усі пов'язані записи з membership_sales.

### 4. Чому DELETE без WHERE небезпечніший?

DELETE без WHERE видаляє всі рядки таблиці, тому одна помилка може призвести до повної втрати даних. Умова WHERE дозволяє обмежити видалення конкретним записом або набором записів.

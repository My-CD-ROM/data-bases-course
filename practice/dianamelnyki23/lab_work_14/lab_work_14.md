## Використана база

Використано копію `lab_work_13.db`. У схемі є таблиці `clients`, `memberships`, `membership_sales` і `visits`. Початковий файл не змінювався. У `memberships` немає лічильника чи статусу, тому для завдання 1 використано пов’язаний факт продажу абонемента і дату завершення попереднього продажу.

## Завдання 1. Атомарна пара INSERT + UPDATE

Для клієнта з `id = 2` додано продаж нового абонемента (`membership_id = 3`) з датою початку 2026-10-11 та датою завершення 2026-11-10. У тій самій транзакції дату завершення попереднього пов’язаного продажу (`id = 10`) змінено з 2026-10-10 на 2026-10-11, щоб перехід між абонементами був без розриву.

Обидві зміни належать до однієї операції поновлення абонемента. Якщо вставити новий продаж, але не змінити дату попереднього, перехідний день може не відповідати домовленості про безперервну дію. Якщо ж змінити дату старого запису, але не створити новий продаж, у базі не буде факту покупки наступного абонемента. Транзакція дозволяє зафіксувати обидві зміни разом або скасувати обидві.

Перевірка до транзакції показувала для продажу `id = 10` дату завершення `2026-10-10`. Усередині транзакції SELECT показав старий рядок із датою `2026-10-11` і новий продаж. Після COMMIT обидва записи залишилися в базі.

## Завдання 2. Свідомий ROLLBACK

У транзакції було додано тестовий продаж абонемента для клієнта `id = 7`, після чого виконано SELECT і ROLLBACK. SELECT до відкату показав тимчасовий рядок продажу з `membership_id = 2`. Повторний SELECT після ROLLBACK не знайшов цього рядка. Це підтверджує, що ROLLBACK скасував зміну.

## Завдання 3. Проміжний стан усередині транзакції

Після BEGIN додано тестове відвідування клієнта `id = 7` на дату 2026-10-12 і виконано SELECT до завершення транзакції. Для `visit_type` використано наявне допустиме значення з іншого відвідування, щоб дотриматися обмеження CHECK таблиці. У цій самій сесії SELECT побачив новий рядок (id 13). Власна сесія бачить незавершені зміни, проте інші транзакції не повинні вважати їх зафіксованими. До COMMIT зміни ще можна скасувати командою ROLLBACK; після відкату фінальний SELECT цей рядок не знаходить.

## Завдання 4. Помилка всередині транзакції

У транзакції успішно додано тестового клієнта з телефоном `+380670000141`. Наступна команда спробувала додати другого клієнта з тим самим телефоном, що порушує обмеження UNIQUE.

Точний текст помилки SQLite:

```text
UNIQUE constraint failed: clients.phone
```

Після помилки SELECT у відкритій транзакції все ще знаходив першого доданого клієнта. Це означає, що помилка другої команди сама по собі не скасувала першу команду й не закрила транзакцію. Після ROLLBACK повторний SELECT не знайшов тестового клієнта.

## Завдання 5. Забутий ROLLBACK

Сценарій повторено з телефоном `+380670000142`: перший INSERT успішно додав тестового клієнта, другий INSERT з тим самим телефоном завершився помилкою UNIQUE. Після помилки виконано COMMIT. Фінальний SELECT показав першого клієнта, але другого рядка-дубліката немає.

Результат саме такий, тому що SQLite скасовує невдалу окрему команду через порушення обмеження, але транзакцію загалом автоматично не відкочує. Успішний перший INSERT залишається частиною відкритої транзакції, і COMMIT зберігає цю успішну зміну. Розробник мав явно виконати ROLLBACK, якщо хотів скасувати всю групу змін.

Атомарність гарантує «все або нічого» для групи змін, яку розробник завершив COMMIT або ROLLBACK. У завданні 5 COMMIT наказав СУБД зафіксувати всі успішні команди транзакції; помилкова команда не стала зміною. Небезпека в тому, що розробник може помилково припустити, ніби помилка автоматично скасувала попередні успішні команди.

## Відповіді на підсумкові питання

**Що могло піти не так у завданні 1 без транзакції?**  
Якби між INSERT продажу й UPDATE дати завершення стався збій, у базі залишився б лише один крок операції. Продаж міг би існувати без узгодженого періоду дії або попередня дата могла б змінитися без запису нового продажу.

**Чому після COMMIT у завданні 5 є перша зміна, але немає другої?**  
Перший INSERT виконався успішно. Другий INSERT не змінив базу, бо порушив UNIQUE. Помилка відхилила лише цю команду; COMMIT згодом зафіксував успішний перший INSERT.

**Як це узгоджується з атомарністю?**  
SQLite гарантувала узгоджене виконання кожної команди та атомарність явного завершення транзакції. Вона не вирішує за розробника, чи треба скасувати всю транзакцію після помилки однієї команди. Для цього розробник мав виконати ROLLBACK; натомість COMMIT зафіксував успішну частину.

## Висновок

На копії бази виконано атомарний продаж абонемента, свідомий відкат і перевірку видимості незавершеної зміни. Також підтверджено, що помилка обмеження UNIQUE не відкочує автоматично попередні успішні команди: після ROLLBACK вони зникають, а після COMMIT залишаються.

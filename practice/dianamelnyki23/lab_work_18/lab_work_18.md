# Практична робота 18. Згенеровані стовпці у SQLite

**Варіант:** 7 — спортзал

## Завдання 1. Похідне числове значення

У таблицю `memberships` додано `weekly_equivalent` — еквівалентну вартість абонемента за 7 днів:

```sql
ROUND(price * 7.0 / duration_days, 2)
```

Формула використовує тільки колонки того самого рядка. Бізнес-сенс: привести абонементи різної тривалості до спільної семиденної вартості, щоб їх було простіше порівнювати.

Наприклад, для `fitness basic` із ціною 699 грн і тривалістю 30 днів згенероване значення дорівнює **163.10 грн за 7 днів**.

## Завдання 2. Похідний логічний прапорець

Додано `is_30_day` з формулою `duration_days = 30`. SQLite повертає `1`, якщо абонемент триває 30 днів, і `0` в іншому разі. У таблиці тривалість має значення `NOT NULL`, тому порівняння не повертає `NULL`.

## Завдання 3. Спроба прямого запису

Спроба виконати `UPDATE memberships SET weekly_equivalent = 1 WHERE id = 8` завершилася помилкою:

```text
Parse error near line 17 of lab_work_18.sql: cannot UPDATE generated column "weekly_equivalent"
```

Значення похідного стовпця не можна задавати вручну — SQLite обчислює його з базових колонок.

## Завдання 4. Автоматичний перерахунок

Для рядка `id = 8` початково `price = 699.0`, а `weekly_equivalent = 163.1`. Після зміни базової ціни на 799.0 нове згенероване значення стало **186.43** без окремого оновлення похідного стовпця. Після перевірки початкову ціну 699.0 відновлено, щоб не змінювати дані абонемента у фінальній базі.

## Завдання 5. Фільтрація за згенерованою колонкою

Запит `WHERE weekly_equivalent > 200` повертає абонементи, семиденний еквівалент ціни яких перевищує 200 грн. Такий запис зрозуміліший за повторення формули `ROUND(price * 7.0 / duration_days, 2)` у кожному запиті. Якщо формула зміниться, достатньо змінити визначення згенерованої колонки, а запити продовжать використовувати її назву.

## Контрольні запитання

**Чому в цій практиці можна створити лише `VIRTUAL`, а не `STORED` колонку?**  
SQLite дозволяє додати через `ALTER TABLE ... ADD COLUMN` згенеровану колонку `VIRTUAL`, яка обчислюється під час читання. Додавання `STORED` вимагало б записати обчислені значення для вже наявних рядків і перебудувати таблицю; SQLite не підтримує додавання `STORED` згенерованої колонки цією командою.

**Що станеться, якщо видалити базову колонку, від якої залежить згенерована?**  
SQLite не дозволить видалити базову колонку, поки від неї залежить generated column: схема втратила б формулу, яку потрібно обчислювати. Спочатку треба прибрати залежний згенерований стовпець або перебудувати таблицю без залежності.

**Чому неможливість прямого запису в згенеровану колонку є перевагою?**  
Це запобігає розбіжності між базовими даними та похідним значенням. Усі записи отримують результат з однієї формули, а SQLite перераховує його автоматично при зміні базових колонок.

## Висновок

До `memberships` додано два `VIRTUAL`-стовпці: числовий еквівалент вартості за тиждень і прапорець 30-денної тривалості. Перевірено заборону прямого оновлення generated column, автоматичний перерахунок при зміні `price` та фільтрацію за згенерованим значенням. Початкову ціну тестового абонемента у фінальній базі відновлено.

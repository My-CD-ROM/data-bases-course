# Практична робота 5

## Обмеження цілісності даних: NOT NULL, UNIQUE, CHECK, DEFAULT

**Варіант:** 7
**Предметна область:** Фітнес-клуб
**Виконала:** Мельник Діана, група I-23

## 1. Мета роботи

Метою практичної роботи є вивчення обмежень цілісності даних у SQLite: NOT NULL, UNIQUE, CHECK та DEFAULT, а також набуття практичних навичок їх додавання шляхом перестворення таблиць, перевірки коректних і некоректних операцій та аналізу результатів.

## 2. Виконання роботи

### Завдання 1. Обмеження NOT NULL

Для таблиці `clients` було явно встановлено обмеження NOT NULL для поля `phone`.

Після перестворення таблиці було виконано спробу додати клієнта без зазначення номера телефону.

SQLite відхилив операцію з помилкою:

`Error near line 15: NOT NULL constraint failed: clients.phone`

Це підтверджує, що поле `phone` не може містити порожнє значення.

### Завдання 2. Обмеження UNIQUE

Для поля `clients.phone` було встановлено обмеження UNIQUE.

Після цього було виконано спробу додати клієнта з номером телефону, який уже існує в таблиці.

SQLite відхилив операцію з помилкою:

`Error near line 28: UNIQUE constraint failed: clients.phone`

Отже, два клієнти не можуть мати однаковий номер телефону.

### Завдання 3. Обмеження CHECK

Для поля `memberships.price` було встановлено обмеження CHECK, яке дозволяє використовувати тільки додатні значення ціни.

Під час перевірки було виконано спробу додати абонемент з від'ємною ціною.

SQLite відхилив операцію з помилкою:

`Error near line 43: CHECK constraint failed: price > 0`

Після цього було перевірено коректне значення ціни. Запис із додатною ціною був успішно доданий, після перевірки тестовий запис було видалено.

### Завдання 4. Обмеження DEFAULT

Для поля `memberships.duration_days` було встановлено значення за замовчуванням — 30 днів.

Для перевірки було створено тестовий абонемент без зазначення тривалості. SQLite автоматично встановив значення `30`.

Результат перевірки:

* тип: `Тестовий DEFAULT`;
* тривалість: `30` днів;
* ціна: `1000.0`.

Після перевірки тестовий запис було видалено.

### Завдання 5. Перевірка обмеження через UPDATE

Для перевірки роботи CHECK під час оновлення даних було виконано спробу встановити для першого абонемента від'ємну ціну.

SQLite відхилив операцію з помилкою:

`Error near line 66: CHECK constraint failed: price > 0`

Таким чином, обмеження CHECK контролює не тільки додавання нових записів через INSERT, а й зміну вже існуючих записів через UPDATE.

## 3. Перевірка збереження даних

Після виконання всіх операцій було перевірено кількість записів у таблицях.

Результати перевірки:

* клієнтів — 6;
* абонементів — 6;
* продажів — 10.

Отже, початкові дані були збережені.

Також було перевірено зовнішні ключі таблиці `membership_sales`. Вони правильно посилаються на таблиці `clients` та `memberships`.

Для клієнтів використовується дія `ON DELETE CASCADE`, а для абонементів — `ON DELETE RESTRICT`.

Додаткова перевірка цілісності зовнішніх ключів не виявила порушень.

## 4. Відповіді на контрольні питання

### 1. Чому в SQLite не можна просто виконати ALTER TABLE ... ADD CONSTRAINT CHECK?

SQLite має обмежені можливості команди ALTER TABLE і не дозволяє додавати CHECK-обмеження до вже існуючої таблиці окремою командою. Тому таблицю необхідно перестворити з потрібним обмеженням, перенести до неї дані, а стару таблицю видалити.

### 2. Що буде, якщо додати NOT NULL до існуючого стовпця, де вже є NULL?

Якщо в існуючій таблиці є NULL-значення, їх потрібно спочатку замінити або видалити. Інакше після встановлення NOT NULL дані не відповідатимуть новому обмеженню.

### 3. Чим CHECK, доданий шляхом перестворення таблиці, відрізняється від CHECK при CREATE TABLE?

У SQLite CHECK фактично задається під час створення таблиці. Якщо потрібно додати його до існуючої таблиці, використовується перестворення таблиці з новим визначенням та перенесенням даних.

### 4. Чому DEFAULT не перевіряється через порушення, як інші обмеження?

DEFAULT не забороняє значення, а автоматично підставляє його, коли значення не було задано. Тому його правильність перевіряють шляхом INSERT без зазначення відповідного поля та подальшого SELECT.

### 5. Оцінка виконаної роботи

У роботі було виконано перестворення таблиць із використанням NOT NULL, UNIQUE, CHECK та DEFAULT. Дані були перенесені та збережені. Роботу обмежень перевірено за допомогою INSERT та UPDATE, а для помилкових операцій зафіксовано точні повідомлення SQLite. Значення DEFAULT також було перевірено окремим тестовим записом.

## 5. Бізнес-логіка використаних обмежень

**NOT NULL:** номер телефону клієнта є обов'язковим для збереження контактної інформації.

**UNIQUE:** номер телефону має бути унікальним, щоб не створювати дублікати клієнтів.

**CHECK:** ціна абонемента повинна бути додатною, оскільки від'ємна або нульова ціна не відповідає логіці продажу абонемента.

**DEFAULT:** стандартна тривалість абонемента становить 30 днів, якщо інше значення не було вказане під час створення запису.

## 6. Висновок

Під час практичної роботи було опрацьовано основні обмеження цілісності даних у SQLite: NOT NULL, UNIQUE, CHECK та DEFAULT. Було отримано практичний досвід перестворення таблиць, перенесення існуючих даних та перевірки роботи обмежень. Також було перевірено, що обмеження контролюють як додавання, так і оновлення даних. У результаті структура бази даних була доповнена необхідними обмеженнями, а початкові записи збережені.

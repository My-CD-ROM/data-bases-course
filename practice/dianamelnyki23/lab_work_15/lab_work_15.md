## Використана таблиця

Практичну виконано на копії фінальної бази з практики 14. Фактовою таблицею обрано `visits`; зовнішній ключ — `client_id`, колонка тривалості — `duration_minutes`, колонка дати — `visit_date`. Структуру таблиць не змінювали. Початковий індексний стан не містив створених у цій роботі користувацьких індексів.

## Завдання 1. План до індексу

Для запиту `SELECT * FROM visits WHERE client_id = 2` до створення індексу SQLite показала:

```text
`--SCAN visits
```

Отже, SQLite переглядала рядки таблиці `visits`, щоб знайти записи потрібного клієнта.

## Завдання 2. Індекс на зовнішньому ключі

Створено індекс `idx_visits_client` на колонці `visits.client_id`. План того самого запиту змінився на:

```text
`--SEARCH visits USING INDEX idx_visits_client (client_id=?)
```

Замість повного перегляду таблиці SQLite може шукати потрібні рядки через індекс за `client_id`.

## Завдання 3. Композитний індекс

Для запиту з двома фільтрами до композитного індексу план використовував одноколонковий індекс і перевіряв `duration_minutes` після пошуку за клієнтом:

```text
`--SEARCH visits USING INDEX idx_visits_client (client_id=?)
```

Після створення `idx_visits_client_duration` на `(client_id, duration_minutes)` план став таким:

```text
`--SEARCH visits USING INDEX idx_visits_client_duration (client_id=? AND duration_minutes=?)
```

Композитний індекс містить обидві колонки в заданому порядку, тому SQLite застосовує обидві умови під час пошуку індексу. Одноколонковий індекс звужував пошук лише за клієнтом.

## Завдання 4. Індекс і ORDER BY

До індексу запит `SELECT visit_date FROM visits ORDER BY visit_date` мав план:

```text
|--SCAN visits
`--USE TEMP B-TREE FOR ORDER BY
```

SQLite переглядала таблицю та створювала тимчасове B-tree для сортування. Після створення `idx_visits_date` план став:

```text
`--SCAN visits USING COVERING INDEX idx_visits_date
```

SQLite читає значення дат уже в порядку індексу. Індекс покриває запит, бо запитується тільки `visit_date`, тому додатковий тимчасовий крок сортування не потрібен.

## Завдання 5. DROP INDEX

Видалено `idx_visits_client`. Після цього запит за `client_id` отримав план:

```text
`--SEARCH visits USING INDEX idx_visits_client_duration (client_id=?)
```

План не повернувся до `SCAN`, оскільки залишився композитний індекс, перша колонка якого — `client_id`. Запит до `sqlite_master` для `idx_visits_client` повернув 0 рядків, що підтверджує видалення індексу. У фінальній базі лишилися `idx_visits_client_duration` та `idx_visits_date`.

## Контрольні запитання

**Чому `EXPLAIN QUERY PLAN` показує план, а не результат запиту, і навіщо перевіряти план окремо?**  
Команда пояснює, як SQLite планує отримати дані, але не виконує запит для повернення рядків. Звичайний SELECT може бути правильним за результатом, але виконуватися повним скануванням або непотрібним сортуванням. План допомагає побачити, чи використовує SQLite індекс.

**Чому індекс лише на першій колонці дає менший ефект, ніж композитний?**  
Для умови за двома колонками одноколонковий індекс звужує пошук тільки за першою колонкою, а другу умову доводиться перевіряти окремо. Композитний індекс на `(client_id, duration_minutes)` дозволив використати обидві умови в пошуку.

**Яка ціна індексу і чому не варто індексувати всі колонки?**  
Індекс займає додаткове місце та потребує оновлення під час INSERT, UPDATE і DELETE. Надмірна кількість індексів збільшує розмір бази й уповільнює зміни даних, тому індекси варто створювати для запитів, яким вони реально допомагають.

## Висновок

На таблиці `visits` перевірено зміну планів із повного сканування на пошук через індекси. Композитний індекс дозволив SQLite врахувати дві умови, а індекс за датою усунув тимчасове сортування для відповідного запиту. Після видалення одноколонкового індексу оптимізатор продовжив використовувати композитний.

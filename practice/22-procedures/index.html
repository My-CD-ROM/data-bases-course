    Практика 22. Створення процедур у PostgreSQL¶

    Мета заняття: оформити атомарну пару пов'язаних змін (за зразком Практики 14, тепер у PostgreSQL) як іменовану процедуру мовою PL/pgSQL, викликати її через CALL, додати перевірку вхідних даних і повернути результат через OUT-параметр. Окремої лекції для цієї теми немає: усе потрібне наведено в розділі «Теорія» нижче.

    Теорія: процедури у PostgreSQL¶

    Функції з Лекції 17 обчислюють значення і викликаються прямо в запиті. Але часто потрібне інше: іменована дія, що змінює дані (записати візит, оформити продаж, видати книгу), яку викликають однією командою замість кількох запитів щоразу. Для цього в PostgreSQL є окремий вид об'єкта: процедура.

    Приклади нижче використовують базу ветклініки (таблиці owners, animals, vets, visits). Щоб повторити їх і отримати ті самі результати, створіть окрему базу (наприклад, vet_demo) і виконайте в ній файл vet_clinic_demo.sql. Приклади виконуйте по черзі, бо кожен спирається на стан бази після попереднього.

    1. CREATE PROCEDURE і CALL¶

    Запис візиту до лікаря складається з двох пов'язаних змін: новий рядок у visits і статус тварини 'на лікуванні' в animals. Оформимо їх як процедуру:

    CREATE PROCEDURE register_visit(p_animal_id INTEGER, p_vet_id INTEGER, p_diagnosis TEXT)
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO visits (animal_id, vet_id, visit_date, diagnosis)
    VALUES (p_animal_id, p_vet_id, CURRENT_DATE, p_diagnosis);

    UPDATE animals SET status = 'на лікуванні' WHERE id = p_animal_id;
END;
$$;

CALL register_visit(2, 1, 'отит');
SELECT id, name, status FROM animals WHERE id = 2;

     id |  name  |    status
----+--------+--------------
  2 | Барсик | на лікуванні

    Синтаксис схожий на функцію: параметри з типами в дужках, тіло між $$, мова plpgsql. Відмінність одна, але принципова: немає RETURNS, бо процедура не є виразом, що повертає значення в запит. Тому й викликають її окремою командою CALL, а в visits після виклику 4 рядки замість 3.

    2. Процедуру не викликають через SELECT¶

    SELECT register_visit(2, 1, 'отит');

    ERROR:  register_visit(integer, integer, unknown) is a procedure
LINE 1: SELECT register_visit(2, 1, 'отит');
               ^
HINT:  To call a procedure, use CALL.

    PostgreSQL не просто відмовляє, а підказує правильну команду. Друга типова помилка: неповний список аргументів. Процедуру шукають за назвою і кількістю та типами параметрів, тож виклик CALL register_visit(2, 1); дає ERROR: procedure register_visit(integer, integer) does not exist.

    3. Процедура і функція: порівняння¶

    Функція (Лекція 17) Процедура
    Оголошення CREATE FUNCTION ... RETURNS тип CREATE PROCEDURE ... без RETURNS
    Виклик у запиті: SELECT f(...), WHERE f(...) = ... окремою командою CALL p(...)
    Результат значення чи набір рядків для запиту лише через OUT/INOUT-параметри (розділ 5)
    COMMIT/ROLLBACK у тілі заборонено дозволено (Практика 23)
    Типове призначення обчислення всередині запиту самостійна дія, послідовність змін

    Увесь виклик CALL виконується як одна транзакція. Якщо будь-який крок процедури завершиться помилкою, скасуються й уже виконані кроки цього виклику, тож атомарна пара з Практики 14 (BEGIN, два запити, COMMIT) тепер займає один рядок CALL. Керування транзакцією всередині процедури розглянуто в Практиці 23.

    4. Перевірка вхідних даних: IF і RAISE EXCEPTION¶

    Процедура з розділу 1 запише візит навіть із порожнім діагнозом. Додамо перевірку на початок тіла, до будь-яких змін. CREATE OR REPLACE замінює тіло наявної процедури з тими самими параметрами:

    CREATE OR REPLACE PROCEDURE register_visit(p_animal_id INTEGER, p_vet_id INTEGER, p_diagnosis TEXT)
LANGUAGE plpgsql
AS $$
BEGIN
    IF p_diagnosis IS NULL OR trim(p_diagnosis) = '' THEN
        RAISE EXCEPTION 'Діагноз не може бути порожнім (тварина %)', p_animal_id;
    END IF;

    INSERT INTO visits (animal_id, vet_id, visit_date, diagnosis)
    VALUES (p_animal_id, p_vet_id, CURRENT_DATE, p_diagnosis);

    UPDATE animals SET status = 'на лікуванні' WHERE id = p_animal_id;
END;
$$;

CALL register_visit(1, 2, '');

    ERROR:  Діагноз не може бути порожнім (тварина 1)
CONTEXT:  PL/pgSQL function register_visit(integer,integer,text) line 4 at RAISE

    RAISE EXCEPTION працює так само, як у функціях (Лекція 17, розділ 6): перериває виконання, а % підставляє значення аргументу. Після помилки в visits так само 4 рядки, а Мурка (id 1) лишилась 'на обліку': до змін справа не дійшла. Умова IS NULL потрібна не випадково: порівняння trim(NULL) = '' дає невизначений результат, і без неї NULL пройшов би перевірку (Лекція 17, розділ 7). Рядок CONTEXT у PostgreSQL пише «function» і для процедур, це нормально.

    5. Параметри IN, OUT, INOUT і значення за умовчанням¶

    Кожен параметр має режим. IN (за умовчанням) лише передає значення в процедуру. OUT повертає значення з процедури. INOUT робить обидва: значення передають усередину, а після виклику отримують нове. Типовий випадок для OUT: повернути id щойно доданого рядка, щоб не шукати його окремим запитом. RETURNING id INTO записує згенерований id прямо в параметр:

    CREATE PROCEDURE add_visit(
    p_animal_id INTEGER,
    p_vet_id INTEGER,
    p_diagnosis TEXT,
    OUT p_visit_id INTEGER
)
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO visits (animal_id, vet_id, visit_date, diagnosis)
    VALUES (p_animal_id, p_vet_id, CURRENT_DATE, p_diagnosis)
    RETURNING id INTO p_visit_id;

    UPDATE animals SET status = 'на лікуванні' WHERE id = p_animal_id;
END;
$$;

CALL add_visit(3, 2, 'перелом лапи', NULL);

     p_visit_id
------------
          5

    На місці OUT-параметра у CALL передають NULL як заповнювач, а результат повертається рядком, як у SELECT (у pgAdmin він з'являється на вкладці Data Output). Без заповнювача PostgreSQL не знайде процедуру: procedure add_visit(integer, integer, unknown) does not exist.

    Параметру можна задати значення за умовчанням (DEFAULT), і тоді при виклику його можна пропустити. Процедура нижче встановлює новий статус і через той самий INOUT-параметр повертає попередній:

    CREATE PROCEDURE set_status(p_animal_id INTEGER, INOUT p_status TEXT DEFAULT 'на обліку')
LANGUAGE plpgsql
AS $$
DECLARE
    v_old TEXT;
BEGIN
    SELECT status INTO v_old FROM animals WHERE id = p_animal_id;
    UPDATE animals SET status = p_status WHERE id = p_animal_id;
    p_status := v_old;
END;
$$;

CALL set_status(3, 'вибув');   -- поверне 'на лікуванні'
CALL set_status(3);            -- поверне 'вибув', новий статус 'на обліку'

    6. Перегляд, зміна і видалення процедур¶

    У psql процедури показує команда \df, у pgAdmin вони розташовані у вітці Procedures схеми public. У колонці Type для процедури стоїть proc (для функції func), а Result data type порожній:

     Schema |      Name      | Result data type |                                   Argument data types                                    | Type
--------+----------------+------------------+------------------------------------------------------------------------------------------+------
 public | add_visit      |                  | IN p_animal_id integer, IN p_vet_id integer, IN p_diagnosis text, OUT p_visit_id integer | proc
 public | register_visit |                  | IN p_animal_id integer, IN p_vet_id integer, IN p_diagnosis text                         | proc
 public | set_status     |                  | IN p_animal_id integer, INOUT p_status text DEFAULT 'на обліку'::text                    | proc

    Як і функції, процедури можуть бути перевантаженими (однакова назва, різні параметри), тому у DROP PROCEDURE вказують типи вхідних параметрів: DROP PROCEDURE add_visit(INTEGER, INTEGER, TEXT);. CREATE OR REPLACE змінює лише тіло. Якщо додати новий вхідний параметр, з'явиться друга процедура з тією самою назвою, а якщо додати до наявної процедури OUT-параметр, PostgreSQL відмовить:

    ERROR:  cannot change whether a procedure has output parameters
HINT:  Use DROP PROCEDURE register_visit(integer,integer,text) first.

    Тому процедуру з OUT-параметром або створюють під новою назвою (як add_visit), або спершу видаляють стару версію.

    Варіант¶

    Ваша база у PostgreSQL з Практики 19 (перенесена схема й дані). Якщо базу втрачено, поверніться до Практики 19. Знадобиться також атомарна пара змін, яку ви виконували вручну в Практиці 14: INSERT у фактову таблицю і UPDATE пов'язаного рядка (лічильника чи статусу в таблиці-вимірі або пов'язаного рядка фактової таблиці). Структура вашого варіанта наведена в таблиці варіантів Практики 3.

    Команди виконуйте в Query Tool у pgAdmin (чи в psql). Якщо колонка дати у вашій таблиці має тип TEXT, а не DATE, CURRENT_DATE однаково можна записувати в неї: PostgreSQL сам перетворить дату на текст вигляду 2026-10-16.

    Завдання¶

    Завдання 1. Процедура для атомарної пари. Напишіть процедуру, що виконує атомарну пару змін вашого варіанта з Практики 14: INSERT у фактову таблицю і UPDATE пов'язаного рядка. Параметри процедури (з префіксом p_) мають містити всі значення, потрібні для обох операцій; дату можна брати з CURRENT_DATE. Перед викликом запишіть SELECT-ом поточний стан обох рядків, потім викличте процедуру через CALL з реальними значеннями свого варіанта і повторним SELECT підтвердьте, що застосувались обидві зміни.

    Завдання 2. Свідомі помилки виклику. Спробуйте викликати свою процедуру через SELECT ваша_процедура(...) замість CALL, а потім через CALL з меншою кількістю аргументів, ніж оголошено. Зафіксуйте письмово точний текст обох помилок разом із рядками HINT і поясніть, чому PostgreSQL не знайшов процедуру в другому випадку.

    Завдання 3. Перевірка вхідних даних. Додайте до процедури (через CREATE OR REPLACE PROCEDURE) перевірку IF ... THEN RAISE EXCEPTION ... на початку тіла, що не дає виконати операцію за нелогічних вхідних даних: від'ємна чи нульова кількість або ціна, порожній текст, оцінка поза шкалою, NULL замість обов'язкового значення тощо. Повідомлення має пояснювати причину й містити значення через %. Перевірте обидва випадки: виклик із коректними даними (успіх) і з некоректними (помилка), і SELECT-ом підтвердьте, що після помилки жодна з двох таблиць не змінилась.

    Завдання 4. OUT-параметр. Створіть другу процедуру (з новою назвою, наприклад, з суфіксом _ret), що виконує ту саму пару змін і повертає через OUT-параметр id щойно доданого рядка фактової таблиці (INSERT ... RETURNING id INTO ...). Викличте її, передавши NULL на місці OUT-параметра, і порівняйте отримане значення з SELECT MAX(id) фактової таблиці. Виконайте \df (або відкрийте вітку Procedures у pgAdmin) і запишіть, як позначено режими параметрів обох процедур.

    Завдання 5. Порівняння з Практикою 14. Письмово порівняйте підхід цієї практики (іменована процедура з перевіркою, викликана одним CALL) з підходом Практики 14 (ручний BEGIN, два запити, COMMIT щоразу заново). Що саме процедура дозволяє НЕ повторювати, де тепер зберігається перевірка вхідних даних і що гарантує атомарність виклику, якщо в процедурі немає жодного BEGIN чи COMMIT?

    Що здати й оцінюється¶

    Здайте lab_work_22.sql: усі CREATE PROCEDURE (Завдання 1, 3, 4), виклики CALL з результатами перевірочних SELECT, точні тексти помилок із Завдань 2 і 3; і lab_work_22.md: письмові пояснення до Завдань 2 і 4 та порівняння із Завдання 5. Контрольні питання:

    • Процедуру із Завдання 1 технічно можна переписати як функцію RETURNS VOID. Чим тоді відрізнявся б виклик і чому для дії, що змінює дані, обирають процедуру?
    • Що станеться з першою зміною (INSERT), якщо друга (UPDATE) у тому самому виклику процедури завершиться помилкою? Чому?
    • Чому перевірку в Завданні 3 ставлять на початок тіла, а не після INSERT і UPDATE?
    • Навіщо у CALL передавати NULL на місці OUT-параметра і чим OUT відрізняється від INOUT?

    Оцінюється коректність процедури Завдання 1 (обидві зміни, перевірені SELECT), точно зафіксовані помилки Завдання 2, робоча перевірка обох випадків (успіх і помилка) у Завданні 3 і правильно повернутий id у Завданні 4.

    Підсумок заняття¶

    • Оформлено атомарну пару змін фактової та вимірної таблиці свого варіанта як іменовану процедуру мовою PL/pgSQL.
    • На практиці підтверджено: процедуру викликають лише через CALL, а PostgreSQL розрізняє процедури за назвою і списком параметрів.
    • Додано перевірку вхідних даних з RAISE EXCEPTION і підтверджено, що помилка скасовує весь виклик.
    • Використано OUT-параметр, щоб повернути з процедури id нового рядка.

    Теорія до цієї практики: розділ «Теорія» вище на цій сторінці (спирається на Лекцію 17. Функції у PostgreSQL).

# Practice 14 — Importing data from CSV into SQLite

**Variant:** 4 — Apteka (Pharmacy)
**Deliverables:** `medicines.db` (SQLite database), `script.sql`, `v4_new_rows.csv`
(input file: 8 new rows for `medicines`), this `readme.md`.

## Task 1 — Count BEFORE the import
```sql
SELECT COUNT(*) AS medicines_count_before FROM medicines;   -- 12
```

## Task 2 — Staging table and CSV import
The staging table matches the CSV header exactly (no `id` column):
```sql
CREATE TABLE medicines_staging (name TEXT, manufacturer TEXT, form TEXT, price REAL, stock_quantity INTEGER);
```
Then, via the CLI:
```
.mode csv
.import --skip 1 v4_new_rows.csv medicines_staging
```
Verification: `SELECT COUNT(*) FROM medicines_staging;` → **8**.

## Task 3 — Move into the real table, drop staging, count again
```sql
INSERT INTO medicines (name, manufacturer, form, price, stock_quantity)
SELECT name, manufacturer, form, price, stock_quantity FROM medicines_staging;
DROP TABLE medicines_staging;
SELECT COUNT(*) AS medicines_count_after FROM medicines;    -- 20
```
The difference from Task 1 is exactly **20 − 12 = 8**, matching the number of CSV rows.

## Task 4 — Verify the specific new rows with continuing ids
```sql
SELECT id, name, price FROM medicines
WHERE name IN ('Німесил','Ренні','Ефералган','Ліностин','Цитрамон','Кетанов','Фервекс','Смекта')
ORDER BY id;
```
Result: the 8 rows received `id = 13 … 20` — the numbering **continues** the previous
rows (1…12) instead of restarting at 1, because SQLite auto-assigns the next free integer
for the rowid alias.

## Task 5 — Intentional error: direct import into the real table
Run on a separate **test copy** `medicines_test.db` (so the working DB was untouched).
Direct `.import v4_new_rows.csv medicines` into the table that has an `id` column
produced, for every CSV row:
```
v4_new_rows.csv:1: expected 6 columns but found 5 - filling the rest with NULL
v4_new_rows.csv:1: INSERT failed: datatype mismatch
```
**Why this does not work:** the CSV has **5** columns (no `id`), but the table has **6**
columns. SQLite positions the 5 CSV values into the first 5 table columns
(`id, name, manufacturer, form, price`), leaving `stock_quantity` as NULL — so the first
value (the medicine *name*, e.g. `Німесил`) lands in the INTEGER `id` column, which
triggers a `datatype mismatch` and rejects the row. Net effect: **0 of 8 rows** were
imported (count stayed 1), showing that a direct import without a header-aligned staging
table either fails or silently corrupts the column mapping.

## Review questions and answers

**1. Why does this practice's CSV deliberately NOT contain the `id` column — what would happen if you added one with arbitrary values?**

The `id` is the primary key and is meant to be auto-generated by SQLite so that it is
unique and correct. Adding arbitrary ids by hand risks **duplicates or collisions** with
existing rows (comma-syntax table already holds ids 1–12) which would violate the primary
key, and forces you to track the "next" value manually. Letting the rowid alias generate
ids guarantees uniqueness and correct continuation.

**2. What is the role of the `DROP TABLE` of the staging table at the end — can you just leave it "just in case"?**

The staging table is only an intermediate buffer with raw CSV data. Keeping it leaves
**duplicate copies** of the imported rows in the database (confusing, wastes space) and
clutters the schema with a table that has no business meaning. Dropping it keeps the
database clean and ensures the only copy of the data is the real `medicines` table.

**3. How is the COUNT(*) before/after (Tasks 1 and 3) better than "it seems the import worked"?**

A numeric before/after count gives an **objective, verifiable** proof of how many rows
were actually transferred and that the figure exactly matches the CSV row count. "It seems
it worked" is subjective and can miss silent problems (e.g. rows skipped, mis-mapped
columns, or an empty import that returned no error). The count also caught the exact +8
deliverable.

## How to run
```bash
# Tasks 1–4 (and the note for Task 5):
sqlite3 medicines.db < script.sql

# Task 5 — on a separate test copy only (here rebuilt from a single base row):
sqlite3 medicines_test.db <<'EOF'
CREATE TABLE medicines (id INTEGER PRIMARY KEY, name TEXT NOT NULL, manufacturer TEXT, form TEXT, price REAL NOT NULL, stock_quantity INTEGER NOT NULL DEFAULT 0);
INSERT INTO medicines (name, manufacturer, form, price, stock_quantity) VALUES ('Paracetamol','Darnytsia','tablets',25.0,120);
.mode csv
.import v4_new_rows.csv medicines
EOF
```

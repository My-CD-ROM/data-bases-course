### Завдання 2. UPDATE у таблиці-вимірі
UPDATE тут доречний тому, що сутність товару залишається тією самою (зберігається її первинний ключ та ідентифікація), а змінюється лише її поточний стан (кількість на складі), тоді як видалення і повторна вставка порушили б зв'язки з іншими таблицями через зовнішні ключі та призвели б до втрати цілісності історичних даних.

### Завдання 4. Перевірка ON DELETE на реальних даних
- **Для product_id (ON DELETE RESTRICT):** Оскільки для цього зовнішнього ключа встановлено правило `RESTRICT`, спроба видалити продукт, який використовується в таблиці `orders`, буде заблокована системою, і SQLite поверне помилку.
- **Фактичний результат для product_id:** Команда видалення повернула `Error: FOREIGN KEY constraint failed`. Прогноз повністю підтвердився.
- **Для customer_id (ON DELETE CASCADE):** Оскільки встановлено правило `CASCADE`, видалення клієнта з `id = 2` автоматично призведе до видалення всіх його замовлень з таблиці `orders`.
- **Фактичний результат для customer_id:** Клієнт успішно видалений, а замовлення з `customer_id = 2` зникли з таблиці `orders` без додаткових запитів. Прогноз повністю підтвердився.

## Контрольні питання
1. **Чим UPDATE ... SET колонка = колонка + 1 відрізняється від UPDATE ... SET колонка = <конкретне число>?**
   Перший варіант виконує *інкремент* (збільшує поточне значення кожного рядка, що підпадає під умову, на одиницю динамічно, залежно від його попереднього стану), тоді як другий жорстко затирає поточне значення однаковою для всіх відібраних рядків константою.

2. **Чому обмеження NOT NULL/UNIQUE/CHECK завжди перевіряються при UPDATE, тоді як FOREIGN KEY — лише за умови PRAGMA foreign_keys = ON;?**
   Обмеження стовпців (`NOT NULL`, `UNIQUE`, `CHECK`) є внутрішніми правилами цілісності конкретної таблиці й контролюються рушієм постійно. Зовнішні ключі (`FOREIGN KEY`) за замовчуванням у SQLite вимкнені через історичні міркування сумісності, тому для активації перебірки зв'язків між таблицями потрібно явно вмикати прапорець `PRAGMA foreign_keys = ON;`

3. **Якби на вашій фактовій таблиці FK було оголошено з ON DELETE CASCADE замість RESTRICT, як це змінило б наслідки видалення рядка з таблиці-вимір?**
   Замість того, щоб блокувати видалення товару з помилкою (`RESTRICT`), база даних дозволила б видалити товар і автоматично видалила б усі пов'язані з ним замовлення з таблиці `orders` (`CASCADE`), що могло б призвести до ненавмисної втрати важливих даних про продажі.

4. **Чому DELETE без WHERE небезпечніший за помилку типу чи порушення обмеження цілісності?**
   Команда `DELETE` без умов (`WHERE`) повністю очищає всю таблицю, видаляючи абсолютно всі рядки за один раз. Помилки типу чи порушення обмежень зазвичай блокуються або відхиляються самим рушієм БД з генерацією помилки, тоді як операція без `WHERE` виконується успішно й призводить до масової незворотної втрати даних.

## Пояснення до завдань

- **Завдання 1 (`products.price_with_vat`):** стовпець `price * 1.2` (`VIRTUAL`) автоматично обчислює ціну товару з ПДВ 20% у межах одного рядка без дублювання даних і звернень до інших таблиць[cite: 2].
- **Завдання 2 (`orders.is_shipped`):** вираз `shipped_date IS NOT NULL` (`VIRTUAL`) повертає `1`, якщо замовлення відправлено, `0`, якщо умова хибна, і `NULL`, якщо `shipped_date` має значення `NULL` (у тризначній логіці SQL порівняння з `NULL` не дає ні істини, ні хибності)[cite: 2].
- **Завдання 3 (прямий `UPDATE`):** при спробі виконати `UPDATE products SET price_with_vat = ...` SQLite повертає помилку заборони ручного запису у згенерований стовпець: `[вставити точний текст помилки]`[cite: 2].
- **Завдання 4 (автоматичний перерахунок):** до зміни `price` = `[значення]`, `price_with_vat` = `[значення]`; після `UPDATE products SET price = price + 50 WHERE id = 1` значення `price` = `[значення]`, `price_with_vat` = `[значення]`. Похідний стовпець оновився автоматично й синхронно без додаткових запитів[cite: 2].
- **Завдання 5 (`WHERE` за згенерованим стовпцем):** фільтрація `WHERE price_with_vat > 1000` простіша й читабельніша, ніж повторне написання формули `price * 1.2` у запитах, та знижує ризик помилок[cite: 2].

## Контрольні запитання

1. **Чому лише `VIRTUAL`, а не `STORED`?** У SQLite додавання `STORED`-стовпця через `ALTER TABLE ... ADD COLUMN` заборонено правилами для наявних таблиць з певними обмеженнями, тому використовується `VIRTUAL`.
2. **Що буде при `DROP COLUMN` базової колонки?** SQLite заблокує видалення та видасть помилку залежності, бо на цю колонку спирається згенерований стовпець.
3. **Чому заборона прямого запису — це перевага?** Вона гарантує цілісність даних: похідний стовпець завжди відповідає формулі й базовим значенням і не може бути випадково розсинхронізований вручну.

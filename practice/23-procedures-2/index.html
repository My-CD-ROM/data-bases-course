    Практика 23. Транзакції та обробка помилок у процедурах PostgreSQL¶

    Мета заняття: виконати завдання зі створення процедур у PostgreSQL: оформити бізнес-операцію свого варіанта як процедуру з перевірками стану даних, замінити системні помилки зрозумілими повідомленнями через блок EXCEPTION, виконати порційну обробку з COMMIT усередині процедури і на практиці побачити обмеження керування транзакціями. Окремої лекції для цієї теми немає: теорію наведено нижче, вона продовжує практику 22.

    Теорія: транзакції та помилки в процедурах¶

    На практиці 22 процедура була просто іменованою парою змін. Тут розглянемо три питання, без яких процедура не годиться для реальної роботи: коли зміни фіксуються, як перевірити стан даних перед зміною і що робити з помилками.

    Приклади використовують базу прокату туристичного спорядження: gear (спорядження з ціною за добу daily_price і залишком in_stock), customers (клієнти) і rentals (видачі). Щоб повторити їх, створіть окрему базу (наприклад, gear_demo) і виконайте в ній файл gear_rental_demo.sql. Приклади виконуйте по черзі. У більшості виводів нижче рядок CONTEXT (де саме в процедурі сталася помилка) для стислості опущено, у вашому виводі він може бути.

    1. Один виклик CALL = одна транзакція¶

    CREATE PROCEDURE two_steps()
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE gear SET in_stock = in_stock - 1 WHERE id = 1;
    RAISE EXCEPTION 'збій на другому кроці';
END;
$$;

CALL two_steps();
SELECT in_stock FROM gear WHERE id = 1;

    ERROR:  збій на другому кроці
 in_stock
----------
       10

    Перший крок виконався, але після помилки залишок каремата знову 10: скасовано весь виклик. Без жодного COMMIT у тілі процедури (слова BEGIN ... END тут лише межі блоку PL/pgSQL, а не початок транзакції) вона працює за принципом «все або нічого», як транзакція з лекції 12.

    2. COMMIT і ROLLBACK усередині процедури¶

    Іноді «все або нічого» якраз заважає. Наприклад, процедура оновлює тисячі рядків, і помилка на останньому не повинна знищувати вже виконану роботу. Тоді роботу фіксують частинами: на відміну від функції (лекція 17, розділ 5), процедура може виконувати COMMIT і ROLLBACK у своєму тілі. Процедура нижче підвищує ціни на заданий відсоток, рядок за рядком, і фіксує кожен рядок окремо. Правило бізнесу: ціна за добу не може перевищити межу p_max.

    CREATE PROCEDURE reprice_gear(p_percent NUMERIC, p_max NUMERIC)
LANGUAGE plpgsql
AS $$
DECLARE
    r RECORD;
    v_new NUMERIC;
BEGIN
    FOR r IN SELECT id, daily_price FROM gear ORDER BY id LOOP
        v_new := round(r.daily_price * (1 + p_percent / 100), 2);
        IF v_new > p_max THEN
            RAISE EXCEPTION 'Ціна спорядження % перевищила б межу: %', r.id, v_new;
        END IF;
        UPDATE gear SET daily_price = v_new WHERE id = r.id;
        COMMIT;
    END LOOP;
END;
$$;

CALL reprice_gear(10, 200);
SELECT id, name, daily_price FROM gear ORDER BY id;

    ERROR:  Ціна спорядження 3 перевищила б межу: 275.00
 id |       name        | daily_price
----+-------------------+-------------
  1 | Каремат           |       44.00
  2 | Спальник          |      132.00
  3 | Намет двомісний   |      250.00
  4 | Казанок           |       60.00
  5 | Трекінгові палиці |       80.00

    FOR r IN SELECT ... LOOP перебирає рядки запиту по одному (r.id, r.daily_price є полями поточного рядка; докладніше про цикли і тип RECORD – лекція 17, розділ 6. Рядки 1 і 2 встигли зафіксуватися власними COMMIT і лишилися зміненими, помилка скасувала лише незафіксовану роботу після останнього COMMIT. Якби COMMIT у циклі не було, ця сама помилка скасувала б увесь виклик, і всі п’ять цін лишилися б початковими. Після COMMIT чи ROLLBACK усередині процедури PostgreSQL одразу починає нову транзакцію, тож наступні команди процедури працюють уже в ній. ROLLBACK у тілі відкидає все, що змінено після останнього COMMIT. У реальних системах фіксують порціями (наприклад, по 1000 рядків), тут для наочності по одному.

    3. Пастка: CALL усередині явної транзакції¶

    Процедура може завершувати лише ту транзакцію, яку почав сам CALL. Якщо виклик стоїть усередині транзакції, відкритої вручну, COMMIT у тілі процедури не має права її закрити:

    BEGIN;
CALL reprice_gear(10, 1000);

    ERROR:  invalid transaction termination
CONTEXT:  PL/pgSQL function reprice_gear(numeric,numeric) line 12 at COMMIT

    Після помилки транзакцію треба закрити командою ROLLBACK, жодна ціна при цьому не зміниться. Висновок: процедури з COMMIT викликають окремою командою, а не між BEGIN і COMMIT клієнтського коду. У pgAdmin виклик процедури з COMMIT виконуйте окремо: виділіть лише рядок CALL ...; і натисніть F5. Якщо запустити його разом з іншими командами скрипту, PostgreSQL виконає їх в одній неявній транзакції, і буде та сама помилка invalid transaction termination (разом з нею скасується навіть щойно виконаний CREATE PROCEDURE). Процедурі без COMMIT така ситуація не загрожує: усередині чужої транзакції вона просто стає її частиною.

    4. Процедура-обгортка бізнес-операції¶

    Видача спорядження складається з кількох кроків: перевірити запит, перевірити залишок, записати видачу, зменшити залишок. Атомарність сама від логічних помилок не захищає: без перевірки процедура спокійно видасть три намети, коли на складі один, і залишок стане від’ємним. Правила бізнесу процедура перевіряє сама, до будь-яких змін:

    CREATE PROCEDURE rent_gear(p_gear_id INTEGER, p_customer_id INTEGER, p_qty INTEGER)
LANGUAGE plpgsql
AS $$
DECLARE
    v_stock INTEGER;
BEGIN
    IF p_qty IS NULL OR p_qty <= 0 THEN
        RAISE EXCEPTION 'Кількість має бути додатною, отримано %', p_qty;
    END IF;

    SELECT in_stock INTO v_stock FROM gear WHERE id = p_gear_id FOR UPDATE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Спорядження з id % не існує', p_gear_id;
    END IF;

    IF v_stock < p_qty THEN
        RAISE EXCEPTION 'Недостатньо на складі: є %, потрібно %', v_stock, p_qty;
    END IF;

    INSERT INTO rentals (gear_id, customer_id, qty, rent_date)
    VALUES (p_gear_id, p_customer_id, p_qty, CURRENT_DATE);

    UPDATE gear SET in_stock = in_stock - p_qty WHERE id = p_gear_id;

    RAISE NOTICE 'Видано % шт., залишок %', p_qty, v_stock - p_qty;
END;
$$;

CALL rent_gear(3, 1, 2);
CALL rent_gear(3, 2, 2);
CALL rent_gear(99, 2, 1);

    NOTICE:  Видано 2 шт., залишок 1
CALL
ERROR:  Недостатньо на складі: є 1, потрібно 2
ERROR:  Спорядження з id 99 не існує

    Порядок завжди однаковий: спершу перевірки, потім зміни. Некоректний запит зупиняється ще до того, як щось змінилось. RAISE NOTICE не перериває роботу, а лише виводить повідомлення (у pgAdmin воно на вкладці Messages), тому ним зручно звітувати про успіх. Перевірку «чи немає вже такого рядка» (зайняте місце, чинний абонемент) записують через IF EXISTS (підзапит). Умова істинна, якщо вкладений SELECT повернув хоча б один рядок (що саме він вибирає, неважливо, тому пишуть SELECT 1). Наприклад, заборонимо клієнтові брати спорядження вдруге за один день:

        IF EXISTS (SELECT 1 FROM rentals
               WHERE customer_id = p_customer_id AND rent_date = CURRENT_DATE) THEN
        RAISE EXCEPTION 'Клієнт % уже брав спорядження сьогодні', p_customer_id;
    END IF;

    Якщо правило стосується статусу, умову пишуть як IF v_status IS DISTINCT FROM 'вільний' THEN: звичайне <> для статусу NULL дало б невизначений результат, і операція пройшла б без перевірки (лекція 17, розділ 7).

    FOR UPDATE блокує прочитаний рядок gear до кінця транзакції. Без нього два одночасні виклики могли б обидва прочитати «є 1» і обидва видати намет (сценарій двох продавців із лекції 12). З FOR UPDATE другий виклик чекає, доки перший завершиться, і читає вже зменшений залишок.

    Клієнта процедура не перевіряє, і для неіснуючого клієнта PostgreSQL сам зупинить INSERT зовнішнім ключем:

    CALL rent_gear(5, 99, 1);

    ERROR:  insert or update on table "rentals" violates foreign key constraint "rentals_customer_id_fkey"
DETAIL:  Key (customer_id)=(99) is not present in table "customers".

    Дані захищені, але таке повідомлення незрозуміле касиру прокату.

    5. Обробка помилок: блок EXCEPTION¶

    Будь-яку частину тіла можна загорнути у вкладений блок BEGIN ... EXCEPTION ... END; і вказати, що робити з помилкою певного виду. Замінимо в процедурі INSERT таким блоком:

        BEGIN
        INSERT INTO rentals (gear_id, customer_id, qty, rent_date)
        VALUES (p_gear_id, p_customer_id, p_qty, CURRENT_DATE);
    EXCEPTION
        WHEN foreign_key_violation THEN
            RAISE EXCEPTION 'Клієнта з id % не існує', p_customer_id;
    END;

    Після CREATE OR REPLACE PROCEDURE rent_gear з цим блоком (решта тіла без змін) той самий виклик дає:

    ERROR:  Клієнта з id 99 не існує

    Як працює блок. Коли команда всередині блоку завершується помилкою, PostgreSQL скасовує зміни, зроблені в цьому блоці, і шукає в EXCEPTION гілку WHEN з назвою цієї помилки. Поширені назви: foreign_key_violation, unique_violation, check_violation, not_null_violation; OTHERS перехоплює будь-яку помилку. Усередині обробника доступні SQLERRM (текст початкової помилки) і SQLSTATE (її код, наприклад 23503). Якщо гілки для помилки немає, вона йде далі, як без блоку.

    Обробник у прикладі знову викликає RAISE EXCEPTION, тож весь виклик скасовується, як і раніше, змінюється лише текст. Якщо ж обробник помилку «проковтне» (наприклад, лише RAISE NOTICE), процедура продовжить роботу з наступної команди після блоку і завершиться успішно: у нашому прикладі вона зменшила б залишок, хоча видачу не записано. Тому обробник без повторного RAISE EXCEPTION пишуть лише тоді, коли продовження справді допустиме.

    6. Пастка: COMMIT у блоці з EXCEPTION¶

    Блок з EXCEPTION працює як вкладена транзакція (точка збереження), і доки він виконується, завершити основну транзакцію не можна. Якщо поставити COMMIT всередину такого блоку, виклик із правильними даними завершиться помилкою:

    ERROR:  cannot commit while a subtransaction is active

    Тож COMMIT у процедурі розміщують поза блоками з EXCEPTION, як у циклі з розділу 2.

    Варіант¶

    Ваша база у PostgreSQL з практики 19 разом із процедурами з практики 22. Якщо базу втрачено, поверніться до практики 19. Повна структура варіантів наведена в практиці 3.

    Бізнес-операцію для завдань 1–2 і колонку для порційного оновлення в завданні 3 оберіть з таблиці. Назви статусів у вашій базі можуть відрізнятися: використовуйте свої. Можна запропонувати й власну операцію, якщо в ній є щонайменше дві перевірки стану даних.

    8 Доставка їжі Нове замовлення: страва існує, у кур’єра немає незавершеного замовлення; INSERT в orders зі статусом «прийнято» dishes.price + N %, з межею
    9 Університет Виставлення оцінки: оцінка від 0 до 100, дисципліна існує; якщо оцінка студента з цієї дисципліни вже є, UPDATE, інакше INSERT у grades courses.credits + N, з межею
    10 Транспорт Призначення рейсу: маршрут існує, на маршрут понад 300 км лише водій зі стажем від 2 років, у водія немає іншого рейсу в цю дату; INSERT у trips (стаж водія читайте лише для маршрутів понад 300 км, тож на короткому маршруті водій не перевіряється) drivers.experience_years + N, з межею

    Якщо колонка ціни має тип REAL, вираз round(price * 1.1, 2) завершиться помилкою function round(double precision, integer) does not exist: приведіть значення до NUMERIC, наприклад round(price::numeric * 1.1, 2). Якщо дата зберігається як TEXT, для порівняння приведіть її до дати: expiration_date::date >= CURRENT_DATE.

    Завдання¶

    Завдання 1. Процедура бізнес-операції з перевірками. Напишіть процедуру для операції свого варіанта з таблиці. Тіло побудуйте за зразком розділу 4: перевірка вхідних параметрів, читання потрібного рядка (SELECT ... INTO ... FOR UPDATE) з перевіркою NOT FOUND, перевірка правила бізнесу, і лише потім зміни та RAISE NOTICE з підсумком. У базі вже є процедури з практики 22, тож дайте новій процедурі іншу назву або використайте CREATE OR REPLACE (інакше PostgreSQL відповість already exists with same argument types). Виконайте один успішний виклик і щонайменше два виклики, що порушують різні правила. Після кожного невдалого виклику SELECT-ом підтвердьте, що жодна таблиця не змінилась.

    Завдання 2. Зрозуміле повідомлення замість системної помилки. Викличте процедуру із завдання 1 з неіснуючим id у таблиці, яку процедура явно не перевіряє (наприклад, читача, покупця, клієнта, постачальника), і запишіть системну помилку зовнішнього ключа. (Для варіанта 10 візьміть неіснуючого водія на короткому маршруті, бо для довгого його стаж перевіряє сама процедура.) Потім загорніть INSERT у блок BEGIN ... EXCEPTION WHEN foreign_key_violation THEN RAISE EXCEPTION ... (розділ 5), повторіть виклик і запишіть нове повідомлення. Перевірте, що й цього разу нічого не змінилось.

    Завдання 3. Порційна обробка з COMMIT. Напишіть процедуру з двома параметрами (величина зміни і межа), що в циклі FOR ... IN SELECT ... ORDER BY id LOOP змінює колонку свого варіанта з таблиці рядок за рядком, виконує COMMIT після кожного рядка і викликає RAISE EXCEPTION, якщо нове значення перевищує межу. Запишіть SELECT-ом значення до виклику, підберіть межу так, щоб помилка сталася десь посередині таблиці, викличте процедуру (виклик CALL виконуйте окремо, розділ 3) і знову запишіть значення. Письмово поясніть, які рядки змінились, а які ні, і чому.

    Завдання 4. Дві пастки керування транзакціями. (а) Виконайте BEGIN;, потім виклик процедури із завдання 3 з межею, за якої помилки правила не буде, запишіть точний текст помилки (перший рядок ERROR, рядок CONTEXT необов’язковий), закрийте транзакцію ROLLBACK і перевірте, що значення не змінились. (б) Тимчасово додайте COMMIT всередину блоку з EXCEPTION у процедурі із завдання 2 (після INSERT; обробник має перехоплювати лише foreign_key_violation, без WHEN OTHERS), викличте її з коректними даними і запишіть точний текст помилки. Поверніть процедуру до робочого стану й поясніть письмово причину кожної з двох помилок.

    Завдання 5 (додаткове, для тих, хто встиг). Із COMMIT і без нього. Змініть процедуру із завдання 3 через CREATE OR REPLACE, прибравши COMMIT з циклу. Спершу поверніть значення, записані перед завданням 3, командою UPDATE. Запишіть значення, викличте процедуру з тими самими параметрами, що в завданні 3, і порівняйте, які рядки змінились цього разу. Письмово дайте відповідь: у якій ситуації вашого варіанта доречна порційна фіксація, а в якій потрібне «все або нічого», і чи потрібен COMMIT процедурі із завдання 1.

    Що здати й оцінюється¶

    Здайте lab_work_23.sql: усі CREATE PROCEDURE (завдання 1, 2, 3 і додаткового 5), усі виклики CALL з повідомленнями й результатами перевірочних SELECT, точні тексти помилок із завдань 2 і 4; і lab_work_23.md: письмові пояснення до завдань 3 і 4 (і 5, якщо виконували). Контрольні питання:

    • Що станеться з частиною роботи процедури, виконаною до COMMIT, якщо після COMMIT виникне помилка? А без COMMIT у тілі?
    • Чому процедуру з COMMIT не можна викликати між BEGIN і COMMIT у клієнтському коді?
    • Чому перевірки стану (залишок, статус, зайняте місце) ставлять до змін і від чого захищає FOR UPDATE?
    • Чим небезпечний обробник EXCEPTION, що лише виводить RAISE NOTICE і не викликає повторно RAISE EXCEPTION?

    Оцінюється коректність процедури завдання 1 (усі перевірки до змін, перевірені успішний і невдалі виклики), робочий обробник помилки в завданні 2, правильно пояснений результат порційної обробки в завданні 3 (і 5, якщо виконувалось), і точно зафіксовані помилки завдання 4.

    Підсумок заняття¶

    • Оформлено бізнес-операцію свого варіанта як процедуру, що перевіряє стан даних до змін і звітує про результат через RAISE NOTICE.
    • Системну помилку зовнішнього ключа замінено зрозумілим повідомленням через блок EXCEPTION.
    • На практиці підтверджено: COMMIT у процедурі фіксує роботу частинами, а без нього помилка скасовує весь виклик.
    • Зафіксовано два обмеження: COMMIT у процедурі неможливий усередині явної транзакції викликача і всередині блоку з EXCEPTION.

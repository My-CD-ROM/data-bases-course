## Мета роботи

Застосувати `INNER JOIN` та `LEFT JOIN` для об'єднання таблиць бази даних SQLite, отримати результати з реальними назвами та іменами замість ідентифікаторів, а також знайти записи таблиці-виміру, які не мають пов'язаних записів у фактовій таблиці.

## Завдання 1. INNER JOIN факт + вимір 1

Для виконання завдання таблицю `loans` було об'єднано з таблицею `books` за допомогою `INNER JOIN`.

У результаті замість `book_id` відображається реальна назва книги, а також дата її видачі та дата повернення.

Використано `INNER JOIN`, оскільки потрібно отримати тільки ті записи про видачі, для яких існує відповідна книга.

## Завдання 2. INNER JOIN усіх трьох таблиць

У цьому завданні таблицю `loans` було об'єднано з таблицями `books` та `readers`.

Результат містить назву книги, ім'я та прізвище читача і дату видачі. Ідентифікатори `book_id` та `reader_id` у результаті не відображаються.

`INNER JOIN` використано тому, що потрібні тільки ті записи, для яких одночасно існують відповідна книга та відповідний читач.

## Завдання 3. LEFT JOIN — книги без жодної видачі

Для пошуку книг, які ще ніхто не брав, використано `LEFT JOIN`:

```sql
books
LEFT JOIN loans
    ON loans.book_id = books.id
```

Після об'єднання використано умову:

```sql
WHERE loans.id IS NULL;
```

Це дозволяє знайти книги, для яких немає жодного пов'язаного запису у таблиці `loans`.

`LEFT JOIN` використано тому, що він зберігає всі записи з таблиці `books`, навіть якщо для них немає пов'язаного запису в `loans`. При використанні `INNER JOIN` такі книги не потрапили б до результату.

## Завдання 4. Свідома пастка CROSS JOIN

Для перевірки роботи `CROSS JOIN` було виконано запит:

```sql
SELECT COUNT(*)
FROM books, readers;
```

У результаті отримано **48 пар**.

У таблиці `books` міститься **6 книг**, а в таблиці `readers` — **8 читачів**.

Тому кількість можливих пар дорівнює:

**6 × 8 = 48**

`CROSS JOIN` створює декартів добуток: кожна книга поєднується з кожним читачем.

У реальному звіті такий запит майже завжди є помилкою, якщо всі можливі комбінації не потрібні, оскільки він створює багато непотрібних рядків.

## Завдання 5. Обґрунтування вибору JOIN

**Завдання 1:** `INNER JOIN` використано для отримання тільки тих видач, які мають відповідну книгу.

**Завдання 2:** `INNER JOIN` використано для отримання тільки тих видач, для яких одночасно існують книга та читач.

**Завдання 3:** `LEFT JOIN` використано для пошуку книг без жодної видачі, оскільки він зберігає всі записи таблиці `books`.

## Контрольні питання

### 1. Чому рядок з NULL у зовнішньому ключі не з'явиться в INNER JOIN, а в LEFT JOIN з'явиться?

`INNER JOIN` повертає тільки рядки, для яких виконується умова з'єднання. `NULL` не дорівнює жодному значенню, тому відповідної пари не буде. `LEFT JOIN` зберігає всі рядки лівої таблиці, тому такий рядок буде показаний, а поля правої таблиці матимуть значення `NULL`.

### 2. Що станеться з результатом Завдання 2, якщо один JOIN замінити на LEFT JOIN?

У такому випадку записи з лівої таблиці можуть залишитися в результаті навіть тоді, коли для них немає відповідного запису в приєднаній таблиці. Поля правої таблиці в такому випадку матимуть значення `NULL`.

### 3. Чим кома-синтаксис відрізняється від JOIN ... ON?

Запит із комою та умовою у `WHERE` може дати такий самий результат, як `JOIN ... ON`, якщо умова записана правильно. Проте `JOIN ... ON` чіткіше показує умову з'єднання та зменшує ризик випадково отримати `CROSS JOIN` через пропущену умову.

Було отримано інформацію про книги, читачів та їхні видачі без використання ідентифікаторів у результатах. За допомогою `LEFT JOIN` було знайдено книгу, яка не має пов'язаних видач.

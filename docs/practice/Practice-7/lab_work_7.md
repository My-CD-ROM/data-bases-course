### Завдання 1. INNER JOIN факт + вимір 1

**SQL-запит:**

```sql
SELECT
    loans.loan_date AS 'Дата видачі',
    books.title AS 'Назва книги'
FROM loans
INNER JOIN books ON loans.book_id = books.id
WHERE loans.loan_date BETWEEN '2024-02-01' AND '2024-02-28'
ORDER BY loans.loan_date DESC;
```

**Результат:**

| Дата видачі | Назва книги |
|---|---|
| 2024-02-14 | Тіні забутих предків |
| 2024-02-12 | Захар Беркут |
| 2024-02-10 | Місто |
| 2024-02-05 | Intermezzo |
| 2024-02-03 | Тигролови |
| 2024-02-01 | Кобзар |

**Пояснення:**

У цьому запиті таблиця `loans` об'єднується з таблицею `books` за допомогою `INNER JOIN`.

Умова `loans.book_id = books.id` пов'язує кожну позику з відповідною книгою.

За допомогою `WHERE` вибираються тільки позики за лютий 2024 року, а `ORDER BY loans.loan_date DESC` сортує результат від найновішої дати до найстарішої.

Замість ідентифікатора книги `book_id` виводиться її назва `title`.

### Завдання 2. INNER JOIN усіх трьох таблиць

**SQL-запит:**

```sql
SELECT
    books.title AS 'Назва книги',
    readers.last_name AS 'Прізвище читача',
    loans.loan_date AS 'Дата видачі'
FROM loans
INNER JOIN books ON loans.book_id = books.id
INNER JOIN readers ON loans.reader_id = readers.id
WHERE loans.loan_date BETWEEN '2024-02-01' AND '2024-02-28'
ORDER BY loans.loan_date DESC, readers.last_name ASC;
```

**Результат:**

| Назва книги | Прізвище читача | Дата видачі |
|---|---|---|
| Тіні забутих предків | Мельник | 2024-02-14 |
| Захар Беркут | Бондаренко | 2024-02-12 |
| Місто | Іваненко | 2024-02-10 |
| Intermezzo | Коваль | 2024-02-05 |
| Тигролови | Петренко | 2024-02-03 |
| Кобзар | Іваненко | 2024-02-01 |

**Пояснення:**

У цьому запиті об'єднуються три таблиці: `loans`, `books` та `readers`.

Перший `INNER JOIN` приєднує інформацію про книги, а другий — інформацію про читачів.

У результаті один рядок показує назву книги, прізвище читача та дату її видачі.

Умова `WHERE` залишає тільки записи за лютий 2024 року, а `ORDER BY` сортує їх за датою видачі у спадному порядку.

Таким чином, замість технічних ідентифікаторів отримуємо зрозумілу інформацію про те, хто і яку книгу брав.

### Завдання 3. LEFT JOIN — рядки таблиці-виміру без жодної пари

Спочатку було виконано запит для пошуку книг, які ще жодного разу не видавалися.

**SQL-запит:**

```sql
SELECT books.title AS 'Книга, яку ні разу не брали'
FROM books
LEFT JOIN loans ON books.id = loans.book_id
WHERE loans.id IS NULL;
```

У початковій базі результат був порожнім, оскільки всі шість книг уже мають пов'язані записи у таблиці `loans`.

Тому було додано нову книгу, яку ще ніхто не брав:

```sql
INSERT INTO books (id, title, author, genre, publication_year, copies_count)
VALUES (7, 'Кайдашева сім’я', 'Іван Нечуй-Левицький',
        'Соціально-побутова повість', 1879, 2);
```

Після додавання книги запит було виконано повторно.

**Результат:**

| Книга, яку ні разу не брали |
|---|
| Кайдашева сім’я |

**Пояснення:**

`LEFT JOIN` дозволяє отримати всі книги з таблиці `books`, навіть якщо для них немає відповідних записів у таблиці `loans`.

Умова `WHERE loans.id IS NULL` залишає тільки ті книги, для яких не знайдено жодної позики.

У результаті відображається нова книга «Кайдашева сім’я», яку ще ніхто не брав.

### Завдання 4. Свідома пастка CROSS JOIN

**SQL-запити:**

```sql
SELECT COUNT(*) FROM books, readers;

SELECT COUNT(*) FROM books;

SELECT COUNT(*) FROM readers;
```

**Результат після додавання нової книги:**

| Запит | Результат |
|---|---:|
| COUNT(*) FROM books, readers | 42 |
| COUNT(*) FROM books | 7 |
| COUNT(*) FROM readers | 6 |

**Пояснення:**

Коли дві таблиці вказані через кому без умови об'єднання, SQL створює декартів добуток — кожен рядок першої таблиці поєднується з кожним рядком другої.

У нашому випадку є 7 книг і 6 читачів, тому кількість отриманих комбінацій дорівнює:

`7 × 6 = 42`.

Це добуток, а не сума кількості рядків двох таблиць.

У реальних звітах такий запит майже завжди є помилкою, оскільки він поєднує кожну книгу з кожним читачем незалежно від того, чи існує між ними реальний зв'язок. Через це результат може містити багато зайвих комбінацій.

### Завдання 5. Обґрунтування вибору JOIN

**Завдання 1 — INNER JOIN.**

Використано `INNER JOIN`, оскільки потрібно показати тільки ті позики, для яких існує відповідна книга; якби використали `LEFT JOIN`, у результат могли б потрапити також позики без відповідної книги.

**Завдання 2 — INNER JOIN.**

Використано два `INNER JOIN`, оскільки потрібно отримати тільки ті записи, для яких існують і відповідна книга, і читач; якби один із JOIN був замінений на `LEFT JOIN`, могли б залишитися записи без відповідного значення у приєднаній таблиці.

**Завдання 3 — LEFT JOIN.**

Використано `LEFT JOIN`, оскільки потрібно знайти книги, які не мають пов'язаних позик; якби використали `INNER JOIN`, такі книги не потрапили б у результат.

## Контрольні питання

### 1. Чому рядок з NULL у зовнішньому ключі ніколи не з'явиться в результаті INNER JOIN за цим ключем, а в LEFT JOIN — з'явиться?

`INNER JOIN` повертає тільки ті рядки, для яких знайдено відповідність в обох таблицях.

Якщо зовнішній ключ містить `NULL`, він не може збігтися з первинним ключем іншої таблиці, тому такий рядок не потрапить у результат `INNER JOIN`.

`LEFT JOIN` зберігає всі рядки лівої таблиці, навіть якщо відповідного запису в правій таблиці немає. У такому випадку колонки правої таблиці матимуть значення `NULL`.

### 2. Що станеться з результатом Завдання 2, якщо один JOIN замінити на LEFT JOIN, а решту лишити INNER JOIN?

Це залежить від того, який саме `JOIN` замінити.

Якщо замінити `INNER JOIN readers` на `LEFT JOIN readers`, то в результаті залишаться всі позики з відповідними книгами, навіть якщо для деяких позик не вказаний читач (`reader_id IS NULL`).

Якщо ж замінити `INNER JOIN books` на `LEFT JOIN books`, то збережуться позики навіть без відповідної книги, але наступний `INNER JOIN readers` усе одно вимагатиме наявності читача.

У нашій базі всі записи мають відповідні книги й читачів, тому для поточних даних результат не зміниться.

### 3. Чим JOIN a, b WHERE a.id = b.a_id відрізняється від JOIN a JOIN b ON a.id = b.a_id за результатом і за ризиком помилки?

Якщо в обох запитах використовується однакова умова зв'язку, результат буде однаковим.

Старий запис через кому спочатку створює всі можливі комбінації рядків таблиць, а потім `WHERE` залишає тільки ті, які відповідають умові.

Сучасний запис `JOIN ... ON` одразу вказує умову об'єднання таблиць.

Варіант із `JOIN ... ON` зрозуміліший і безпечніший, оскільки умова зв'язку знаходиться окремо від умов фільтрації `WHERE`. У старому записі можна випадково забути умову зв'язку, через що отримаємо декартів добуток і велику кількість зайвих рядків.

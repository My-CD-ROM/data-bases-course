# Практика 4. Додавання записів, встановлення ключів і зв'язків

*Це ключова практика курсу: тут ваша база вперше стає тим, чим і
задумувалась — не однією таблицею, а зв'язаною структурою. Таблиця-
вимір 1 вашого варіанта вже існує ([Практика 1](01-sqlite-create.md)),
а повна ER-схема з усіма трьома таблицями вже намальована на папері
([Практика 3](03-er-modeling.md)). Сьогодні ця схема стає робочим SQL:
додається таблиця-вимір 2, фактова таблиця з двома зовнішніми ключами,
і в них — реальні, зв'язані між собою рядки.*

## Де знайти свій варіант

Повна таблиця з переліком усіх 10 варіантів і трьох таблиць кожного
(вимір 1, вимір 2, фактова таблиця) — у [Практиці 1](01-sqlite-create.md),
розділ "Варіанти". ER-діаграма саме вашого варіанта, яку слід звірити
з результатом сьогоднішньої практики, — у [Практиці 3](03-er-modeling.md).
Тут ця таблиця не повторюється — відкрийте Практику 1 у другій вкладці
й тримайте її поруч.

## Заготовка вашого варіанта (файл `.sql`)

Якщо файл `.db` з Практики 1 загублено, пошкоджено чи його просто не
було збережено — не потрібно переписувати `CREATE TABLE`/`INSERT`
таблиці-вимір 1 вручну за підказкою з таблиці варіантів. Нижче для
кожного з 10 варіантів є готовий файл `v{N}_prerequisites.sql`: він
відтворює рівно той стан бази, який мала дати Практика 1, — **тільки**
таблиця-вимір 1, заповнена реалістичними прикладами рядків, без
таблиці-вимір 2 і фактової таблиці (їх ви створюєте самі, це і є
завдання цієї практики). Це саме "заготовка без FK", про яку йдеться
нижче в Завданні 2 — почати сьогоднішню роботу з неї, а не з порожньої
бази.

Кожен скрипт ідемпотентний (`DROP TABLE IF EXISTS` перед `CREATE
TABLE`), тож виконати можна і на порожній базі, і повторно на вже
наявній — результат однаковий:

- [v1_prerequisites.sql](sql/04-insert-keys/v1_prerequisites.sql) — Бібліотека
- [v2_prerequisites.sql](sql/04-insert-keys/v2_prerequisites.sql) — Інтернет-магазин одягу
- [v3_prerequisites.sql](sql/04-insert-keys/v3_prerequisites.sql) — Кінотеатр
- [v4_prerequisites.sql](sql/04-insert-keys/v4_prerequisites.sql) — Аптека
- [v5_prerequisites.sql](sql/04-insert-keys/v5_prerequisites.sql) — Автосалон
- [v6_prerequisites.sql](sql/04-insert-keys/v6_prerequisites.sql) — Готель
- [v7_prerequisites.sql](sql/04-insert-keys/v7_prerequisites.sql) — Спортзал (фітнес-клуб)
- [v8_prerequisites.sql](sql/04-insert-keys/v8_prerequisites.sql) — Служба доставки їжі
- [v9_prerequisites.sql](sql/04-insert-keys/v9_prerequisites.sql) — Університет (деканат)
- [v10_prerequisites.sql](sql/04-insert-keys/v10_prerequisites.sql) — Транспортна компанія

Завантажте файл свого варіанта і виконайте його в CLI —
`sqlite3 назва_файлу.db < v3_prerequisites.sql` — або відкрийте його
текст і виконайте через **Execute SQL** у DB Browser for SQLite.

## Приклад: наскрізна демонстрація

Розберіть цей приклад — кав'ярня із напоями, баристами та
замовленнями — перш ніж працювати зі своїм варіантом. Домен навмисно
не повторює жоден із 10 варіантів практики.

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE drinks (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    price REAL NOT NULL
);

CREATE TABLE baristas (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    experience_years INTEGER
);

CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    drink_id INTEGER NOT NULL,
    barista_id INTEGER NOT NULL,
    order_date TEXT NOT NULL,
    quantity INTEGER NOT NULL DEFAULT 1,
    FOREIGN KEY (drink_id) REFERENCES drinks (id),
    FOREIGN KEY (barista_id) REFERENCES baristas (id)
);

INSERT INTO drinks (name, price) VALUES
    ('Лате', 75),
    ('Американо', 55),
    ('Капучино', 70);

INSERT INTO baristas (name, experience_years) VALUES
    ('Олена', 3),
    ('Максим', 1);

INSERT INTO orders (drink_id, barista_id, order_date, quantity) VALUES
    (1, 1, '2026-08-20', 2),
    (2, 2, '2026-08-20', 1),
    (3, 1, '2026-08-21', 3);
```

Три таблиці зібрано: `drinks` і `baristas` — вимірювання (незалежні одна
від одної), `orders` — фактова таблиця з двома `FOREIGN KEY`, яка
зв'язує їх. Зверніть увагу на `PRAGMA foreign_keys = ON;` у самому
початку — без неї наступна демонстрація нічого б не показала.

**А тепер зламаємо це навмисно.** Спробуємо додати замовлення на напій,
якого не існує (`drink_id = 99`):

```sql
INSERT INTO orders (drink_id, barista_id, order_date, quantity)
VALUES (99, 1, '2026-08-22', 1);
```

```text
Error: FOREIGN KEY constraint failed
```

Саме так `PRAGMA foreign_keys = ON;` захищає цілісність даних: рядок
не потрапив у таблицю, і замовлення "нізвідки" не з'явилось. Якби
PRAGMA не була включена на цьому з'єднанні, той самий `INSERT`
виконався б без жодної помилки — і таблиця `orders` містила б
посилання на напій, якого не існує.

## Завдання 1. Увімкнення перевірки і таблиця-вимір 2

1. Відкрийте файл бази свого варіанта (той, що з Практики 1) і виконайте
   `PRAGMA foreign_keys = ON;` як перший рядок сеансу.
2. Створіть таблицю-вимір 2 свого варіанта (назва й колонки — за
   таблицею варіантів у Практиці 1) з коректними типами (`INTEGER`,
   `TEXT`, `REAL` — залежно від змісту колонки) і первинним ключем
   `id INTEGER PRIMARY KEY`.

## Завдання 2. Фактова таблиця з двома FOREIGN KEY

1. Створіть фактову (журнальну) таблицю свого варіанта з `id INTEGER
   PRIMARY KEY` і двома колонками зовнішніх ключів — по одній на кожну
   таблицю-вимір (наприклад, `book_id` і `reader_id` для варіанта
   "Бібліотека").
2. Для кожного `FOREIGN KEY` явно оберіть дію `ON DELETE` (`RESTRICT`,
   `SET NULL` або `CASCADE`) і письмово (кількома реченнями в звіті)
   поясніть свій вибір для кожного з двох зв'язків — чому саме ця дія
   відповідає бізнес-сенсу вашого домену, а не просто "яка простіша в
   написанні".

## Завдання 3. Заповнення пов'язаними даними

1. Вставте щонайменше **5-6 рядків** у таблицю-вимір 2.
2. Вставте щонайменше **8-10 рядків** у фактову таблицю, коректно
   пов'язавши кожен рядок із наявними рядками таблиці-вимір 1 (з
   Практики 1) і щойно заповненої таблиці-вимір 2 — жодне значення
   зовнішнього ключа не повинно бути вигаданим.

## Завдання 4. Навмисна помилка зовнішнього ключа

1. Спробуйте вставити в фактову таблицю рядок із зовнішнім ключом, що
   вказує на значення, якого немає в жодній таблиці-вимірюванні
   (наприклад, `book_id = 9999`).
2. Зафіксуйте письмово (скопіюйте) точне повідомлення про помилку, яке
   видала SQLite. Це — підтвердження, що `PRAGMA foreign_keys = ON;`
   на вашому з'єднанні справді працює, а не просто написана в скрипті.

## Завдання 5. Звірка з ER-діаграмою Практики 3

1. Порівняйте фактично створену структуру (назви таблиць, назви
   колонок, напрямки зовнішніх ключів) з ER-діаграмою вашого варіанта
   з Практики 3.
2. Письмово зафіксуйте: чи реалізовано рівно те, що було
   спроєктовано, чи довелось щось змінити (назву колонки, тип даних,
   напрямок зв'язку) — і чому саме таку зміну ви внесли. Якщо змін не
   було — так і напишіть, це теж валідний результат.

!!! warning "Готового розв'язку цієї практики немає навмисно"
    Файли `v{N}_prerequisites.sql` вище відтворюють лише стан **перед**
    цією практикою — таблицю-вимір 1, без жодного зв'язку. Побудова
    таблиці-вимір 2, фактової таблиці й самих `FOREIGN KEY` — це і є
    завдання Практики 4, тож готовий файл із уже вбудованими зв'язками
    (як "відповідь") тут навмисно не публікується: це знецінило б саме
    те, що перевіряється в Завданнях 1-4. Якщо під час роботи базу
    пошкоджено безповоротно — поверніться до `v{N}_prerequisites.sql`
    свого варіанта і виконайте Завдання 1-4 повторно на ньому.

## Що здати й оцінюється

Здайте SQL-скрипт (або файл `.db`) зі своїм варіантом і короткий звіт
із виконаними Завданнями 1-5, письмовими поясненнями до Завдання 2 й
Завдання 5, та точним текстом помилки з Завдання 4. Контрольні
питання, на які варто вміти відповісти:

- Навіщо потрібна `PRAGMA foreign_keys = ON;`, якщо `FOREIGN KEY` уже
  оголошений у `CREATE TABLE`, і чому цю команду доводиться повторювати
  на кожному новому з'єднанні?
- Яка принципова різниця між `PRIMARY KEY` і `FOREIGN KEY` — що кожен
  із них ідентифікує чи на що посилається?
- Чим `ON DELETE CASCADE` відрізняється від `ON DELETE RESTRICT` за
  наслідками для залежних рядків, і чому для одного й того самого
  зв'язку різні студенти можуть обґрунтовано обрати різну дію?

Оцінюється те, що всі три таблиці варіанта створені з правильними
типами й зв'язками, дані справді пов'язані (жодного вигаданого
зовнішнього ключа), помилка з Завдання 4 зафіксована буквально, а
письмові пояснення до Завдань 2 і 5 змістовні, а не формальні.

## Підсумок заняття

- Таблиця-вимір 2 і фактова таблиця вашого варіанта створені та
  заповнені зв'язаними даними — база більше не одна таблиця, а
  структура з трьох, як і планувалось у Практиці 3.
- `PRAGMA foreign_keys = ON;` перевірена не лише в теорії, а й на
  практиці — через навмисну спробу вставити рядок з неправильним
  зовнішнім ключом і побачене повідомлення про помилку.
- Обрані дії `ON DELETE` для кожного зв'язку — усвідомлене рішення
  про бізнес-логіку домену, зафіксоване письмово, а не випадковий
  вибір "за замовчуванням".

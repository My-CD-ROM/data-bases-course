## Завдання 1. UPDATE у фактовій таблиці

**Опис перевірки:** Виконано оновлення одного конкретного рядка журнальної таблиці `loans` (видачі книг) за первинним ключем (`id = 1`). Стовпець `return_date`, який відповідав за дату фактичного повернення книги та містив `NULL`, успішно заповнено актуальною датою.

**Запит оновлення:**
```sql
UPDATE loans SET return_date = '2026-09-29' WHERE id = 1;
```

**Результат виконання:** Рядок успішно оновлено, значення `NULL` замінено на дату.

## Завдання 2. UPDATE у таблиці-вимірі

**Опис перевірки:** В таблиці-вимірі `books` оновлено змінний показник кількості доступних примірників (`copies_count`) для конкретної книги з ідентифікатором `id = 1`.

**Запит оновлення:**
```sql
UPDATE books SET copies_count = 10 WHERE id = 1;
```

**Обґрунтування доречності UPDATE:** Використання оператора `UPDATE` тут є єдино правильним та доречним, оскільки ми модифікуємо лише один змінний показник (кількість копій). Якби ми замість цього видалили старий рядок і вставили новий, ми б безповоротно втратили унікальний `id` книги та зруйнували всі історичні зв'язки з таблицею `loans` (журналом видач), де цей `id` фігурує як зовнішній ключ.

## Завдання 3. DELETE одного рядка

**Опис перевірки:** Проведено видалення рівно одного рядка з журнальної таблиці `loans` за умовою на первинний ключ (`id = 4`). Документування результату виконано за допомогою підрахунку кількості записів агрегатною функцією `COUNT(*)` до та після операції видалення.

**Запити перевірки та видалення:**
```sql
SELECT COUNT(*) FROM loans; -- До видалення
DELETE FROM loans WHERE id = 4;
SELECT COUNT(*) FROM loans; -- Після видалення
```

**Результат документування:**
- Кількість рядків до видалення: **49**
- Кількість рядків після видалення: **48**
- Висновок: Зник рівно **1** рядок (49 - 48 = 1), що підтверджує абсолютну точність роботи умови за первинним ключем.

## Завдання 4. Перевірка ON DELETE на реальних даних

**Опис перевірки:** Здійснено спробу видалення рядка з таблиці-виміру `books` (`id = 1`), на який посилаються активні записи у журнальній таблиці `loans`.

**Прогноз:** Оскільки для зовнішнього ключа `book_id` у таблиці видач встановлено обмеження `ON DELETE RESTRICT`, СУБД SQLite повинна повністю заблокувати спробу видалення книги з `id = 1`. Це необхідно для захисту цілісності даних, щоб у журналі видач не з'явилися "сирітські" записи, які посилаються на вже неіснуючий об'єкт книги.

**Запит видалення:**
```sql
DELETE FROM books WHERE id = 1;
```

**Точний текст помилки SQLite:**
`[19] [SQLITE_CONSTRAINT_FOREIGNKEY] A foreign key constraint failed (FOREIGN KEY constraint failed)`

**Порівняння з прогнозом:** Фактичний результат повністю збігся з теоретичним прогнозом. Обмеження `RESTRICT` надійно заблокувало транзакцію видалення, не дозволивши порушити логічні зв'язки між таблицями бази даних.

# Практика 19. Створення бази даних у PostgreSQL (PgAdmin)

*Мета заняття: перенести свою вже готову тритабличну схему (з усіма
зв’язками) з SQLite у PostgreSQL – самостійно перекласти `CREATE
TABLE` за відмінностями з лекції 15, а потім перенести наявні дані
через експорт та імпорт CSV.*

## Що знадобиться

Ваш файл `.db` з SQLite (з усіма трьома таблицями й даними, накопиченими
за практики 1–18) і встановлені PostgreSQL та pgAdmin (як їх встановити –
у [додатку до лекції 15](../lectures/15-postgres-intro.md#postgresql-pgadmin)). Структуру вашого
варіанта (назви таблиць і колонок) шукайте в таблиці варіантів з
[практики 1](01-sqlite-create.md).

## Приклад: наскрізна демонстрація (переклад однієї таблиці)

```sql
-- було в SQLite:
CREATE TABLE owners (
    id INTEGER PRIMARY KEY,
    last_name TEXT NOT NULL,
    first_name TEXT NOT NULL,
    phone TEXT,
    email TEXT
);
```

```sql
-- стало в PostgreSQL (Query Tool у pgAdmin):
CREATE TABLE owners (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    last_name TEXT NOT NULL,
    first_name TEXT NOT NULL,
    phone TEXT,
    email TEXT
);
```

Рядки `owners` експортують із DB Browser for SQLite у CSV (меню
**File**, **Export**, **Table(s) as CSV file**, з рядком заголовків) і
імпортують у щойно створену таблицю PostgreSQL (у pgAdmin: правий клік
на таблиці, **Import/Export Data**, режим Import, формат csv, на вкладці
Options – Header). Після імпорту обов’язково виконайте:

```sql
SELECT setval(pg_get_serial_sequence('owners', 'id'), (SELECT MAX(id) FROM owners));
```

Інакше наступний `INSERT` без явного `id` спробує повторити вже
зайняте значення (лекція 15, розділ 8).

## Завдання

**Завдання 1. Створення бази даних.** У pgAdmin створіть нову базу
даних для свого варіанта (правий клік на `Databases`, **Create**,
**Database**). Дайте їй назву, що відображає ваш варіант (наприклад,
`library_db`, `gym_db`), і відкрийте Query Tool саме на цій базі
(лекція 15, розділ 2).

**Завдання 2. Переклад трьох CREATE TABLE.** Самостійно перекладіть
структуру всіх трьох таблиць свого варіанта (таблиця-вимір 1,
таблиця-вимір 2, фактова таблиця) із синтаксису SQLite на PostgreSQL,
застосувавши відмінності з лекції 15: `GENERATED ALWAYS AS IDENTITY`
замість `INTEGER PRIMARY KEY`, коректні типи (`TEXT`, `INTEGER`,
`REAL`, `BOOLEAN`, де доречно) і `FOREIGN KEY` на обох зв’язках
фактової таблиці (`PRAGMA` для цього не потрібна – лекція 15, розділ 5).
Виконайте всі три `CREATE TABLE` у Query Tool.

**Завдання 3. Перенесення даних.** Для кожної з трьох таблиць
експортуйте її поточний вміст із SQLite у CSV і імпортуйте цей CSV у
відповідну таблицю PostgreSQL через **Import/Export Data** у pgAdmin
(так, як у прикладі вище). Колонки в `CREATE TABLE` мають іти в тому
самому порядку, що й у CSV; згенерований стовпець з практики 18
приберіть з файлу або оголосіть у PostgreSQL так само згенерованим
(лекція 15, розділ 8). Дотримуйтеся порядку: спершу обидві
таблиці-виміри, потім фактова таблиця (щоб зовнішні ключі одразу
знаходили свої рядки).

**Завдання 4. Виправлення лічильника id.** Для кожної з трьох таблиць
виконайте `setval(pg_get_serial_sequence(...), MAX(id))` (за зразком
вище) і переконайтеся, вставивши новий рядок без явного `id`, що
лічильник продовжує нумерацію, а не повторює вже зайняте значення.

**Завдання 5. Перевірка цілісності перенесення.** Для кожної з трьох
таблиць виконайте `SELECT COUNT(*)` у PostgreSQL і порівняйте з
`SELECT COUNT(*)` тієї ж таблиці в SQLite (до перенесення), врахувавши
тестовий рядок із завдання 4. Письмово підтвердьте, що числа
збігаються. Потім спробуйте одну свідому помилку – `INSERT` рядка із
зовнішнім ключем, якого немає в таблиці-вимірі, – і запишіть точний
текст помилки PostgreSQL.

## Що здати й оцінюється

Починаючи з цієї практики, база зберігається на сервері PostgreSQL, і
портативного файлу `.db` для здачі вже немає. Тому до кінця курсу
здаються лише два файли: `lab_work_19.sql` – SQL-скрипт із трьома
перекладеними `CREATE TABLE`, командами `setval` і перевірочними
`INSERT` із завдання 4, підтвердженням збігу `COUNT(*)` для кожної з
трьох таблиць і точним текстом помилки із завдання 5; і `lab_work_19.md`
– письмові відповіді на контрольні питання:

- Чим PostgreSQL як клієнт-серверна СУБД відрізняється від SQLite і яка
  в ньому ієрархія об’єктів?
- Чому саме `GENERATED ALWAYS AS IDENTITY`, а не старіший `SERIAL`,
  обрано як основний спосіб автоінкременту в цьому курсі і чим вони
  відрізняються по суті?
- Чому таблиці-виміри потрібно перенести (і створити, і
  заповнити даними) перед фактовою таблицею, а не в довільному
  порядку?
- Що сталося б, якби завдання 4 (виправлення лічильника) пропустити, і
  на якому саме кроці це призвело б до помилки?
- Для чого потрібні pgAdmin і Query Tool і аналогами яких інструментів
  DB Browser for SQLite вони є?
- Чому після перенесення бази в PostgreSQL для перевірки зовнішніх
  ключів більше не потрібна команда `PRAGMA foreign_keys`?

Оцінюється коректність перекладеної структури (типи, автоінкремент,
`FOREIGN KEY`), точний збіг кількості рядків до й після перенесення для
всіх трьох таблиць і правильно виконане виправлення лічильника
(завдання 4).

## Підсумок заняття

- Створено нову базу даних PostgreSQL і перекладено в ній повну
  тритабличну структуру свого варіанта з коректними типами й
  зв’язками.
- Перенесено всі наявні дані через експорт та імпорт CSV з перевіркою
  збігу кількості рядків.
- На практиці підтверджено й виправлено пастку «збитого» лічильника
  автоінкременту після імпорту рядків із явними `id`.

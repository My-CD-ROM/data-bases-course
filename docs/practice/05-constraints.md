# Практика 5. Обмеження цілісності даних: NOT NULL, UNIQUE, CHECK, DEFAULT

*Мета заняття: застосувати до власного варіанта чотири обмеження цілісності
з Лекції 6 — `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT`. Оскільки SQLite не
підтримує `ALTER TABLE ... ADD CONSTRAINT`, єдиний спосіб додати обмеження
до вже існуючого стовпця — перестворити таблицю; сьогодні це виконується
тричі поспіль, на трьох різних обмеженнях, а потім кожне з них навмисно
порушується, щоб побачити повідомлення про помилку на власні очі.*

## Варіант

Той самий варіант і той самий файл `.db`, що в [Практиці 1](01-sqlite-create.md)
і [Практиці 4](04-insert-keys.md) — сьогодні структура таблиць
**змінюється** (додаються обмеження), а не дані. Знадобляться обидві
таблиці-вимір із Практики 4.

Якщо свій файл `.db` після Практики 4 не збережено чи загублено —
поверніться до `v{N}_prerequisites.sql` свого варіанта з
[Практики 4](04-insert-keys.md#sql) і виконайте Завдання 1-4 тієї практики
ще раз.

## Приклад: наскрізна демонстрація

На ветклініці з лекцій — додавання `CHECK` до стовпця, який досі його не
мав, через стандартний рецепт перестворення таблиці:

```sql
ALTER TABLE animals RENAME TO animals_old;

CREATE TABLE animals (
    id        INTEGER PRIMARY KEY,
    name      TEXT NOT NULL,
    species   TEXT NOT NULL,
    age       INTEGER CHECK (age >= 0),   -- нове обмеження
    status    TEXT NOT NULL DEFAULT 'на обліку',
    owner_id  INTEGER NOT NULL,
    FOREIGN KEY (owner_id) REFERENCES owners (id),
    UNIQUE (owner_id, name)
);

INSERT INTO animals SELECT * FROM animals_old;

DROP TABLE animals_old;
```

Перевірка порушення одразу після перестворення:

```sql
UPDATE animals SET age = -1 WHERE name = 'Мурчик';
-- Runtime error: CHECK constraint failed: age >= 0
```

`CHECK`, доданий уже ПІСЛЯ того, як таблиця існувала якийсь час без нього,
діє точно так само безумовно, як і оголошений одразу при `CREATE TABLE` —
саме це й перевіряють Завдання 1-3 нижче на вашому власному варіанті.

## Завдання

**Завдання 1. Додайте `NOT NULL`.** Оберіть у одній з двох таблиць-вимірів
стовпець, який досі не має жодного обмеження (крім `PRIMARY KEY`) і який,
за змістом даних, завжди повинен мати значення (наприклад назва товару,
прізвище клієнта). Перестворіть таблицю за рецептом вище, додавши йому
`NOT NULL`. Перевірте: спробуйте вставити новий рядок, пропустивши саме цю
колонку, і зафіксуйте точний текст помилки.

**Завдання 2. Додайте `UNIQUE`.** Оберіть інший стовпець (чи комбінацію
двох стовпців) тієї самої чи другої таблиці-виміру, значення якого
змістовно не повинні повторюватися (номер документа, комбінація
"назва + категорія" тощо). Перестворіть таблицю, додавши `UNIQUE`.
Перевірте: спробуйте вставити рядок зі значенням, що вже є серед наявних
даних, і зафіксуйте помилку.

**Завдання 3. Додайте `CHECK`.** Оберіть числовий стовпець зі змістовним
діапазоном допустимих значень (вік, ціна, кількість, рейтинг) і додайте
йому умову через `CHECK` (наприклад `CHECK (price > 0)`). Перестворіть
таблицю. Перевірте двома спробами: одна порушує умову (очікується
помилка), інша — ні (виконується без помилок).

**Завдання 4. Додайте `DEFAULT`.** Оберіть стовпець, для якого є
змістовне значення "за замовчуванням" (статус, кількість копій, дата
створення) і додайте йому `DEFAULT` — за потреби разом з `NOT NULL`, як у
прикладі лекції. Перевірте: вставте рядок, не вказуючи цю колонку, і
`SELECT`-ом підтвердіть, що підставилося саме очікуване значення.

**Завдання 5. Перевірка через `UPDATE`, а не `INSERT`.** Оберіть **одне**
з трьох обмежень, доданих у Завданнях 1-3, і навмисно поруште його не
новим `INSERT`, а командою `UPDATE` над уже існуючим рядком. Зафіксуйте
точний текст помилки і письмово (одне речення) підтвердіть, що обмеження
однаково діє і при вставці, і при оновленні.

**Завдання 6. Письмовий висновок.** Для кожного з чотирьох обмежень,
застосованих сьогодні (`NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT`), одним
реченням поясніть, чому саме цей стовпець вашого варіанта потребував
саме цього обмеження — тобто чому обмеження відповідає бізнес-сенсу
даних, а не обрано довільно.

## Що здати й оцінюється

Здайте `lab_work_5.sql` — усі чотири скрипти перестворення таблиці із
Завдань 1-4 і команду `UPDATE` із Завдання 5; `lab_work_5.db` — оновлений
файл бази даних із усіма чотирма новими обмеженнями; і `lab_work_5.md` —
письмові відповіді Завдань 4 (підтверджене значення), 5 (текст помилки) і
6 (обґрунтування для кожного обмеження).

Контрольні питання:

- Чому в SQLite неможливо просто виконати `ALTER TABLE ... ADD CONSTRAINT
  CHECK (...)`, і що доводиться робити замість цього?
- Що станеться, якщо перестворити таблицю, додавши `NOT NULL` до
  стовпця, у якому серед наявних рядків уже є `NULL`?
- Чим перевірка `CHECK`, доданого через перестворення таблиці,
  відрізняється від перевірки `CHECK`, оголошеного одразу при
  `CREATE TABLE`?
- Чому `DEFAULT` не можна перевірити тим самим способом, що й `NOT
  NULL`/`UNIQUE`/`CHECK` (спробою порушення), і як його перевіряють
  замість цього?

Оцінюється коректність усіх чотирьох перестворень таблиці (дані
збережені, нове обмеження справді діє), точність зафіксованих
повідомлень про помилки із Завдань 1-3 і 5, правильність підтвердженого
значення в Завданні 4, а також обґрунтованість письмових відповідей
Завдання 6.

## Підсумок заняття

- До двох уже існуючих таблиць-вимірів варіанта додано всі чотири
  обмеження цілісності з Лекції 6 — `NOT NULL`, `UNIQUE`, `CHECK`,
  `DEFAULT` — єдиним доступним у SQLite способом: перестворенням таблиці.
- Кожне обмеження перевірено навмисним порушенням; окремо підтверджено,
  що ці обмеження діють і при `UPDATE`, не лише при `INSERT`.
- `DEFAULT`, на відміну від решти трьох, перевіряється не спробою
  порушення, а підтвердженням підставленого значення через `SELECT`.

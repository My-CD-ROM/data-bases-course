# Практика 5. Робота з командами оновлення та видалення у SQLite

*Мета заняття: застосувати `UPDATE` і `DELETE` з Лекції 6 до фактової
(журнальної) таблиці свого варіанта, на практиці переконатися, що
обмеження цілісності з Лекції 5 (`NOT NULL`, `UNIQUE`, `CHECK`)
продовжують діяти й після того, як рядок уже записано, а також — додати
одне таке обмеження до вже існуючої таблиці-виміру (SQLite не має
`ALTER TABLE ... ADD CONSTRAINT`, тож єдиний спосіб — перестворити
таблицю) і на реальних даних перевірити, як обрана в Практиці 4 дія
`ON DELETE` насправді впливає на пов'язані рядки.*

## Варіант

Той самий варіант і той самий файл `.db`, що в
[Практиці 1](01-sqlite-create.md) і [Практиці 4](04-insert-keys.md) —
сьогодні структура таблиць **не змінюється**, лише дані в них.
Знадобиться повна тристаблична схема з Практики 4: обидві
таблиці-вимір і фактова (журнальна) таблиця з двома зовнішніми ключами.

Якщо свій файл `.db` після Практики 4 не збережено чи загублено —
готового файлу з уже побудованими зв'язками тут немає навмисно
(побудова зв'язків — це власне завдання Практики 4). Поверніться до
`v{N}_prerequisites.sql` свого варіанта з
[Практики 4](04-insert-keys.md#sql) і виконайте Завдання 1-4 тієї
практики ще раз, щоб отримати повну робочу схему для сьогоднішнього
заняття.

## Приклад: наскрізна демонстрація

На ветклініці з лекцій — `UPDATE` одного рядка, потім `DELETE`, потім
спроба порушити `CHECK` при оновленні:

```sql
-- позначити, що тварині виповнилось на рік більше
UPDATE animals SET age = age + 1 WHERE name = 'Мурчик';

-- видалити один конкретний візит (за id, найнадійніший спосіб — унікальний PK)
DELETE FROM visits WHERE id = 2;

-- спроба оновлення, яка порушує CHECK з Лекції 5
UPDATE animals SET age = -1 WHERE name = 'Рекс';
-- Runtime error: CHECK constraint failed: age >= 0
```

Останній рядок навмисно провальний: обмеження `CHECK (age >= 0)`,
задане ще при `CREATE TABLE`, продовжує діяти й на `UPDATE`, не тільки
на `INSERT` — саме це й перевіряє Завдання 4 нижче на вашому варіанті.

## Завдання

**Завдання 1. UPDATE у фактовій таблиці.** Оновіть **один конкретний**
рядок фактової (журнальної) таблиці свого варіанта, заповнивши
значення стовпця, який досі було `NULL` або мало "тимчасове" значення
— подивіться свій рядок таблиці варіантів із Практики 1: для
"Бібліотеки" це `return_date` у `loans`, для "Готелю" —
фактичний виїзд у `bookings`, для решти варіантів — аналогічний за
змістом стовпець (статус, дата завершення тощо). Використайте `WHERE`
з умовою за первинним ключем (`id = ...`), щоб оновити рівно один
рядок.

**Завдання 2. UPDATE у таблиці-вимірі.** Оновіть один "змінний"
показник в одній з двох таблиць-вимірів (наприклад
`stock_quantity`, `status`, `price`) для одного конкретного рядка.
Письмово (одне речення) поясніть, чому тут доречний саме `UPDATE`, а не
видалення старого рядка й вставка нового.

**Завдання 3. DELETE одного рядка.** Видаліть **рівно один** рядок з
фактової (журнальної) таблиці за умовою на первинний ключ (наприклад,
скасоване замовлення чи бронювання). Виконайте `SELECT COUNT(*)` до і
після видалення, щоб задокументувати, що зникнув саме один рядок, а не
більше.

**Завдання 4. Додайте обмеження цілісності через перестворення таблиці.**
SQLite не вміє `ALTER TABLE ... ADD CONSTRAINT` — додати `NOT NULL`,
`UNIQUE` чи `CHECK` до вже існуючого стовпця можна лише перестворивши
таблицю. Оберіть один стовпець однієї з ваших двох таблиць-вимірів, який
досі не має жодного обмеження (крім `PRIMARY KEY`), і додайте йому
обмеження, яке справді відповідає бізнес-сенсу цього стовпця (наприклад
`CHECK (price > 0)`, `UNIQUE` на стовпці, що має бути унікальним, або
`NOT NULL` на стовпці, що завжди повинен мати значення). Використайте
стандартний рецепт SQLite:

```sql
ALTER TABLE products RENAME TO products_old;

CREATE TABLE products (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    category TEXT,
    size TEXT,
    price REAL CHECK (price > 0),   -- нове обмеження
    stock_quantity INTEGER
);

INSERT INTO products SELECT * FROM products_old;

DROP TABLE products_old;
```

Письмово поясніть, чому саме перестворення таблиці — а не пряме
`ALTER TABLE` — потрібне тут, і чому ви обрали саме це обмеження для
цього стовпця.

**Завдання 5. Перевірка обмеження цілісності при UPDATE.** Навмисно
спробуйте виконати `UPDATE`, який порушує обмеження, щойно додане в
Завданні 4 (а не будь-яке довільне). Запишіть точний текст повідомлення
про помилку, яке видала SQLite, і поясніть, яке саме обмеження
спрацювало.

**Завдання 6. Перевірка ON DELETE на реальних даних.** У Практиці 4 ви
обрали й письмово обґрунтували дію `ON DELETE` для кожного з двох
зовнішніх ключів фактової таблиці. Не забудьте `PRAGMA foreign_keys =
ON;` на початку сесії — інакше SQLite обмеження зовнішніх ключів взагалі
не перевіряє. Оберіть один рядок з однієї таблиці-виміру, на який
посилається хоча б один рядок фактової таблиці, і видаліть його
(`DELETE ... WHERE id = ...`). До видалення письмово запишіть **прогноз**
— що станеться з пов'язаними рядками фактової таблиці, виходячи з
обраної в Практиці 4 дії (`RESTRICT` — видалення буде відхилено;
`SET NULL` — FK-стовпець стане `NULL`; `CASCADE` — пов'язані рядки також
зникнуть). Після видалення (чи спроби видалення) `SELECT`-ом перевірте
фактичний результат і письмово порівняйте його з прогнозом — якщо вони
відрізняються, поясніть чому.

## Що здати й оцінюється

Здайте `lab_work_5.sql` — команди `UPDATE`/`DELETE` із Завдань 1-3,
скрипт перестворення таблиці із Завдання 4, спробу порушення обмеження
із Завдання 5 і команду `DELETE` із Завдання 6; `lab_work_5.db` —
оновлений файл бази даних після всіх завдань; і `lab_work_5.md` —
письмові відповіді Завдань 2, 4, 5 і 6 (прогноз і фактичний результат
для Завдання 6).

Контрольні питання:

- Чим `UPDATE ... SET колонка = колонка + 1` відрізняється від
  `UPDATE ... SET колонка = <конкретне число>`?
- Чому обмеження `NOT NULL`/`UNIQUE`/`CHECK` завжди перевіряються при
  `UPDATE`, тоді як `FOREIGN KEY` — лише за умови
  `PRAGMA foreign_keys = ON;`?
- Якби на вашій фактовій таблиці FK було оголошено з `ON DELETE
  CASCADE` замість `RESTRICT` (Лекція 4), як це змінило б наслідки
  видалення рядка з таблиці-вимір, на яку та фактова таблиця
  посилається?
- Чому `DELETE` без `WHERE` небезпечніший за помилку типу чи
  порушення обмеження цілісності?

Оцінюється правильність виконаних `UPDATE`/`DELETE` (рівно ті рядки, що
вимагались, жодного зайвого), коректність перестворення таблиці в
Завданні 4 (дані збережені, нове обмеження справді діє), точність
зафіксованого повідомлення про помилку в Завданні 5, а також те,
наскільки прогноз у Завданні 6 узгоджується з фактично спостереженою
поведінкою `ON DELETE` — і обґрунтованість усіх письмових відповідей.

## Підсумок заняття

- Фактова (журнальна) таблиця варіанта оновлена (`UPDATE`) і зменшена
  на один рядок (`DELETE`).
- До вже існуючої таблиці-виміру додано нове обмеження цілісності через
  перестворення таблиці — єдиний спосіб зробити це в SQLite — і
  підтверджено практично, що воно, як і решта обмежень з Лекції 5, діє
  і при `UPDATE`, не лише при `INSERT`.
- Дія `ON DELETE`, обрана й обґрунтована в Практиці 4, перевірена на
  реальних даних: прогнозована поведінка порівняна з фактичною після
  видалення рядка з таблиці-виміру.

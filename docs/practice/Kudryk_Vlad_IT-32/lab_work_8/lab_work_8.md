# Звіт до Практичної роботи №8
**Варіант 8. Служба доставки їжі**

Структуру таблиць не змінено — усі запити виконано на вже наявній схемі Практик 4-7 (`restaurants`, `clients`, `orders`).

## Завдання 1. COUNT(*) проти COUNT(колонка)

Як "необов'язкову" (nullable) колонку обрано `orders.client_id` — вона може стати `NULL` через `ON DELETE SET NULL`, якщо клієнта видалено з бази.

```sql
SELECT COUNT(*), COUNT(client_id) FROM orders;
```
Результат **до** змін: `6 | 6` — числа збіглися, бо на момент запиту жодного клієнта ще не було видалено, і `client_id` був заповнений у кожному рядку.

Щоб продемонструвати різницю, навмисно оновлено один рядок:
```sql
UPDATE orders SET client_id = NULL WHERE id = 6;
```
Результат **після** змін: `6 | 5`. `COUNT(*)` рахує всі рядки незалежно від вмісту, а `COUNT(колонка)` пропускає `NULL` — тому друге число стало меншим на один.

## Завдання 2. SUM і AVG на числовій колонці

```sql
SELECT SUM(price), AVG(price) FROM orders;
-- 1068.0 | 178.0
```
`SUM(price) = 1068.0` — це сумарна виручка сервісу доставки від усіх шести зафіксованих замовлень. `AVG(price) = 178.0` — середній чек одного замовлення по всій базі.

## Завдання 3. MIN/MAX на датовій колонці

```sql
SELECT MIN(order_date), MAX(order_date) FROM orders;
-- '2026-09-01' | '2026-09-06'
```
Колонка `order_date` зберігається як `TEXT` у форматі `YYYY-MM-DD`. СУБД порівнює такі рядки **лексикографічно** (посимвольно, як звичайний текст), а не як календарні дати. Завдяки формату `YYYY-MM-DD` (рік-місяць-день, усі частини з однаковою кількістю цифр) лексикографічне порівняння випадково збігається з хронологічним: рядок `'2026-09-01'` "менший" за `'2026-09-06'` так само за буквами, як і за часом. Якби дати зберігались, наприклад, у форматі `DD.MM.YYYY`, результат `MIN`/`MAX` був би неправильним із хронологічної точки зору, хоч технічно й коректним із текстової.

## Завдання 4. Кілька агрегатних функцій в одному запиті

```sql
SELECT COUNT(*), SUM(price), AVG(price), MIN(price), MAX(price)
FROM orders;
-- 6 | 1068.0 | 178.0 | 120.0 | 240.0
```
Один узагальнений звіт по всій фактовій таблиці: 6 замовлень, сумарна виручка 1068.0, середній чек 178.0, найдешевше замовлення 120.0 (борщ), найдорожче — 240.0 (піца пепероні).

## Завдання 5. Агрегат + WHERE на таблиці-вимірі

```sql
SELECT AVG(orders.price)
FROM orders
JOIN restaurants ON orders.restaurant_id = restaurants.id
WHERE restaurants.category = 'Піца';
-- 206.333...
```
Середній чек по всіх замовленнях становив `178.0`, а середній чек лише по замовленнях з піцерій (`Pizza House`) — `206.33`. `WHERE restaurants.category = 'Піца'` прибрав із розрахунку замовлення з інших закладів (борщ, бургер, вареники) ще **до** того, як `AVG` їх побачила — тому середнє порахувалось лише по трьох замовленнях з піци (220.0, 240.0, 159.0), а не по всіх шести, і вийшло вищим за загальний середній чек.

## Контрольні питання

**1. Чому `COUNT(*)` і `COUNT(колонка)` можуть відрізнятись, а `COUNT(*)` і `COUNT(id)` — практично завжди однакові?**
`COUNT(*)` рахує всі рядки незалежно від вмісту. `COUNT(колонка)` рахує лише ті рядки, де значення в цій колонці не `NULL`. Якщо колонка — первинний ключ (`id`), вона за визначенням ніколи не може бути `NULL`, тому `COUNT(id)` завжди дорівнює `COUNT(*)`. Будь-яка інша, "необов'язкова" колонка (як наш `client_id`) може містити `NULL`, і тоді числа розходяться — саме це показало Завдання 1.

**2. Якби в таблиці було 5 рядків, і в одному — `NULL` у числовій колонці, чому дорівнював би знаменник `AVG`: 5 чи 4?**
4. `AVG` обчислюється як `SUM(колонка) / COUNT(колонка)`, а не `/ COUNT(*)`. Рядок з `NULL` просто не бере участі ні в сумі, ні в підрахунку кількості — він повністю ігнорується, тому знаменник зменшується до кількості рядків із реальним значенням.

**3. Що поверне `SUM(колонка)`, якщо всі рядки мають `NULL` у цій колонці — 0, `NULL`, чи помилку?**
`NULL`, а не `0`. Перевірено на базі (запит `SELECT SUM(price) FROM orders WHERE restaurant_id = 9999;` — жодного рядка з таким рестораном не існує, тобто `SUM` не бачить жодного числового значення для підсумовування) — результат саме `NULL`. Це логічно: `SUM` над порожньою множиною значень не має сенсу дорівнювати нулю (нуль — це теж конкретне число, яке означало б "сума дорівнює нулю", а не "даних немає взагалі"). SQLite явно розрізняє "сума дорівнює нулю" і "дані відсутні", повертаючи в другому випадку `NULL`.

# Звіт до Практичної роботи №15
**Варіант 8. Служба доставки їжі**

Структуру таблиць не змінено, додавались лише індекси. Усі плани нижче отримані командою `EXPLAIN QUERY PLAN` у SQLite 3.45.1.

## Завдання 1. План до індексу

```sql
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE client_id = 1;
```
Точний текст плану:
```
SCAN orders
```
`SCAN` означає повний перегляд таблиці: SQLite перевіряє кожен рядок `orders` і для кожного порівнює `client_id` з 1.

## Завдання 2. Індекс на зовнішньому ключі

```sql
CREATE INDEX idx_orders_client ON orders(client_id);
```
Той самий запит тепер має план:
```
SEARCH orders USING INDEX idx_orders_client (client_id=?)
```
Слово `SCAN` змінилось на `SEARCH ... USING INDEX`: SQLite більше не переглядає всю таблицю, а за індексом знаходить лише рядки з `client_id = 1`. Частина `(client_id=?)` показує, що індекс використано для умови рівності саме на цій колонці.

## Завдання 3. Композитний індекс

Запит: `SELECT * FROM orders WHERE client_id = 1 AND status = 'Нове';`

**До композитного індексу** (одноколонковий `idx_orders_client` уже існує):
```
SEARCH orders USING INDEX idx_orders_client (client_id=?)
```
**Після** `CREATE INDEX idx_orders_client_status ON orders(client_id, status);`:
```
SEARCH orders USING INDEX idx_orders_client_status (client_id=? AND status=?)
```
Різниця видна в дужках. Одноколонковий індекс звужує пошук лише за `client_id`, а умову на `status` SQLite потім перевіряє окремо для кожного знайденого рядка. Композитний індекс враховує **обидві** умови одразу (`client_id=? AND status=?`), тому відразу виходить на потрібні рядки без додаткової перевірки.

## Завдання 4. Індекс і ORDER BY

Запит: `SELECT * FROM orders ORDER BY order_date;`

**До індексу:**
```
SCAN orders
USE TEMP B-TREE FOR ORDER BY
```
**Після** `CREATE INDEX idx_orders_date ON orders(order_date);`:
```
SCAN orders USING INDEX idx_orders_date
```
Зник крок `USE TEMP B-TREE FOR ORDER BY`, тобто окреме сортування. Раніше SQLite спершу читала всі рядки, а потім будувала для них тимчасову впорядковану структуру. Індекс уже зберігає значення `order_date` у відсортованому вигляді, тож SQLite просто проходить його по порядку і рядки приходять уже відсортованими.

## Завдання 5. DROP INDEX

```sql
DROP INDEX idx_orders_client;
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE client_id = 1;
```
План:
```
SEARCH orders USING INDEX idx_orders_client_status (client_id=?)
```
До `SCAN` план **не повернувся**: SQLite використала інший наявний індекс, а саме композитний `idx_orders_client_status`, бо він починається з тієї самої колонки `client_id`, і за його першою частиною можна шукати так само, як за одноколонковим.

Перевірка списку індексів:
```sql
SELECT name FROM sqlite_master WHERE type = 'index' AND tbl_name = 'orders';
```
Результат: `idx_orders_client_status`, `idx_orders_date`. Індексу `idx_orders_client` у списку немає, тобто його справді видалено.

## Про масштаб

У моїй таблиці лише 8 замовлень, тому на практиці різниця в швидкості між `SCAN` і `SEARCH` непомітна. Індекси починають давати відчутний виграш на таблицях із тисячами й мільйонами рядків, а тут їхній ефект видно саме в тексті плану.

## Контрольні питання

**1. Чому EXPLAIN QUERY PLAN показує план, а не результат, і навіщо перевіряти план окремо?**
Команда не виконує запит, а лише показує, **як SQLite збирається його виконувати** (який індекс, чи буде повний перегляд, чи потрібне сортування). Запит може «просто працювати» й повертати правильні дані, але робити це повільно, через повний `SCAN`. Правильність результату й ефективність виконання це різні речі, тож без перегляду плану повільний запит залишиться непоміченим. Це видно і в нашій роботі: запит `WHERE client_id = 1` повертає однакові рядки (замовлення 1, 5, 7) і з індексом, і без, змінюється лише план.

**2. Чому індекс лише на першій колонці дає менший ефект, ніж композитний на обох?**
Індекс на `client_id` звужує пошук тільки за цією колонкою. Усі рядки цього клієнта SQLite мусить прочитати й для кожного окремо перевірити `status`. Композитний індекс `(client_id, status)` зберігає пари значень разом, тому за ним одразу знаходяться рядки, що задовольняють обидві умови. Чим більше рядків має один клієнт, тим більше зайвої роботи вдалось би уникнути. У плані це видно як `(client_id=?)` проти `(client_id=? AND status=?)`.

**3. Яка ціна створення індексу і чому не індексувати кожну колонку «про всяк випадок»?**
Індекс займає додаткове місце на диску (це окрема структура даних) і сповільнює зміни даних: кожен `INSERT`, `UPDATE` і `DELETE` змушує SQLite оновлювати не лише таблицю, а й усі індекси, що її стосуються. Тому індекс виправданий для колонок, за якими часто фільтрують, з'єднують таблиці або сортують. Індексування всього підряд збільшує розмір бази й гальмує запис, а виграшу для запитів, які ці індекси не використовують, не дає.

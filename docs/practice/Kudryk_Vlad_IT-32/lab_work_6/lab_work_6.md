# Звіт до Практичної роботи №6
**Варіант 8. Служба доставки їжі**

Структуру таблиць у цій практиці не змінено — усі дії виконано на вже наявній схемі Практики 5 (`restaurants`, `clients` з `UNIQUE(phone)`, `orders` з `CHECK(price > 0)` і `DEFAULT` для `status`).

## Завдання 1. UPDATE у фактовій таблиці

Оновлено статус замовлення `id = 1` з початкового `'Нове'` на `'Доставлено'`:
```sql
UPDATE orders SET status = 'Доставлено' WHERE id = 1;
```
Перевірка `SELECT` підтвердила, що змінився рівно один рядок — усі інші замовлення лишились зі статусом `'Нове'`.

## Завдання 2. UPDATE у таблиці-вимірі

Оновлено номер телефону клієнта `id = 3` (Андрій Шевченко) на `+380671234567`:
```sql
UPDATE clients SET phone = '+380671234567' WHERE id = 3;
```

**Обґрунтування.** `UPDATE` тут доречний, бо змінився лише телефон того самого клієнта: його `id` і зв'язок із замовленнями мають залишитися незмінними. Видалення старого рядка й вставка нового створили б нового клієнта з іншим `id`, а через `ON DELETE SET NULL` усі замовлення, що посилались на старий рядок, втратили б зв'язок із клієнтом (`client_id` став би `NULL`) ще до того, як з'явився б новий рядок.

## Завдання 3. DELETE одного рядка

Видалено скасоване замовлення `id = 7` ('Піца Гавайська') з фактової таблиці:
```sql
SELECT COUNT(*) FROM orders;   -- 7
DELETE FROM orders WHERE id = 7;
SELECT COUNT(*) FROM orders;   -- 6
```
Кількість рядків зменшилась рівно на один (з 7 до 6), інші замовлення не зачеплено.

## Завдання 4. Перевірка обмежень цілісності при UPDATE

Навмисно порушено обмеження `UNIQUE(phone)` з Практики 5 через `UPDATE`, а не `INSERT`: клієнту `id = 1` спробували встановити номер телефону, який уже належить клієнту `id = 2`:
```sql
UPDATE clients SET phone = '+380672223344' WHERE id = 1;
```
Точний текст помилки:
```
Error: UNIQUE constraint failed: clients.phone
```
Спрацювало саме обмеження `UNIQUE` на стовпці `clients.phone`: SQLite не дозволив, щоб два різних рядки таблиці мали однакове значення в цьому стовпці, навіть коли зміна відбувається через оновлення наявного рядка, а не вставку нового. Контрольний `SELECT` після цієї спроби підтвердив, що телефон клієнта `id = 1` не змінився і лишився попереднім (`+380501112233`) — обмеження відкотило некоректну зміну.

## Завдання 5. DELETE/UPDATE без WHERE — аналіз без виконання

Команди нижче **не виконувались** на базі, це лише письмовий аналіз.

**Якби з команди Завдання 3 прибрати `WHERE`:**
```sql
DELETE FROM orders;
```
На момент виконання Завдання 3 в таблиці `orders` було **7 рядків** (`SELECT COUNT(*)` до видалення). Без умови `WHERE` ця команда видалила б **усі 7 рядків** фактової таблиці — усю історію замовлень варіанта, а не одне скасоване замовлення.

**Якби з команди Завдання 1 прибрати `WHERE`:**
```sql
UPDATE orders SET status = 'Доставлено';
```
На той момент у таблиці `orders` було **7 рядків**. Без умови `WHERE` ця команда встановила б статус `'Доставлено'` у **всіх 7 рядках** одразу — включно з тими замовленнями, які насправді ще не доставлені, що спотворило б реальний стан системи.

В обох випадках відсутність `WHERE` перетворює точкову зміну одного рядка на масову операцію над усією таблицею — і на відміну від помилки типу чи порушення обмеження цілісності (яку СУБД відхиляє й повідомляє одразу), такі команди **виконуються без жодної помилки**, тому їхній наслідок непомітний одразу і його неможливо скасувати автоматично.

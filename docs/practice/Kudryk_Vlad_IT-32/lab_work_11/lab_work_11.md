# Звіт до Практичної роботи №11
**Варіант 8. Служба доставки їжі**

## Питання дослідження

**Який кур'єр найчастіше запізнюється і кому з кур'єрів варто винести попередження?**

## Завдання 1. Проєктування нових таблиць

У базі після Практики 4 була модель `restaurants` + `clients` + `orders`, а потреба варіанта (скарги на кур'єрів) вимагає таблиці, пов'язаної з `couriers`. Тому створено дві таблиці: `couriers` (з плану Практики 3) і залежну від неї `complaints`.

**`couriers`**: `id` (PK), `full_name` (`NOT NULL` — кур'єр без імені не ідентифікується), `phone` (`UNIQUE` — телефон є контактом конкретної людини), `transport`.

**`complaints`**: `id` (PK), `courier_id` (FK на `couriers`), `complaint_type`, `complaint_date`, `description`, `status`.

Обґрунтування рішень:
- **`courier_id INTEGER NOT NULL` + `ON DELETE RESTRICT`.** Скарга без кур'єра не має сенсу, тому `NOT NULL`. `RESTRICT` забороняє видалити кур'єра, на якого є скарги: історія порушень не повинна зникати разом із записом про людину. Перевірено: `DELETE FROM couriers WHERE id = 1` дає `FOREIGN KEY constraint failed`.
- **`complaint_type` з `CHECK (... IN ('Запізнення', 'Пошкоджене замовлення', 'Грубість'))`.** Це колонка для фільтра `WHERE` у Завданні 4. Обмежений список типів гарантує, що вільний текст («запізнився», «Запізнення », «запізнення») не розіб'є одну категорію на кілька і підрахунок буде правильним. Перевірено: тип `'Інше'` відхиляється помилкою `CHECK constraint failed`.
- **`complaint_date NOT NULL`.** Скаргу без дати неможливо ні впорядкувати, ні відфільтрувати за періодом.
- **`status NOT NULL DEFAULT 'Нова'`.** Кожна скарга при реєстрації починає зі статусу «Нова», а оператор змінює його лише коли її розглянуто.
- **`description`** — довільний текст опису (необов'язковий).

Дані: 5 кур'єрів і 10 скарг, розподілених на групи різного розміру (4, 3, 2, 1 скарг). Кур'єр `Сергій Руденко` не має жодної скарги навмисно, для експерименту 5б.

## Завдання 5. Експерименти й висновок

### (а) Пастка групування

Додано кур'єра-двійника `Тарас Лисенко` (id 6, інший телефон) з двома скаргами. Запит із Завдання 3 (`HAVING COUNT(*) >= 3`) виконано двічі.

**Групування за `couriers.id`:** `Богдан Мельник — 4`, `Олена Кравець — 3`. Обидва Тараси лишаються окремими групами з 2 скаргами кожна і поріг не проходять.

**Групування за `couriers.full_name`:** `Богдан Мельник — 4`, `Олена Кравець — 3`, **`Тарас Лисенко — 4`**. Групування за іменем злило двох різних людей в одну групу (2 + 2 = 4), і в результаті з'явився кур'єр, якого за реальними даними в списку бути не повинно. `id` ідентифікує конкретну людину, а ім'я може збігатися, тому групувати треба за первинним ключем.

### (б) LEFT JOIN

У запиті Завдання 4 `JOIN` замінено на `LEFT JOIN`. Результат **не змінився**: `Богдан Мельник — 3`.

Причина: `LEFT JOIN` зберігає кур'єра без скарг (`Сергій Руденко`), але з порожніми (`NULL`) колонками `complaints`. Потім `WHERE complaints.complaint_type = 'Запізнення'` для такого рядка дає не істину, а невідоме (`NULL = 'Запізнення'`), тож рядок відсіюється. Умова у `WHERE` на колонці правої таблиці фактично перетворює `LEFT JOIN` на `INNER JOIN`. Навіть якби рядок пройшов `WHERE`, `HAVING COUNT(*) >= 3` його б відсіяв, бо у нього 0 або 1 запис. Щоб кур'єр без скарг лишився в результаті, умову на тип скарги треба переносити з `WHERE` в `ON`, а в `HAVING` ставити поріг, який пропускає малі значення.

### (в) Відповідь на питання дослідження

Найчастіше запізнюється **Богдан Мельник**: 3 скарги на запізнення (липень, серпень, вересень) із 4 загалом. Йому в першу чергу варто винести попередження. **Олена Кравець** має 3 скарги загалом, але на запізнення лише 2, решту складає скарга на грубість, тож для неї потрібна окрема розмова про поведінку, а не про пунктуальність. Тарас Лисенко (перший) і Ніна Гончар поріг не проходять.

## Контрольне питання

**Якби автор мав дві книги, кожна з яких продавалася тричі, скільки рядків для нього дасть JOIN до GROUP BY, і чому COUNT(*) покаже не те число книг?**

JOIN з'єднує кожну книгу з кожним її продажем, тому для автора вийде 2 × 3 = **6 рядків**. `GROUP BY authors.id` згортає їх в одну групу, і `COUNT(*)` рахує рядки після з'єднання (тобто продажі), отримуючи 6, а не 2. Щоб порахувати саме книги, потрібно `COUNT(DISTINCT books.id)`. У нашій базі та сама логіка: `COUNT(*)` у запитах рахує скарги (рядки `complaints`), а не кур'єрів.

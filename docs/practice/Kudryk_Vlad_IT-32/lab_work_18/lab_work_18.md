# Звіт до Практичної роботи №18
**Варіант 8. Служба доставки їжі**

До таблиці `orders` додано два згенеровані VIRTUAL-стовпці. Жодну таблицю не видалено. Команди виконано в консолі `sqlite3` 3.45.1.

## Завдання 1. Похідне числове значення

```sql
ALTER TABLE orders ADD COLUMN price_with_service REAL
    GENERATED ALWAYS AS (ROUND(price * 1.1, 2)) VIRTUAL;
SELECT id, dish_name, price, price_with_service FROM orders;
```
Результат (фрагмент): `Борщ український 120.0 → 132.0`, `Бургер класичний 189.0 → 207.9`, `Піца Пепероні 240.0 → 264.0`.

**Бізнес-сенс.** `price_with_service` це сума до сплати клієнтом: ціна страви плюс сервісний збір 10%. Формула бере лише колонку `price` того самого рядка (значення з інших таблиць у згенерованому стовпці брати не можна), а `ROUND(..., 2)` залишає два знаки після крапки, як у грошових сумах. Так збір не доводиться рахувати вручну в кожному звіті, і всі бачать одну й ту саму суму.

## Завдання 2. Похідний логічний прапорець

```sql
ALTER TABLE orders ADD COLUMN is_delivered INTEGER
    GENERATED ALWAYS AS (status = 'Доставлено') VIRTUAL;
SELECT id, status, is_delivered FROM orders;
```
Результат: `is_delivered = 1` для замовлень 1 і 5 (статус `Доставлено`) і `0` для решти шести (статус `Нове`). Значення збігається з реальним станом кожного рядка.

Про `NULL`: порівняння з `NULL` дає `NULL`, а не 0 (перевірено: `typeof(NULL = 'Доставлено')` повертає `null`). У моїй таблиці колонка `status` має `NOT NULL`, тому на реальних даних `NULL` у прапорці не з'явиться, але для колонки без цього обмеження такий рядок дав би в прапорці `NULL`.

## Завдання 3. Свідома помилка прямого запису

```sql
UPDATE orders SET price_with_service = 1 WHERE id = 1;
```
Точний текст помилки SQLite:
```
cannot UPDATE generated column "price_with_service"
```
Так само для другого стовпця: `cannot UPDATE generated column "is_delivered"`. Спроба напряму вставити значення також відхиляється: `cannot INSERT into generated column "price_with_service"`. Жодного рядка при цьому не змінилось і не додалося (в таблиці лишилось 8 замовлень).

## Завдання 4. Автоматичний перерахунок

```sql
SELECT id, price, price_with_service FROM orders WHERE id = 1;   -- 120.0 | 132.0
UPDATE orders SET price = 150.00 WHERE id = 1;
SELECT id, price, price_with_service FROM orders WHERE id = 1;   -- 150.0 | 165.0
```
Після зміни базової колонки `price` значення згенерованого стовпця змінилось **автоматично**: з 132.0 на 165.0 (150 × 1.1), без жодної додаткової команди. Обчислення відбувається в момент читання, тому розбіжності між `price` і `price_with_service` бути не може. Щоб дані лишились такими, як у попередніх практиках, ціну повернено до 120.0, і `price_with_service` знову 132.0.

## Завдання 5. WHERE за згенерованим стовпцем

```sql
SELECT id, dish_name, price_with_service FROM orders WHERE price_with_service > 200;
```
Результат: замовлення 2, 3, 5 і 7 (суми 242.0, 207.9, 264.0, 218.9). Запит із формулою прямо в умові (`WHERE ROUND(price * 1.1, 2) > 200`) дає той самий результат.

**Чому запис зручніший.** Формула визначена в одному місці (у схемі таблиці), а в запитах умова читається як бізнес-поняття («сума до сплати понад 200»), а не як арифметика. Якщо збір зміниться з 10% на 12%, достатньо поправити одну формулу, і всі запити автоматично працюватимуть із новою сумою. Якщо ж повторювати `ROUND(price * 1.1, 2)` у кожному запиті, легко десь забути оновити коефіцієнт чи заокруглення, і різні звіти покажуть різні суми.

## Контрольні питання

**1. Чому можна створити лише VIRTUAL, а не STORED, і що цьому заважає?**
Таблиця `orders` уже існує й містить дані, а SQLite дозволяє додати згенеровану колонку до наявної таблиці лише через `ALTER TABLE ... ADD COLUMN`, і лише типу VIRTUAL. Перевірено на тимчасовій копії: спроба додати `STORED` дає помилку `cannot add a STORED column`. Щоб отримати `STORED`, довелося б перестворити таблицю заново (`CREATE TABLE` з такою колонкою й перенесення даних, як у Практиці 5).

**2. Що станеться при `DROP COLUMN` базової колонки, від якої залежить згенерований стовпець?**
SQLite відмовить. Перевірено на тимчасовій копії: `ALTER TABLE tmp_orders DROP COLUMN price` дає помилку `error in table tmp_orders after drop column: no such column: price`, бо формула згенерованого стовпця після видалення посилалася б на колонку, якої немає. Спершу треба видалити сам згенерований стовпець.

**3. Чому неможливість прямого INSERT/UPDATE у згенеровану колонку є перевагою?**
Це гарантує, що похідне значення завжди відповідає формулі: ніхто (людина чи помилковий запит) не може записати туди довільне число, яке розійдеться з базовою колонкою. Не потрібно пам'ятати, що поруч зі зміною ціни треба вручну перерахувати суму, бо цим займається сама СУБД. Тому дані лишаються узгодженими.

# Звіт до Практичної роботи №12
**Варіант 8. Служба доставки їжі**

Структуру таблиць не змінено, виконано лише запити до наявних таблиць.

## Завдання 1. ORDER BY за однією колонкою

```sql
SELECT id, dish_name, price FROM orders ORDER BY price DESC;
```
Першим опинився рядок `5 | Піца Пепероні | 240.0`. Сортування за спаданням (`DESC`) ставить найбільше значення першим, а найвища ціна серед усіх шести замовлень саме 240.0. Останнім стоїть борщ із ціною 120.0.

## Завдання 2. ORDER BY за кількома колонками

```sql
SELECT id, status, order_date, dish_name FROM orders ORDER BY status ASC, order_date DESC;
```
Спершу рядки впорядковуються за `status` за алфавітом: `Доставлено` йде перед `Нове`. Друга колонка (`order_date DESC`) працює лише **в межах однакового значення першої**: п'ять замовлень зі статусом `Нове` додатково розташовано від найновішого (06.09) до найстарішого (01.09). Якщо значення першої колонки різні, друга на порядок не впливає (замовлення зі статусом `Доставлено` одне, тому для нього друге сортування нічого не змінює).

## Завдання 3. Топ-N через ORDER BY + LIMIT

```sql
SELECT id, dish_name, price FROM orders ORDER BY price DESC LIMIT 3;
```
Результат: `Піца Пепероні — 240.0`, `Піца Маргарита — 220.0`, `Бургер класичний — 189.0`.

`ORDER BY` має стояти перед `LIMIT`, бо `LIMIT` просто обрізає вже готовий результат після сортування, беручи перші N рядків. Спочатку рядки впорядковуються за ціною від більшої до меншої, і лише потім береться три перші, тому це справді три найдорожчі. Без `ORDER BY` `LIMIT 3` повернув би три довільних рядки, зазвичай перші за порядком збереження в таблиці (замовлення 1, 2, 3 з цінами 120, 220, 189), і серед них був би найдешевший борщ, а найдорожча піца пепероні випала б.

## Завдання 4. DISTINCT і BETWEEN/IN

**(а) DISTINCT.**
```sql
SELECT DISTINCT transport FROM couriers;
```
Отримано **4 унікальні значення** (`Велосипед`, `Скутер`, `Авто`, `Пішки`) із 6 рядків таблиці `couriers`: `Скутер` повторюється у двох кур'єрів, `Велосипед` також у двох. `DISTINCT` залишає кожне значення один раз.

**(б) BETWEEN і IN.**
```sql
SELECT ... FROM orders WHERE price BETWEEN 150 AND 220;       -- замовлення 2, 3, 6
SELECT ... FROM orders WHERE restaurant_id IN (1, 3);         -- замовлення 1, 3, 4
```
- Для **ціни** обрано `BETWEEN`, бо це неперервний діапазон: «від 150 до 220». `BETWEEN` включає обидві межі (замовлення з ціною рівно 220 потрапило в результат). Список через `IN` довелося б складати з усіх можливих цін, що неможливо для дробових чисел.
- Для **ресторанів** доречний `IN`, бо потрібні конкретні значення, які не утворюють діапазону (1 і 3, без 2). `BETWEEN 1 AND 3` захопив би й ресторан 2.

## Завдання 5. LIKE і пастка з кирилицею

```sql
SELECT full_name FROM clients WHERE full_name LIKE 'Ірина%';   -- 1 рядок: Ірина Коваль
SELECT full_name FROM clients WHERE full_name LIKE 'ірина%';   -- 0 рядків
SELECT name FROM restaurants WHERE name LIKE 'pizza%';         -- 1 рядок: Pizza House
```
Кількість знайдених рядків **не збіглася**: шаблон `'Ірина%'` знайшов клієнтку, а `'ірина%'` (мала літера) не знайшов нікого. Причина в тому, що `LIKE` у SQLite без регістру порівнює тільки латинські (ASCII) літери, а для кирилиці велика `І` і мала `і` вважаються різними символами. Для порівняння, шаблон `'pizza%'` з малої літери знайшов `Pizza House`, бо це латиниця.

Також перевірено: підкреслення `_` замінює рівно один символ, і кириличний теж (`'Ір_на%'` знайшло `Ірина Коваль`). Функція `LOWER()` кирилицю не змінює: `LOWER('Ірина Коваль')` повертає той самий рядок, тому спроба «привести все до нижнього регістру» не допоможе.

## Контрольні питання

**1. Чому ORDER BY обов'язково перед LIMIT, і що буде, якщо ORDER BY прибрати?**
`LIMIT` лише відрізає перші N рядків уже сформованого результату, а впорядковує їх `ORDER BY`. Якщо прибрати `ORDER BY`, залишивши `LIMIT 3`, результат буде просто трьома першими рядками в тому порядку, в якому їх віддала таблиця, а не «топ-3». Порядок без `ORDER BY` стандартом SQL не гарантується. Писати `LIMIT` перед `ORDER BY` синтаксично неможливо.

**2. Коли IN, а коли BETWEEN?**
`BETWEEN` для неперервного діапазону значень (ціна, дата, вік) з межами включно. `IN` для переліку окремих значень, які не утворюють діапазону (конкретні ресторани, статуси, види). Обидва можна замінити ланцюжком `OR`/`AND`, але запис стає довшим і легше помилитись у логіці: наприклад, у довгому ланцюжку `OR` легко пропустити дужки.

**3. Чому висновок про регістр і кирилицю важливий для цього курсу?**
Майже всі текстові дані тут українські (прізвища, назви страв, ресторани). Тому пошук через `LIKE` залежить від регістру літери: запит `LIKE 'петренко%'` нічого не знайде серед `Петренко`, і без помилки або попередження можна отримати порожній результат і зробити хибний висновок, що такого запису немає. Обхідні шляхи: писати шаблон з тим самим регістром, що й у даних, або перелічити обидва варіанти через `OR` (`LIKE 'Ірина%' OR LIKE 'ірина%'`).

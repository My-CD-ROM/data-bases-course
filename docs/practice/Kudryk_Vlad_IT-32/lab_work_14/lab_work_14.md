# Звіт до Практичної роботи №14
**Варіант 8. Служба доставки їжі**

Структуру таблиць не змінено, виконано лише транзакції над наявними даними.

## Завдання 1. Атомарна пара INSERT + UPDATE

```sql
BEGIN;
INSERT INTO orders (restaurant_id, client_id, dish_name, price, order_date)
VALUES (3, 1, 'Бургер з беконом', 199.00, '2026-09-08');
UPDATE orders SET status = 'Доставлено' WHERE id = 5;
COMMIT;
```
У моїй схемі немає лічильника чи статусу в таблицях-вимірах, тому другою зміною обрано статус попереднього замовлення того самого клієнта (id 5, піца пепероні): клієнт, оформлюючи нове замовлення, підтверджує, що попереднє отримав, і воно стає `Доставлено`.

**Чому разом.** Обидві зміни описують одну подію («клієнт підтвердив отримання і замовив знову»). Якби вони виконувались двома незалежними запитами і між ними стався збій, база опинилась би в суперечливому стані: або нове замовлення створене, а попереднє досі «Нове» (хоч клієнт його отримав і тепер воно виглядає як необроблене), або попереднє закрите, а нового замовлення нема (клієнт нічого не замовив, а історія вже змінена). Транзакція гарантує, що застосуються обидві зміни або жодна.

## Завдання 2. Свідомий ROLLBACK

Відкрито транзакцію, у ній вставлено замовлення на суші й змінено статус замовлення 2, після чого виконано `ROLLBACK`. Перевірено три речі:
- `SELECT COUNT(*) FROM orders` дав **7**, тобто стільки ж, скільки до `BEGIN` (шість початкових і одне з Завдання 1);
- `SELECT COUNT(*) ... WHERE dish_name = 'Суші Філадельфія'` дав **0**: вставлений рядок скасовано;
- статус замовлення 2 лишився **`Нове`**: зміну `UPDATE` теж скасовано.

Отже, `ROLLBACK` скасував обидві зміни, і дані такі самі, як до `BEGIN`.

## Завдання 3. Проміжний стан усередині транзакції

```sql
BEGIN;
UPDATE orders SET status = 'Скасовано' WHERE id = 4;
SELECT id, status FROM orders WHERE id = 4;   -- 4 | Скасовано
ROLLBACK;
```
Так, **власну зміну видно до `COMMIT`**: запит усередині транзакції повернув `Скасовано`. Це не суперечить тому, що зміна ще не остаточна, бо транзакція показує своїй сесії актуальний стан із її власними змінами, а остаточною (видимою для інших і незворотною) зміна стає лише після `COMMIT`. Додатково перевірено на окремому тестовому з'єднанні: поки перша сесія тримала транзакцію відкритою, друге з'єднання читало ще **старе** значення (`Нове`). Після `ROLLBACK` у першій сесії статус знову `Нове`.

## Завдання 4. Помилка всередині транзакції

```sql
BEGIN;
INSERT INTO orders (restaurant_id, client_id, dish_name, price, order_date)
VALUES (1, 4, 'Вареники', 140.00, '2026-09-10');                 -- успішно
INSERT INTO clients (full_name, phone) VALUES ('Дублікат', '+380501112233');   -- помилка
```
Точний текст помилки SQLite:
```
UNIQUE constraint failed: clients.phone
```
(у консолі `sqlite3` він виводиться з префіксом `Runtime error:` чи `Error:` залежно від версії.)

Перевірка `SELECT COUNT(*) FROM orders` після помилки дала **8**: перша, успішна зміна **присутня** в базі просто зараз (транзакція ще відкрита). Помилка скасувала лише ту команду, яка її викликала, а транзакція лишилась відкритою. Після `ROLLBACK` кількість замовлень знову **7**: скасовано все, включно з першою успішною зміною.

## Завдання 5. Забутий ROLLBACK

Той самий сценарій, але замість `ROLLBACK` виконано `COMMIT`. Результат:
- `SELECT COUNT(*) FROM orders` дав **8**: перша зміна (замовлення на вареники) **зафіксувалась**;
- `SELECT COUNT(*) FROM clients WHERE full_name = 'Дублікат'` дав **0**: друга зміна, що дала помилку, **не застосувалась**.

**Чому так.** Команда, що дала помилку, ніколи не змінювала даних (її скасовано окремо), а транзакція лишилась відкритою. `COMMIT` зафіксував усе, що в ній реально виконалось, тобто лише першу зміну.

**Чим це небезпечно.** Розробник, який вважає, що вся транзакція «не пройшла» через помилку, лишає в базі половину змін: тут замовлення на вареники створене, а пов'язана з ним друга частина операції відсутня. Це і є часткове застосування, якого транзакції мали уникати, і помилка при цьому не видима, поки не перевірити дані.

## Контрольні питання

**1. Що пішло б не так без транзакції при збої між двома змінами в Завданні 1?**
База лишилась би в суперечливому стані: або нове замовлення є, а попереднє досі «Нове», або попереднє закрите, а нового нема. Жодна зміна окремо не помилкова, але разом вони дають неправдивий образ реальності.

**2. Чому в Завданні 5 результат «перша зміна є, другої нема», а не «нічого» чи «обидві»?**
Помилкова команда не змінила даних, а SQLite за замовчуванням скасовує лише її (поведінка `ABORT`), не всю транзакцію. Тож у транзакції лишилась тільки перша успішна зміна, і `COMMIT` її зберіг. «Нічого» вийшло б лише після `ROLLBACK`, а «обидві» неможливо, бо друга порушує `UNIQUE`.

**3. Атомарність це «все або нічого». Чому ж лишилась частина змін?**
СУБД гарантує атомарність **кожної окремої команди** і те, що транзакція завершиться цілком: або всі її зміни зафіксуються (`COMMIT`), або всі скасуються (`ROLLBACK`). Але **вибір** між `COMMIT` і `ROLLBACK` робить розробник: SQLite сама не відкочує транзакцію через помилку однієї команди. Розробник мав перехопити помилку й виконати `ROLLBACK`, а він виконав `COMMIT`, і СУБД чесно зафіксувала те, що було. Для довідки, у SQLite є варіант `INSERT OR ROLLBACK ...`, який відкочує всю транзакцію автоматично при конфлікті: перевірено, що після нього `in_transaction` стає `False` і всі зміни скасовані.

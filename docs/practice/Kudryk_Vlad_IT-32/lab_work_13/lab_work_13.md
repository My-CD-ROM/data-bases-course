# Звіт до Практичної роботи №13
**Варіант 8. Служба доставки їжі**

Структуру таблиць не змінено, виконано лише запити. Числова колонка взята з фактової таблиці `orders` (`price`), оскільки в моїй схемі вона там є.

## Завдання 1. printf() для числової колонки

```sql
SELECT dish_name, price, printf('%.2f грн', price) FROM orders;
```
Сире значення колонки виглядає як `120.0`, а відформатоване як `120.00 грн`. Для читача звіту різниця в тому, що відформатований результат має сталу кількість знаків після крапки (завжди рівно два, як у грошових сумах) і одразу показує одиницю виміру. Сире `120.0` не каже, чи це гривні, чи кількість, а число на кшталт `159.5` без форматування виглядало б «неповним» порівняно з `159.00`.

## Завдання 2. printf() з вирівнюванням

```sql
SELECT printf('%05d', id), printf('%8.2f', price) FROM orders;
```
Результат: `'00001'`, `'  120.00'` (ширина поля 8, незайняте місце зліва заповнено пробілами; `%05d` доповнює ціле нулями до п'яти знаків).

Вирівнювання потрібне, бо `printf` повертає **текст**, а не число. Текст у більшості виводів вирівнюється вліво, і числа з різною кількістю цифр (`99.00` і `1250.00`) мали б розрізнені розряди. Фіксована ширина з пробілами зліва вирівнює такі значення по правому краю, і розряди та крапка опиняються одне під одним у моноширинному виводі. Нулі зліва (`00001`) зручні для номерів, які мають однакову довжину (номер замовлення, код).

## Завдання 3. Зсув дати

```sql
SELECT id, order_date, date(order_date, '+7 days') FROM orders;
```
Приклад: замовлення від `2026-09-01` дає `2026-09-08`. Практичний сенс у моєму варіанті: це **кінцева дата подання претензії** щодо замовлення (наприклад, 7 днів на скаргу про запізнення чи пошкодження). Сервіс може за цією датою відрізняти скарги, подані вчасно, від прострочених. Модифікатор рахує календар коректно (враховує різну довжину місяців): `date('2026-09-01', '+1 month')` дає `2026-10-01`.

## Завдання 4. strftime() і GROUP BY

```sql
SELECT strftime('%Y-%m', complaint_date) AS місяць, COUNT(*)
FROM complaints GROUP BY місяць;
```
Результат: `2026-06 — 1`, `2026-07 — 1`, `2026-08 — 2`, `2026-09 — 8`. Для цього завдання взято таблицю скарг на кур'єрів (`complaints`), бо її дати охоплюють кілька місяців, а всі замовлення в `orders` припадають на один місяць.

Групувати довелось за результатом `strftime`, а не за самою колонкою дати, бо повна дата містить день, і майже кожен рядок мав би власну унікальну дату: вийшло б стільки груп, скільки різних днів, і кожна містила б одну-дві скарги. `strftime('%Y-%m', ...)` відкидає день і залишає спільну частину (рік і місяць), завдяки чому рядки різних днів одного місяця потрапляють в одну групу.

## Завдання 5. Некоректна дата

```sql
SELECT strftime('%Y', 'not-a-date');        -- NULL
SELECT date('not-a-date');                   -- NULL
SELECT strftime('%Y', dish_name) ...;        -- NULL (колонка без дат)
SELECT date('2026-02-30');                   -- 2026-03-02
```
SQLite **не видала помилки**: для сміття вона повернула `NULL`. А для дати, що виглядає правдоподібно, але не існує (30 лютого), повернула не `NULL`, а «виправлену» дату `2026-03-02` без жодного попередження.

Покладатися на це як на автоматичну перевірку вхідних дат не можна: `NULL` легко не помітити (наприклад, при `GROUP BY` такі рядки просто потраплять в окрему групу з `NULL`), а мовчазне виправлення неіснуючої дати взагалі приховує помилку введення.

## Контрольні питання

**1. Чим printf() відрізняється від зміни збереженого значення?**
`printf()` лише формує текст для **виводу** в результаті запиту, а значення в таблиці не змінює. Перевірено: після запитів з `printf` значення `price` для замовлення 1 у таблиці так і лишилось числом `120.0`, а не текстом `'120.00 грн'`. Щоб змінити дані фізично, потрібен `UPDATE`.

**2. Чому strftime('%Y', ...) повертає текст, а не число, і коли це має значення?**
`strftime` завжди повертає рядок. Перевірено: `typeof(strftime('%Y', '2026-09-01'))` дає `text`. Це важливо при порівнянні: `strftime('%Y', '2026-09-01') = 2026` повертає `0` (хибно), бо текст `'2026'` не дорівнює числу `2026`. Після `CAST(... AS INTEGER)` порівняння дає `1`. Так само при сортуванні: рядки сортуються посимвольно, а не за числовим значенням (для років з однаковою кількістю цифр це збігається, але для номерів без нулів зліва, наприклад `'9'` і `'10'`, ні).

**3. Що висновок Завдання 5 означає для CHECK-обмежень на колонки з датами?**
Оскільки некоректна дата дає `NULL`, а не помилку, а `CHECK` пропускає рядок, коли умова дає `NULL` (не хибність), наївне обмеження не захистить від сміття. Перевірено на пробній таблиці: `CHECK (date(d) > '2020-01-01')` **прийняло** значення `'not-a-date'`, бо вираз дав `NULL`. Правильно додавати явну перевірку: `CHECK (date(d) IS NOT NULL)`: така таблиця відхилила `'not-a-date'` помилкою `CHECK constraint failed`. Утім, і це обмеження не виявляє неіснуючі дати на кшталт 30 лютого (бо `date()` їх «виправляє»). Щоб відловити й їх, потрібна комбінація `CHECK (date(d) IS NOT NULL AND date(d) = d)`: перевірено, що вона приймає `'2026-09-01'` і відхиляє і `'not-a-date'`, і `'2026-02-30'`. Умова `date(d) = d` окремо не годиться: для сміття вона дає `NULL`, і `CHECK` такий рядок пропускає.

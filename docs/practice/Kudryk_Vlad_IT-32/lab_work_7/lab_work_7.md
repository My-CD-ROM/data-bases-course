# Звіт до Практичної роботи №7
**Варіант 8. Служба доставки їжі**

Структуру таблиць не змінено — усі запити виконано на вже наявній схемі Практик 4-6 (`restaurants`, `clients`, `orders`).

## Завдання 3. Рядок таблиці-виміру без жодної пари

На поточних даних усі три наявні ресторани (`Смак`, `Pizza House`, `Burger Point`) уже мають хоча б одне замовлення, тому запит `LEFT JOIN ... WHERE orders.id IS NULL` на вихідних даних не повернув би жодного рядка. Щоб продемонструвати роботу `LEFT JOIN` за призначенням, додано новий ресторан:
```sql
INSERT INTO restaurants (id, name, category) VALUES (4, 'Sushi Master', 'Суші');
```
Після цього запит
```sql
SELECT restaurants.name
FROM restaurants
LEFT JOIN orders ON orders.restaurant_id = restaurants.id
WHERE orders.id IS NULL;
```
повернув рівно один рядок — `Sushi Master`, оскільки на цей ресторан ще жодного замовлення не оформлено.

## Завдання 4. Свідома пастка CROSS JOIN

```sql
SELECT COUNT(*) FROM restaurants, clients;   -- 16
SELECT COUNT(*) FROM restaurants;            -- 4
SELECT COUNT(*) FROM clients;                -- 4
```
Результат кома-синтаксису без `WHERE` — **16**, тобто добуток кількості рядків (4 × 4), а не сума (4 + 4 = 8). Це відбувається тому, що `FROM restaurants, clients` без умови з'єднання — це декартів добуток (`CROSS JOIN`): SQLite бере кожен рядок `restaurants` і комбінує його з кожним рядком `clients`, не відкидаючи жодної пари.

У реальному звіті такий результат майже завжди є помилкою, а не задумом, бо кожен "ресторан × клієнт" у вигляді 16 рядків — це не 16 реальних подій (замовлень), а всі можливі штучні комбінації, які ніколи не оформлялись. Якби розробник забув дописати умову з'єднання (`ON` або `WHERE a.id = b.a_id`) у реальному запиті з великими таблицями, результат міг би "роздутися" до мільйонів рядків і або впасти з помилкою браку пам'яті, або — що гірше — мовчки видати звіт з повністю фіктивними комбінаціями, які виглядають правдоподібно, але не відповідають жодній реальній події в базі.

## Завдання 5. Обґрунтування вибору JOIN

- **Завдання 1 (INNER JOIN `orders` + `restaurants`)** — обрано `INNER JOIN`, бо кожне замовлення в таблиці `orders` гарантовано посилається на реальний, наявний ресторан (це забезпечує `FOREIGN KEY`); рядків `orders` без відповідного ресторану просто не може існувати, тому `INNER` і `LEFT` дали б тут однаковий результат — але `INNER JOIN` чіткіше передає намір "показати лише замовлення, що мають ресторан", а не "усі замовлення, навіть гіпотетично без ресторану".
- **Завдання 2 (INNER JOIN усіх трьох таблиць)** — так само `INNER JOIN` для обох з'єднань, оскільки мета — отримати рядки, де одночасно відомі і ресторан, і клієнт; якби замінити хоча б одне з'єднання на `LEFT JOIN`, у результаті могли б з'явитися рядки з `NULL` замість назви ресторану чи імені клієнта для замовлень, де `client_id` став `NULL` (наприклад, через `ON DELETE SET NULL` після видалення клієнта) — а це спотворило б звіт "ресторан-клієнт-страва", який повинен показувати лише повністю заповнені зв'язки.
- **Завдання 3 (LEFT JOIN `restaurants` → `orders`)** — тут навмисно обрано `LEFT JOIN`, бо саме мета завдання — знайти ресторани, яким НЕ відповідає жоден рядок у `orders`. З `INNER JOIN` такі ресторани взагалі зникли б із результату (INNER JOIN лишає тільки рядки, для яких знайшлася пара), і запит ніколи не зміг би повернути жодного "ресторану без замовлень" — умова `WHERE orders.id IS NULL` просто не мала б на чому спрацювати.

## Завдання 4. Підтвердження значення DEFAULT

**Опис перевірки:** При додаванні книги `'Тест 4'` стовпець `copies_count` було навмисно пропущено в списку полів команди `INSERT`. За допомогою перевірочного `SELECT`-запиту підтверджено, що база даних автоматично підставила очікуване дефолтне значення (одиницю).

**Перевірочний запит:**
```sql
SELECT title, copies_count FROM books WHERE title = 'Тест 4' AND copies_count = 1;
```

**Результат виконання:** База даних успішно повернула рядок із назвою книги та числом `1` у стовпці `copies_count`.

## Завдання 5. Навмисне порушення обмеження через UPDATE

**Опис перевірки:** Було виконано команду `UPDATE` для зміни року видання існуючої книги на `2030` рік, що порушує правило `CHECK (publication_year == 2026)`.

**Запит оновлення:**
```sql
UPDATE books SET publication_year = 2030 WHERE title = 'Тест 4';
```

**Точний текст помилки SQLite:**
`[SQLITE_CONSTRAINT_CHECK] A CHECK constraint failed (CHECK constraint failed: publication_year == 2026)`

**Письмове підтвердження:** Обмеження `CHECK` однаково ефективно блокує некоректні дані як під час створення нового запису через `INSERT`, так і під час модифікації існуючого рядка через `UPDATE`.

## Завдання 6. Обґрунтування обмежень

- **`title` (NOT NULL):** Будь-яка книга обов'язково повинна мати назву для її точної ідентифікації та пошуку користувачами в каталозі.
- **`genre` (UNIQUE):** Кожен літературний жанр має бути унікальним, щоб уникнути дублювання категорій та плутанини при сортуванні книг.
- **`publication_year` (CHECK):** Захищає базу від помилкових дат, гарантуючи, що рік видання суворо відповідає правилам обліку поточного варіанту.
- **`copies_count` (DEFAULT):** Позбавляє від ручного введення даних, автоматично підставляючи щонайменше `1` примірник для кожної нової книги в бібліотеці.

## Контрольні питання

Питання 1: Чому в SQLite неможливо просто виконати ALTER TABLE ... ADD CONSTRAINT CHECK (...), і що доводиться робити замість цього?

Відповідь: SQLite має обмежену підтримку команди `ALTER TABLE` через спрощену архітектуру. Вона дозволяє лише перейменовувати таблиці або додавати нові стовпці, але не підтримує модифікацію чинних колонок чи динамічне додавання нових обмежень (`CHECK`, `UNIQUE`, `FOREIGN KEY`). Замість цього доводиться повністю перестворювати таблицю: тимчасово вимикати перевірку ключів (`PRAGMA foreign_keys = OFF;`), перейменовувати стару таблицю в тимчасову копію, створювати нову з потрібними обмеженнями, копіювати туди дані й вмикати перевірку назад.


Питання 2: Що станеться, якщо перестворити таблицю, додавши NOT NULL до стовпця, у якому серед наявних рядків уже є NULL?

Відповідь: При копіюванні даних зі старої таблиці в нову за допомогою команди `INSERT INTO ... SELECT` виникне помилка цілісності `SQLITE_CONSTRAINT_NOTNULL` на першому ж рядку, який містить `NULL`. Вся операція перенесення даних буде заблокована і повністю скасована СУБД, а нова таблиця залишиться порожньою. Для успішного перестворення необхідно спочатку очистити або замінити всі значення `NULL` у старій таблиці на коректні дефолтні значення.


Питання 3: Чим перевірка CHECK, доданого через перестворення таблиці, відрізняється від перевірки CHECK, оголошеного одразу при CREATE TABLE?

Відповідь: Технічно всередині системи вони працюють однаково, але принципова різниця полягає в моменті первинної валідації. `CHECK`, оголошений одразу при першому `CREATE TABLE`, контролює лише нові дані, які будуть вставлятися в майбутньому. `CHECK`, доданий через перестворення таблиці, змушує SQLite примусово перевірити ще й увесь накопичений історичний архів даних під час їхнього перенесення зі старої таблиці — якщо хоча б один старий рядок не відповідає новому правилу, перестворення заблокується.


Питання 4: Чому DEFAULT не можна перевірити тим самим способом, що й NOT NULL/UNIQUE/CHECK (спробою порушення), і як його перевіряють замість цього?

Відповідь: Обмеження `NOT NULL`, `UNIQUE` та `CHECK` є забороняючими — вони відстежують дії користувача та блокують їх помилкою у разі порушення правил. `DEFAULT` працює протилежним чином: це не заборона, а автоматичний заповнювач порожнечі. Його неможливо порушити, бо якщо користувач сам передає будь-яке значення, воно просто записується поверх. Замість цього `DEFAULT` перевіряють методом виключення: навмисно не вказують потрібну колонку в запиті `INSERT`, а потім за допомогою `SELECT` підтверджують, що база даних самостійно підставила туди очікуване значення за замовчуванням.

# Практика 6. Робота з командами оновлення та видалення у SQLite

*Мета заняття: застосувати `UPDATE` і `DELETE` з Лекції 7 до фактової
(журнальної) таблиці свого варіанта, на практиці переконатися, що
обмеження цілісності з Лекції 6 (`NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT`
— щойно застосовані в [Практиці 5](05-constraints.md)) продовжують діяти
й після того, як рядок уже записано, а також на реальних даних перевірити,
як обрана в Практиці 4 дія `ON DELETE` насправді впливає на пов'язані
рядки.*

## Варіант

Той самий варіант і той самий файл `.db`, що в
[Практиці 1](01-sqlite-create.md), [Практиці 4](04-insert-keys.md) і
[Практиці 5](05-constraints.md) — сьогодні структура таблиць **не
змінюється**, лише дані в них. Знадобиться повна тристаблична схема з
Практики 4 з уже доданими в Практиці 5 обмеженнями.

Якщо свій файл `.db` після попередніх практик не збережено чи загублено —
поверніться до `v{N}_prerequisites.sql` свого варіанта з
[Практики 4](04-insert-keys.md#sql) і виконайте Завдання 1-4 тієї
практики ще раз, щоб отримати повну робочу схему для сьогоднішнього
заняття.

## Приклад: наскрізна демонстрація

На ветклініці з лекцій — `UPDATE` одного рядка, потім `DELETE`, потім
спроба порушити `CHECK` при оновленні:

```sql
-- позначити, що тварині виповнилось на рік більше
UPDATE animals SET age = age + 1 WHERE name = 'Мурчик';

-- видалити один конкретний візит (за id, найнадійніший спосіб — унікальний PK)
DELETE FROM visits WHERE id = 2;

-- спроба оновлення, яка порушує CHECK з Лекції 6
UPDATE animals SET age = -1 WHERE name = 'Рекс';
-- Runtime error: CHECK constraint failed: age >= 0
```

Останній рядок навмисно провальний: обмеження `CHECK (age >= 0)`,
додане ще в Практиці 5, продовжує діяти й на `UPDATE`, не тільки на
`INSERT`.

## Завдання

**Завдання 1. UPDATE у фактовій таблиці.** Оновіть **один конкретний**
рядок фактової (журнальної) таблиці свого варіанта, заповнивши
значення стовпця, який досі було `NULL` або мало "тимчасове" значення
— подивіться свій рядок таблиці варіантів із Практики 1: для
"Бібліотеки" це `return_date` у `loans`, для "Готелю" —
фактичний виїзд у `bookings`, для решти варіантів — аналогічний за
змістом стовпець (статус, дата завершення тощо). Використайте `WHERE`
з умовою за первинним ключем (`id = ...`), щоб оновити рівно один
рядок.

**Завдання 2. UPDATE у таблиці-вимірі.** Оновіть один "змінний"
показник в одній з двох таблиць-вимірів (наприклад
`stock_quantity`, `status`, `price`) для одного конкретного рядка.
Письмово (одне речення) поясніть, чому тут доречний саме `UPDATE`, а не
видалення старого рядка й вставка нового.

**Завдання 3. DELETE одного рядка.** Видаліть **рівно один** рядок з
фактової (журнальної) таблиці за умовою на первинний ключ (наприклад,
скасоване замовлення чи бронювання). Виконайте `SELECT COUNT(*)` до і
після видалення, щоб задокументувати, що зникнув саме один рядок, а не
більше.

**Завдання 4. Перевірка ON DELETE на реальних даних.** У Практиці 4 ви
обрали й письмово обґрунтували дію `ON DELETE` для кожного з двох
зовнішніх ключів фактової таблиці. Не забудьте `PRAGMA foreign_keys =
ON;` на початку сесії — інакше SQLite обмеження зовнішніх ключів взагалі
не перевіряє. Оберіть один рядок з однієї таблиці-виміру, на який
посилається хоча б один рядок фактової таблиці, і видаліть його
(`DELETE ... WHERE id = ...`). До видалення письмово запишіть **прогноз**
— що станеться з пов'язаними рядками фактової таблиці, виходячи з
обраної в Практиці 4 дії (`RESTRICT` — видалення буде відхилено;
`SET NULL` — FK-стовпець стане `NULL`; `CASCADE` — пов'язані рядки також
зникнуть). Після видалення (чи спроби видалення) `SELECT`-ом перевірте
фактичний результат і письмово порівняйте його з прогнозом — якщо вони
відрізняються, поясніть чому.

## Що здати й оцінюється

Здайте `lab_work_6.sql` — команди `UPDATE`/`DELETE` із Завдань 1-3 і
команду `DELETE` із Завдання 4; `lab_work_6.db` — оновлений файл бази
даних після всіх завдань; і `lab_work_6.md` — письмові відповіді
Завдань 2 і 4 (прогноз і фактичний результат для Завдання 4).

Контрольні питання:

- Чим `UPDATE ... SET колонка = колонка + 1` відрізняється від
  `UPDATE ... SET колонка = <конкретне число>`?
- Чому обмеження `NOT NULL`/`UNIQUE`/`CHECK` (Практика 5) завжди
  перевіряються при `UPDATE`, тоді як `FOREIGN KEY` — лише за умови
  `PRAGMA foreign_keys = ON;`?
- Якби на вашій фактовій таблиці FK було оголошено з `ON DELETE
  CASCADE` замість `RESTRICT` (Лекція 5), як це змінило б наслідки
  видалення рядка з таблиці-вимір, на яку та фактова таблиця
  посилається?
- Чому `DELETE` без `WHERE` небезпечніший за помилку типу чи
  порушення обмеження цілісності?

Оцінюється правильність виконаних `UPDATE`/`DELETE` (рівно ті рядки, що
вимагались, жодного зайвого), а також те, наскільки прогноз у Завданні 4
узгоджується з фактично спостереженою поведінкою `ON DELETE` — і
обґрунтованість усіх письмових відповідей.

## Підсумок заняття

- Фактова (журнальна) таблиця варіанта оновлена (`UPDATE`) і зменшена
  на один рядок (`DELETE`).
- Обмеження цілісності, додані в Практиці 5, підтверджено діють і при
  `UPDATE`, не лише при `INSERT`.
- Дія `ON DELETE`, обрана й обґрунтована в Практиці 4, перевірена на
  реальних даних: прогнозована поведінка порівняна з фактичною після
  видалення рядка з таблиці-виміру.

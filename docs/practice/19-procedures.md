# Практика 19. Створення процедур у PostgreSQL

*Мета заняття: оформити атомарну пару пов'язаних змін (за зразком
Практики 12, тепер у PostgreSQL) як іменовану процедуру мовою PL/pgSQL
за Лекцією 21 — і на практиці підтвердити, чому саме процедура, а не
функція, підходить для цієї задачі.*

## Варіант

Ваша база у PostgreSQL з Практики 16. Якщо базу втрачено — поверніться
до Практики 16.

## Приклад: наскрізна демонстрація

```sql
CREATE OR REPLACE PROCEDURE sell_car(p_car_id INTEGER, p_client_id INTEGER, p_price NUMERIC)
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO sales (car_id, client_id, sale_date, sale_price)
    VALUES (p_car_id, p_client_id, CURRENT_DATE, p_price);

    UPDATE cars SET status = 'продано' WHERE id = p_car_id;

    COMMIT;
END;
$$;

CALL sell_car(5, 3, 980000);
```

## Завдання

**Завдання 1. Процедура для атомарної пари.** Напишіть процедуру, що
виконує ту саму атомарну пару змін, яку ви реалізували в Практиці 12
(вручну через `BEGIN`/`COMMIT`) — `INSERT` у фактову таблицю й
`UPDATE` пов'язаного рядка таблиці-виміру (лічильник чи статус).
Параметри процедури — значення, потрібні для обох операцій.

**Завдання 2. Викликати процедуру.** Викличте процедуру з Завдання 1
через `CALL` з реальними значеннями вашого варіанта. Перевірте
запитом `SELECT`, що обидві зміни (в обох таблицях) застосувались.

**Завдання 3. Свідома помилка викликати процедуру через SELECT.**
Спробуйте викликати свою процедуру через `SELECT ваша_процедура(...)`
замість `CALL`. Зафіксуйте письмово точний текст помилки та підказку,
яку дає PostgreSQL.

**Завдання 4. Процедура з умовною логікою.** Додайте до нової чи
вже написаної процедури умовну перевірку (`IF ... THEN RAISE
EXCEPTION ...`), що не дає виконати операцію за нелогічних вхідних
даних (наприклад, від'ємна ціна чи кількість). Перевірте обидва
випадки: виклик із коректними даними (успіх) і з некоректними
(помилка).

**Завдання 5. Порівняння з Практикою 12.** Письмово порівняйте
підхід цієї практики (іменована процедура, викликана одним `CALL`) з
підходом Практики 12 (ручний `BEGIN`/два запити/`COMMIT` щоразу
заново). Що саме процедура дозволяє НЕ повторювати?

## Що здати й оцінюється

Здайте текст усіх написаних `CREATE PROCEDURE` (Завдання 1 і 4),
виклики `CALL` з результатами, точний текст помилки з Завдання 3, і
письмове порівняння з Завдання 5. Контрольні питання:

- Чому в Завданні 1 обрана вами процедура НЕ могла бути написана як
  функція (Лекція 20) — що саме в її тілі це виключає?
- Що станеться з частиною процедури, виконаною ДО `COMMIT`, якщо
  друга частина (після `COMMIT`) впаде з помилкою?
- Чому підказка з Завдання 3 ("To call a procedure, use CALL") —
  корисніша для розробника, ніж просто загальна помилка синтаксису?

Оцінюється коректність і завершеність процедури Завдання 1 (обидві
зміни, `COMMIT`), правильно зафіксована помилка Завдання 3, і робоча
перевірка обох випадків (успіх/помилка) у Завданні 4.

## Підсумок заняття

- Оформлено атомарну пару пов'язаних змін фактової та вимірної таблиці
  свого варіанта як іменовану процедуру мовою PL/pgSQL.
- На практиці підтверджено: процедуру можна викликати лише через
  `CALL`, а не `SELECT`.
- Додано умовну перевірку вхідних даних усередині процедури з
  `RAISE EXCEPTION` для навмисно некоректного випадку.

# Лекція 14. Транзакції у SQLite: BEGIN, COMMIT, ROLLBACK

*Лекція 13 пояснила, ЩО таке транзакція і чому вона потрібна (ACID).
Ця лекція — конкретний синтаксис SQLite: як позначити межі транзакції
(`BEGIN`), зафіксувати її результат (`COMMIT`) чи скасувати його
(`ROLLBACK`), і найважливіша практична пастка — що станеться, якщо
всередині транзакції виникла помилка, а розробник забув про
`ROLLBACK`.*

## 1. BEGIN … COMMIT — фіксація групи змін

```sql
BEGIN;

INSERT INTO owners VALUES (2, 'Коваль', 'Андрій', NULL, NULL);
INSERT INTO animals VALUES (2, 'Мурка', 'кіт', 3, 'на обліку', 2);

COMMIT;
```

`BEGIN` відкриває транзакцію — усі наступні команди стають частиною
однієї групи, а не окремими неявними транзакціями (Лекція 13, розділ
4). `COMMIT` фіксує РАЗОМ усі зміни, зроблені після `BEGIN`: перевірено
— після `COMMIT` обидва нових рядки (і `owners`, і `animals`) присутні
в базі.

## 2. BEGIN … ROLLBACK — скасування групи змін

```sql
BEGIN;

INSERT INTO owners VALUES (3, 'Тест', 'Тестович', NULL, NULL);
-- у цей момент рядок УЖЕ видно всередині цієї ж транзакції...

ROLLBACK;
-- ...але після ROLLBACK його в базі немає зовсім, як і не додавали
```

`ROLLBACK` скасовує ВСІ зміни, зроблені від останнього `BEGIN` —
перевірено: рядок, доданий усередині транзакції, зникає повністю після
`ROLLBACK`, так, наче команди `INSERT` ніколи не виконувалось.

## 3. Найважливіша пастка: помилка не скасовує транзакцію сама

```sql
BEGIN;

INSERT INTO owners (id, email) VALUES (4, 'c@test.com');   -- успішно
INSERT INTO owners (id, email) VALUES (5, 'c@test.com');   -- email має UNIQUE!
```

```text
Runtime error: UNIQUE constraint failed: owners.email
```

Помилка в другій команді **не скасовує транзакцію автоматично** —
перевірено: перший `INSERT` (id = 4) залишається "в очікуванні" всередині
відкритої транзакції. Якщо на цьому місці розробник (забувши про
помилку) все одно виконає `COMMIT` —

```sql
COMMIT;
```

— зафіксується лише ПЕРШИЙ, успішний `INSERT` (id = 4); другий, що
впав з помилкою, просто не застосувався, а решта транзакції — так,
наче нічого не сталося. Це небезпечно: розробник може вважати, що вся
група команд не пройшла (бо була помилка), тоді як частина вже
зафіксована в базі. **Правильна реакція на помилку всередині
транзакції — завжди явний `ROLLBACK`**, а не спроба продовжити чи
одразу `COMMIT`:

```sql
BEGIN;
INSERT INTO owners (id, email) VALUES (4, 'c@test.com');
-- ... тут виникла помилка на другій команді ...
ROLLBACK;   -- прибирає і перший, уже "успішний" INSERT
```

## 4. Вкладені транзакції — заборонені

```sql
BEGIN;
BEGIN;
```

```text
Runtime error: cannot start a transaction within a transaction
```

SQLite не дозволяє відкрити другу транзакцію всередині вже відкритої —
перевірено: спроба повторного `BEGIN` до `COMMIT`/`ROLLBACK` першої
завершується помилкою. (Для складніших сценаріїв, де потрібна
"транзакція всередині транзакції", SQLite має `SAVEPOINT` — за межами
цього курсу.)

## 5. Практичний шаблон: атомарна пара INSERT + UPDATE

```sql
BEGIN;

INSERT INTO sales (car_id, client_id, sale_date, sale_price)
VALUES (5, 3, '2025-06-10', 980000);

UPDATE cars SET status = 'продано' WHERE id = 5;

COMMIT;
```

Це і є розв'язок мотивуючої проблеми з Лекції 13: обидві команди
всередині однієї транзакції — або обидві зафіксуються `COMMIT`, або (у
разі помилки чи свідомого `ROLLBACK`) жодна з них не залишить слід у
базі. Автомобіль ніколи не опиниться в стані "продано без запису
продажу" чи "запис продажу без позначки продано".

## Підсумок

- `BEGIN` відкриває транзакцію; `COMMIT` фіксує всі зміни від
  `BEGIN` разом; `ROLLBACK` скасовує їх усі, включно з тими, що вже
  "виконались" усередині транзакції.
- Помилка всередині транзакції НЕ скасовує її автоматично — забутий
  `ROLLBACK` і подальший `COMMIT` фіксує лише ту частину команд, що
  встигла виконатись без помилки, мовчки залишаючи базу в частково
  зміненому стані.
- SQLite не дозволяє вкладені транзакції — повторний `BEGIN` до
  завершення першої транзакції завершується помилкою.
- Атомарна пара пов'язаних команд (наприклад, `INSERT` факту +
  `UPDATE` пов'язаного статусу чи лічильника) — типовий і практично
  важливий шаблон використання транзакції.

# Лекція 13. Індекси в SQLite. Оптимізація запитів, EXPLAIN

*Досі ми перевіряли запити на одне: чи правильний результат. Сьогодні
інше питання: скільки роботи виконує SQLite, щоб цю відповідь
отримати? Поки в таблиці кілька десятків рядків, різниці не видно, але
таблиця замовлень інтернет-магазину легко виростає до мільйона рядків.
Індекс робить пошук швидким, а `EXPLAIN QUERY PLAN` показує, як саме
SQLite виконує запит.*

Усі приклади – на базі інтернет-магазину: таблиця `customers` (клієнти)
і таблиця `orders` (замовлення) з колонками `id`, `customer_id`,
`order_date`, `status` (`new`, `paid` або `shipped`) і `amount`. Плани й
час виконання в лекції перевірено в SQLite 3.54 на таблиці з
1 000 000 замовлень від 50 000 клієнтів.

## Частина 1. Від SCAN до SEARCH

### 1. Проблема: повний перегляд таблиці (SCAN)

Знайдемо всі замовлення клієнта з номером 3, але перед `SELECT`
допишемо `EXPLAIN QUERY PLAN`:

```sql
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 3;
```

```text
QUERY PLAN
`--SCAN orders
```

`EXPLAIN QUERY PLAN` (дослівно «поясни план запиту») не виконує запит
і не повертає рядків таблиці. Замість результату він показує **план** –
як SQLite збирається шукати потрібні рядки. У консолі `sqlite3` план має
вигляд дерева, у DB Browser for SQLite – таблиці, зміст однаковий. Є ще
команда `EXPLAIN` без `QUERY PLAN`: вона показує внутрішні інструкції
SQLite, і в цьому курсі вона не потрібна.

`SCAN orders` – це **повний перегляд таблиці**: SQLite бере рядок за
рядком і в кожному перевіряє умову `customer_id = 3`. Якщо в таблиці
мільйон рядків, а потрібних п’ять, перевірено буде все одно мільйон.
Запит при цьому правильний: просто SQLite поки нема чим допомогти собі
шукати швидше.

### 2. CREATE INDEX: прямий шлях до потрібних рядків

**Індекс** – окрема впорядкована структура, у якій для кожного значення
колонки записано, в яких рядках таблиці воно трапляється.

```sql
CREATE INDEX idx_orders_customer ON orders(customer_id);

EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 3;
```

```text
SEARCH orders USING INDEX idx_orders_customer (customer_id=?)
```

`CREATE INDEX ім’я ON таблиця(колонка)` створює індекс. Назву обираємо
самі; зручна домовленість – `idx_таблиця_колонка`.

Той самий запит, без жодної зміни, тепер має план `SEARCH ... USING
INDEX`. **SEARCH** – прямий пошук: SQLite іде в індекс, знаходить там
значення 3 і переходить лише до тих рядків, де воно є. У дужках –
умова, за якою використано індекс; знак питання стоїть на місці
конкретного значення. Змінився лише спосіб пошуку: запит і результат
ті самі.

Індекс не пришвидшує перегляд таблиці, а робить його непотрібним:
`SCAN` перевіряє всі рядки, `SEARCH` – лише потрібні.

### 3. Як влаштований індекс

Найближча аналогія – предметний покажчик у кінці підручника: терміни
стоять за алфавітом, поруч – номери сторінок. Щоб знайти слово, не
гортаємо книгу, а йдемо одразу на потрібну сторінку. Індекс так само
зберігає впорядковані значення колонки і поруч із кожним – посилання на
рядок таблиці.

Усередині індекс – це **дерево**. Нагадаємо різницю двох структур даних:

- **Граф** – вузли і зв’язки між ними без жодних обмежень. Як карта
  доріг: між двома містами може бути кілька шляхів, можна повернутися
  по колу.
- **Дерево** – окремий випадок графа: один корінь, у кожного вузла рівно
  один «батько», циклів немає, тож до будь-якого вузла веде рівно один
  шлях. Як папки на комп’ютері.

Для пошуку дерево зручне: від кореня до потрібного значення веде один
короткий шлях. Тому бази даних найчастіше будують індекси як
**B-дерево** (читається «бі-дерево») – дерево, у якого кожен вузол має
не два відгалуження, а сотні. На кожному рівні відкидається більша
частина варіантів, тож навіть для мільйона значень у B-дереві лише
три-чотири рівні (у нашому тесті – 3 рівні, до ~400 записів у вузлі).
Схоже на гру «вгадай число від 1 до мільйона» з підказками «більше» чи
«менше»: вистачає близько 20 спроб. B-дерево – стандартний тип індексу
і в SQLite, і в PostgreSQL.

Деякі індекси SQLite має без нашої участі:

- таблиця зберігається впорядкованою за `INTEGER PRIMARY KEY`, тож
  пошук за `id` швидкий без `CREATE INDEX`: план показує `SEARCH orders
  USING INTEGER PRIMARY KEY (rowid=?)`;
- для кожної колонки з `UNIQUE` SQLite автоматично будує службовий
  індекс. Якби в `customers` колонка `email` мала `UNIQUE`, з’явився б
  індекс `sqlite_autoindex_customers_1`.

### 4. Як індекс змінюється разом із таблицею

Запис індексу – це пара: значення колонки і номер рядка таблиці (для
таблиці з `INTEGER PRIMARY KEY` номер рядка – це `id`). Пари
впорядковані за значенням. Виконаємо три зміни:

```sql
INSERT INTO orders (id, customer_id, order_date, status, amount)
VALUES (107, 3, '2025-06-10', 'new', 1200);

UPDATE orders SET customer_id = 6 WHERE id = 104;

DELETE FROM orders WHERE id = 102;
```

| Індекс на `customer_id` до змін | Після INSERT, UPDATE і DELETE |
|---|---|
| 1 · рядок 104 | 3 · рядок 103 |
| 2 · рядок 102 | 3 · рядок 105 |
| 3 · рядок 103 | **3 · рядок 107** (INSERT) |
| 3 · рядок 105 | 4 · рядок 106 |
| 4 · рядок 106 | 5 · рядок 101 |
| 5 · рядок 101 | **6 · рядок 104** (UPDATE) |

- `INSERT` додає запис не в кінець, а **на своє місце за порядком**.
- `UPDATE` проіндексованої колонки для індексу означає «видалити старий
  запис і вставити новий» (1 · рядок 104 перейшов у кінець як
  6 · рядок 104). Зміна колонки, якої в індексі немає (наприклад,
  `amount`), індекс не зачіпає.
- `DELETE` прибирає запис (2 · рядок 102 зник).

Усе це SQLite робить **сам, у тій самій транзакції**, що й зміну
таблиці: оновлювати чи перебудовувати індекс вручну не потрібно, і він
ніколи не застаріває. `ROLLBACK` скасовує й зміни в індексі. Але кожна
така зміна – додаткова робота (розділ 15).

### 5. Наскільки індекс прискорює пошук

```sql
SELECT * FROM orders WHERE customer_id = 777;   -- 24 рядки з 1 000 000
```

| | Час |
|---|---|
| без індексу (`SCAN`) | ≈ 0,05 с |
| з індексом (`SEARCH`) | ≈ 0,00015 с |
| побудова індексу, один раз | ≈ 0,3 с |

Різниця – у сотні разів. Точні числа залежать від комп’ютера, а
співвідношення зберігається. На навчальній таблиці з двадцятьма рядками
різниці не видно, тому на практиці дивимося на **план**, а не на
секундомір: саме спосіб пошуку визначає швидкість на великих даних.
Виміряти час самостійно можна в консолі `sqlite3` командою `.timer on`.

### 6. Індекс і JOIN

Індекс прискорює не лише `WHERE`. Під час `JOIN` для рядка однієї
таблиці SQLite шукає пару в іншій:

```sql
EXPLAIN QUERY PLAN
SELECT c.name, o.order_date, o.amount
FROM customers c JOIN orders o ON o.customer_id = c.id
WHERE c.id = 777;
```

```text
-- без індексу на orders.customer_id
|--SEARCH c USING INTEGER PRIMARY KEY (rowid=?)
`--SCAN o

-- з індексом idx_orders_customer
|--SEARCH c USING INTEGER PRIMARY KEY (rowid=?)
`--SEARCH o USING INDEX idx_orders_customer (customer_id=?)
```

План `JOIN` має рядок на кожну таблицю. Без індексу, щоб знайти
замовлення одного клієнта, SQLite переглядає весь мільйон рядків
`orders` (≈ 0,06 с); з індексом – менше мілісекунди.

Майже кожен `JOIN` іде від первинного ключа однієї таблиці до
**зовнішнього ключа** іншої. Первинний ключ SQLite індексує сам, а
зовнішній – ні, тому зовнішні ключі – перші кандидати на індекс.

## Частина 2. Композитний індекс

### 7. Індекс на кілька колонок

Умова на двох колонках:

```sql
SELECT * FROM orders WHERE customer_id = 3 AND status = 'paid';
```

З індексом лише на `customer_id` план – `SEARCH ... (customer_id=?)`:
через індекс SQLite знаходить замовлення клієнта, а статус перевіряє
по черзі в кожному знайденому рядку. **Композитний (складений) індекс**
охоплює кілька колонок, перелічених через кому:

```sql
CREATE INDEX idx_orders_customer_status ON orders(customer_id, status);
```

```text
SEARCH orders USING INDEX idx_orders_customer_status (customer_id=? AND status=?)
```

Тепер обидві умови перевіряються прямо в індексі.

**Композитний індекс працює зліва направо.** Він упорядкований спершу
за `customer_id`, і лише всередині кожного клієнта – за `status`. Тому
запит лише за другою колонкою індекс не використовує:

```sql
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE status = 'paid';
```

```text
SCAN orders
```

Аналогія – список студентів, упорядкований за прізвищем, а
однофамільців – за ім’ям. Знайти всіх Коваленків легко, а всіх Ольг –
лише переглянувши весь список.

Звідси правила:

- у композитному індексі **першою ставлять колонку, за якою фільтрують
  найчастіше** (менеджери щодня шукають замовлення клієнта, а всі
  оплачені – раз на місяць, тож першою йде `customer_id`);
- індекс `(customer_id, status)` працює і для умови лише за
  `customer_id`, тож окремий індекс на `customer_id` поруч із ним зайвий.

### 8. Композитний індекс на п’ять колонок

Таблиця доставок `deliveries` зберігає адресу: область `region`, місто
`city`, вулицю `street`, будинок `house`, квартиру `apartment`.

```sql
CREATE INDEX idx_deliveries_address
ON deliveries(region, city, street, house, apartment);
```

Індекс упорядкований, як посилки в сортувальному центрі: спершу за
областю, всередині області – за містом, далі за вулицею і так далі.
Скільки колонок індексу використано, видно в плані в дужках, наприклад
`SEARCH deliveries USING INDEX idx_deliveries_address (region=? AND
city=?)`. Підсумки для різних умов (замість `?` в умові – конкретне
значення):

| Умова `WHERE` | Що використано з індексу |
|---|---|
| `region = ? AND city = ? AND street = ? AND house = ? AND apartment = ?` | усі 5 колонок |
| `region = ? AND city = ?` | 2 колонки |
| `city = ? AND street = ?` | нічого – `SCAN` |
| `region = ? AND street = ?` | лише `region` |
| `region = ? AND city = ? AND street > ? AND house = ?` | 3 колонки (`house` – уже ні) |

Три правила:

1. Індекс працює для **будь-якого початку ланцюжка**: перша колонка,
   перші дві, перші три і так далі. Без першої колонки (`region`) –
   `SCAN`: не знаючи області, SQLite не знає, з якого місця індексу
   почати шукати місто.
2. **Пропущена колонка із середини** зупиняє пошук через індекс перед
   пропуском; решту умов SQLite перевіряє по черзі.
3. **Порівняння `>` чи `<`** теж зупиняє ланцюжок: вулиць у діапазоні
   багато, і всередині кожної будинки впорядковані заново.

Порядок умов у `WHERE` значення не має: ті самі умови, записані задом
наперед, дають той самий план. Важливий лише порядок колонок в
індексі.

### 9. Широкий індекс чи кілька вузьких

Широкий індекс обслуговує багато запитів (за областю, за областю й
містом, за повною адресою), точніше звужує пошук і частіше дозволяє не
звертатися до таблиці (розділ 10). П’ять окремих вузьких індексів
(на `region`, `city` і так далі) його не замінять: для однієї таблиці в
запиті SQLite зазвичай бере лише один індекс.

Але широкий індекс і забирає більше. На 200 000 доставок таблиця важить
11,9 МБ, а індекс на п’ять колонок – 11,1 МБ: по суті, це друга,
впорядкована копія таблиці. Кожна зміна будь-якої з п’яти колонок
оновлює індекс, а допомагає він лише запитам, умова яких починається з
`region`.

Правило: у композитний індекс беруть **стільки колонок, скільки є в
умовах частих запитів**, від найчастішої до найрідшої. Колонки «про
запас» у кінці лише збільшують індекс. Якщо часто шукають за містом і
вулицею без області, потрібен окремий індекс на `(city, street)`.

### 10. Покривальний індекс

Іноді запиту вистачає самого індексу:

```sql
EXPLAIN QUERY PLAN
SELECT status, COUNT(*) FROM orders
WHERE customer_id = 3 GROUP BY status;
```

```text
SEARCH orders USING COVERING INDEX idx_orders_customer_status (customer_id=?)
```

**Покривальний індекс** (`COVERING INDEX`) – індекс, у якому вже є всі
колонки, потрібні запиту. Тут потрібні лише `customer_id` і `status`, і
обидві є в індексі, тож SQLite бере відповідь з індексу і рядків
таблиці не відкриває. Запит `SELECT *` покривальним не буде: `order_date`
і `amount` в індексі немає. Ще одна причина вибирати лише потрібні
колонки.

Коли для умови підходить кілька індексів, вибір робить сам SQLite. Тому,
дивлячись на план, перевіряйте не лише слово `SEARCH`, а й **назву**
обраного індексу.

## Частина 3. Індекс і ORDER BY

### 11. Сортування без окремого кроку

```sql
EXPLAIN QUERY PLAN SELECT * FROM orders ORDER BY order_date;
```

```text
-- без індексу
|--SCAN orders
`--USE TEMP B-TREE FOR ORDER BY

-- після CREATE INDEX idx_orders_date ON orders(order_date);
`--SCAN orders USING INDEX idx_orders_date
```

`USE TEMP B-TREE FOR ORDER BY` – окремий крок сортування: SQLite
збирає всі рядки і будує тимчасове B-дерево, щоб їх упорядкувати. З
індексом цей рядок зникає: SQLite читає таблицю в порядку індексу, і
результат одразу відсортований. Слово `SCAN` тут не означає, що індекс
не спрацював: запит без `WHERE` сам просить усі рядки, а `USING INDEX`
показує, що перегляд іде в готовому порядку.

### 12. ORDER BY і композитний індекс

П’ять останніх замовлень клієнта:

```sql
SELECT * FROM orders WHERE customer_id = 3
ORDER BY order_date DESC LIMIT 5;
```

```text
-- з індексом лише на customer_id
|--SEARCH orders USING INDEX idx_orders_customer (customer_id=?)
`--USE TEMP B-TREE FOR ORDER BY

-- після CREATE INDEX idx_orders_customer_date ON orders(customer_id, order_date);
`--SEARCH orders USING INDEX idx_orders_customer_date (customer_id=?)
```

У композитному індексі замовлення кожного клієнта вже лежать за датою:
SQLite бере п’ять записів із потрібного кінця і зупиняється. `DESC` не
заважає – індекс можна читати і з початку, і з кінця.

**Правило:** `ORDER BY` бере порядок з індексу, якщо колонки сортування
йдуть в індексі **одразу після колонок, зафіксованих у `WHERE`
рівністю**. На прикладі індексу на адресу з умовою
`region = ? AND city = ?`:

| `ORDER BY` | План |
|---|---|
| `street, house` | без окремого сортування |
| `street DESC, house DESC` | без окремого сортування (індекс читається з кінця) |
| `house` | `USE TEMP B-TREE FOR ORDER BY` – пропущено `street` |
| `street, house DESC` | `USE TEMP B-TREE FOR LAST TERM OF ORDER BY` – змішаний напрям |

Так само з індексом `(customer_id, order_date)` запит
`WHERE customer_id = 3 ORDER BY amount` потребує окремого сортування:
колонки `amount` в індексі немає.

## Частина 4. Коли індекс не допомагає

### 13. Умова, яка вимикає індекс

Створити індекс замало: SQLite скористається ним лише тоді, коли умова
має відповідну форму. Одну таку ситуацію ми вже бачили – умову без
першої колонки композитного індексу (розділи 7–8).

**Вираз чи функція над колонкою.**

```sql
WHERE customer_id + 1 = 4                    -- SCAN
WHERE customer_id = 3                        -- SEARCH
WHERE strftime('%Y', order_date) = '2025'    -- SCAN
WHERE order_date >= '2025-01-01'
  AND order_date <  '2026-01-01'             -- SEARCH
```

Індекс зберігає значення самої колонки, а не результат виразу, і
«розвертати» вираз SQLite не вміє. Вихід – залишити колонку в умові без
обчислень: арифметику перенести на інший бік рівності, функцію над
датою замінити діапазоном дат. Можна також створити індекс саме на
виразі: `CREATE INDEX idx_orders_year ON orders(strftime('%Y', order_date));`.

**Пошук за шаблоном `LIKE`.** Умова `name LIKE '%енко'` (прізвища, що
закінчуються на «енко») не може скористатися індексом: початок значення
невідомий. Навіть `LIKE 'Ков%'` у SQLite зазвичай іде через `SCAN`,
бо `LIKE` за замовчуванням не розрізняє великі й малі латинські
літери, а індекс розрізняє. Для точного збігу пишіть `=`.

**Мало різних значень.** Індекс на колонці `status`, де лише три
значення, SQLite використає – у плані буде `SEARCH`. Але кожен статус –
третина таблиці, а читати третину рядків через індекс довше, ніж
переглянути всю таблицю: для кожного рядка доводиться переходити з
індексу в таблицю. На мільйоні замовлень такий запит з індексом
виконувався **вдвічі довше**, ніж без нього. `SEARCH` у плані ще не
гарантує швидкості.

## Частина 5. DROP INDEX, sqlite_master і ціна індексу

### 14. Перегляд і видалення індексів

```sql
SELECT name, tbl_name FROM sqlite_master WHERE type = 'index';

DROP INDEX idx_orders_customer;
```

`sqlite_master` – службова таблиця з описом усіх об’єктів бази
(таблиць, індексів, представлень); `type = 'index'` відбирає індекси,
`name` – назва індексу, `tbl_name` – його таблиця. Службові індекси для
`UNIQUE` (`sqlite_autoindex_…`) теж потрапляють у цей список.

`DROP INDEX` видаляє лише індекс – таблиця й дані не змінюються. Після
видалення SQLite бере інший придатний індекс (у нашій базі після
видалення `idx_orders_customer` – композитний `idx_orders_customer_date`,
що теж починається з `customer_id`) або повертається до `SCAN`.

### 15. Ціна індексу

Мільйон замовлень вставлено в порожню таблицю з різною кількістю
індексів (1 – на `customer_id`; 3 – ще на `order_date` і
`(customer_id, status)`; 5 – ще на `status` і `amount`):

| Індексів | Вставка 1 000 000 рядків | Розмір файлу бази |
|---|---|---|
| 0 | 0,5 с | 30 МБ |
| 1 | 1,3 с | 42 МБ |
| 3 | 3,5 с | 80 МБ |
| 5 | 5,2 с | 107 МБ |

Що забирає індекс:

- **Місце.** Кожен індекс – копія значень своїх колонок разом із
  номерами рядків. П’ять індексів збільшили файл більш ніж утричі; разом
  із файлом ростуть резервні копії.
- **Час запису.** Кожен `INSERT` і `DELETE` оновлює всі індекси таблиці,
  `UPDATE` – ті, що містять змінену колонку (розділ 4). З п’ятьма
  індексами вставка тривала вдесятеро довше. Водночас знайти рядки для
  `UPDATE` чи `DELETE` з умовою `WHERE` індекс якраз допомагає.
- **Час побудови.** `CREATE INDEX` на великій таблиці читає всю таблицю
  і впорядковує значення; поки індекс будується, записувати в базу не
  можна (у SQLite одночасно пише лише одна транзакція).

Тому індекси створюють **цілеспрямовано**: на колонках, за якими
справді часто шукають, з’єднують таблиці чи сортують, – типово на
зовнішніх ключах. Перед створенням індексу подивіться план запиту, а
після – переконайтеся, що план справді змінився. Таблиці, у які
постійно пишуть і рідко читають (наприклад, журнал подій), мають
обходитися мінімумом індексів.

## 16. Запитання для самоперевірки

**У плані стоїть `SCAN orders`. Що це означає і чи завжди це погано?**

SQLite переглядає всі рядки таблиці. Для маленької таблиці це нормально,
для великої таблиці й частого запиту – сигнал подумати про індекс.

**Що відбувається з індексом на `customer_id`, коли в замовленні змінюють `customer_id`? А коли змінюють `amount`?**

У першому випадку SQLite видаляє старий запис індексу і вставляє новий
на своє місце за порядком. У другому індекс не змінюється: колонки
`amount` в ньому немає.

**Чому індекс на зовнішньому ключі прискорює `JOIN`?**

Під час з’єднання SQLite для кожного рядка однієї таблиці шукає пари в
іншій за зовнішнім ключем. З індексом це `SEARCH` замість `SCAN` усієї
другої таблиці.

**Є індекс `(region, city, street, house, apartment)`. Для яких умов SQLite використає його: `region = ? AND city = ?`; `city = ?`; `region = ? AND street = ?`?**

Для першої – дві колонки. Для другої – ні (`SCAN`), немає першої
колонки. Для третьої – лише `region`, бо `city` пропущено.

**Індекс `(customer_id, order_date)`. Чи потрібне окреме сортування для `WHERE customer_id = 3 ORDER BY order_date DESC`? А для `ORDER BY amount`?**

У першому випадку ні: дати клієнта в індексі вже впорядковані, `DESC`
читає індекс з кінця. У другому так: `amount` в індексі немає.

**Чому `WHERE customer_id + 1 = 4` ігнорує індекс на `customer_id`?**

Індекс упорядковано за значеннями самої колонки, а не за результатом
виразу. Колонка в умові має стояти без обчислень.

**Що означає `COVERING INDEX` у плані?**

Усі колонки, потрібні запиту, є в самому індексі, тож SQLite бере
відповідь з індексу, не звертаючись до таблиці.

**Що забирає кожен новий індекс?**

Місце на диску і час запису: кожен `INSERT`, `DELETE` і `UPDATE`
проіндексованих колонок оновлює ще й індекс. Тому індексів має бути
стільки, скільки справді потрібно запитам.

## Підсумок

- `EXPLAIN QUERY PLAN` показує план запиту, а не результат: `SCAN` –
  повний перегляд таблиці, `SEARCH ... USING INDEX` – прямий пошук.
- `CREATE INDEX` будує B-дерево; SQLite сам оновлює індекс під час
  кожного `INSERT`, `UPDATE` і `DELETE`, у тій самій транзакції.
- Індекс на зовнішньому ключі прискорює `JOIN`.
- Композитний індекс працює зліва направо: для будь-якого початку
  ланцюжка колонок; пропущена колонка або `>` чи `<` зупиняють ланцюжок.
  `COVERING INDEX` – відповідь з індексу, без звернення до таблиці.
- `ORDER BY` бере готовий порядок з індексу, якщо колонки сортування
  йдуть одразу після колонок з рівністю в `WHERE`; інакше в плані
  `USE TEMP B-TREE`.
- Вираз чи функція над колонкою і `LIKE '%...'` вимикають індекс.
- `sqlite_master` показує всі індекси бази, `DROP INDEX` видаляє індекс
  без втрати даних.
- Кожен індекс забирає місце й час запису (5 індексів – файл більш ніж
  утричі більший, вставка вдесятеро довша), тому індекси створюють лише
  там, де за колонкою справді шукають, з’єднують таблиці чи сортують.

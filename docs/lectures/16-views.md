# Лекція 16. Подання (Views) і матеріалізовані подання (Materialized Views)

*Складний запит із `JOIN` і `WHERE` (наприклад, "тварини на обліку з
іменем власника") доводиться переписувати щоразу, коли він потрібен.
І якщо формулу трохи зміните в одному місці, а забудете в іншому,
результати "розійдуться". PostgreSQL дозволяє зберегти запит один раз
під іменем як **подання (view)** і надалі звертатись до нього, як до
звичайної таблиці.*

Приклади лекції виконуються над таблицею `animals(id, name, species, age, status, owner_id)`, де `status` — звичайна текстова колонка без `DEFAULT`; на початку в таблиці є кілька тварин зі статусом `'на обліку'`.

## 1. CREATE VIEW: запит, збережений під іменем

```sql
CREATE VIEW animals_active AS
SELECT id, name, species, age
FROM animals
WHERE status = 'на обліку';

SELECT * FROM animals_active;
```

`CREATE VIEW ім'я AS SELECT ...` не створює нову таблицю з окремими
даними: це збережений **запит**, який виконується щоразу, коли до
подання звертаються. Синтаксично `SELECT * FROM animals_active`
виглядає так, наче це звичайна таблиця, хоча фізично жодних власних
рядків подання не зберігає.

## 2. Подання завжди "живе"

```sql
INSERT INTO animals (name, species, age, status)
VALUES ('Джек', 'собака', 1, 'на обліку');

SELECT * FROM animals_active;
-- новий рядок з'явився в поданні одразу, без жодної додаткової дії
```

Оскільки подання щоразу перевиконує свій `SELECT`, воно автоматично
показує актуальні дані базової таблиці: новий рядок,
доданий у `animals` ПІСЛЯ створення подання, одразу видимий і через
`animals_active`, без потреби щось "оновлювати".

## 3. Через просте подання можна писати дані

```sql
INSERT INTO animals_active (name, species, age) VALUES ('Соня', 'кіт', 2);

SELECT * FROM animals WHERE name = 'Соня';
-- (Соня, кіт, 2, status = NULL) — колонки status немає в SELECT подання,
-- тож рядок отримав NULL, а не значення 'на обліку'
```

Для простого подання (без `JOIN`, без агрегатних функцій, з однієї
таблиці) PostgreSQL дозволяє `INSERT`/`UPDATE` прямо через нього.
Важливий нюанс: рядок реально додається в базову таблицю
(`animals`), але колонки, яких немає в `SELECT` подання (тут
`status`), не отримують значення з умови `WHERE` подання; вони
залишаються `NULL` чи `DEFAULT`, а не автоматично "на обліку".

## 4. CREATE OR REPLACE VIEW: зміна без видалення

```sql
CREATE OR REPLACE VIEW animals_active AS
SELECT id, name, species, age, status
FROM animals
WHERE status = 'на обліку';
```

`CREATE OR REPLACE VIEW` дозволяє переписати запит подання (наприклад,
додати колонку) без попереднього `DROP VIEW`, що зручно, коли на
подання вже посилаються інші об'єкти бази: `DROP VIEW` у такому разі завершився б помилкою.

## 5. MATERIALIZED VIEW: знімок, а не живий запит

```sql
CREATE MATERIALIZED VIEW animals_active_mat AS
SELECT id, name, species, age
FROM animals
WHERE status = 'на обліку';
```

**Матеріалізоване подання** принципово відрізняється від звичайного:
воно ФІЗИЧНО зберігає результат запиту на диску на момент створення, а
не перевиконує його щоразу. Після `INSERT` нового рядка в
`animals` звичайне подання (`animals_active`) одразу показує його, а
матеріалізоване (`animals_active_mat`) **ні**, доки не виконати:

```sql
REFRESH MATERIALIZED VIEW animals_active_mat;
```

Лише після `REFRESH` матеріалізоване подання підхоплює нові дані:
кількість рядків у ньому змінюється саме в момент `REFRESH`, а не одразу
після `INSERT`.

## 6. Коли яке подання обрати

Звичайне `VIEW` підходить майже завжди: воно ніколи не "застаріває" й
не займає додаткового місця на диску, а ціна цього в тому, що запит виконується
заново щоразу. `MATERIALIZED VIEW` варто обирати, коли базовий запит
дорогий (складні агрегати чи `JOIN` по великій таблиці) і прийнятно
показувати трохи застарілі дані взамін швидкості, але тоді потрібно
самостійно (чи за розкладом) викликати `REFRESH`, інакше подання
"замерзне" на старому знімку.

## 7. DROP VIEW / DROP MATERIALIZED VIEW

```sql
DROP VIEW animals_active;
DROP MATERIALIZED VIEW animals_active_mat;
```

Видалення подання не торкається базової таблиці й жодних даних у ній:
зникає лише сам збережений запит (чи, для матеріалізованого, і його
знімок).

## 8. Подання як спосіб сховати складність

Далі працюємо з чистою копією таблиці `animals`: п'ять тварин (Мурка, Барсик, Рекс, Бім, Пушок) і таблиця `owners` із трьома власниками. Тварини Джек і Соня з попередніх розділів тут не враховані.

Головна практична користь від подання проявляється, коли запит стає громіздким. Нехай у клініці регулярно потрібен список тварин разом із прізвищем власника, причому тварин без власника теж потрібно показувати. Такий запит містить `LEFT JOIN` і заміну `NULL` через `COALESCE`. Замість того щоб щоразу переписувати його (і щоразу ризикувати помилитись), збережемо один раз:

```sql
CREATE VIEW animals_with_owners AS
SELECT a.id, a.name, a.species,
       COALESCE(o.last_name, 'без власника') AS owner
FROM animals a
LEFT JOIN owners o ON o.id = a.owner_id;
```

Тепер той, хто пише запити, може про `JOIN` не думати:

```sql
SELECT * FROM animals_with_owners ORDER BY id;
```

```text
 id |  name  | species |    owner
----+--------+---------+--------------
  1 | Мурка  | кіт     | Петренко
  2 | Барсик | кіт     | Петренко
  3 | Рекс   | собака  | Коваль
  4 | Бім    | собака  | Коваль
  5 | Пушок  | хом'як  | без власника
```

Подання допомагає й у двох інших ситуаціях. Воно **ховає зайві колонки**: якщо в `owners` є телефон чи адреса, подання без них дозволяє надати колезі доступ до списку тварин, не розкриваючи контактів. Воно також **захищає запити від перебудови таблиць**: якщо структуру таблиць пізніше змінять, достатньо виправити одне подання, а запити, що до нього звертаються, залишаться без змін.

## 9. Які подання можна змінювати і як це обмежити

У розділі 3 ми вставляли рядки через просте подання. Для подання, яке поєднує кілька таблиць, це не спрацює:

```sql
INSERT INTO animals_with_owners (name) VALUES ('X');
```

```text
ERROR:  cannot insert into view "animals_with_owners"
DETAIL:  Views that do not select from a single table or view are not automatically updatable.
```

PostgreSQL не може вгадати, у яку з двох таблиць і в які колонки записувати значення, тому такі подання призначені лише для читання.

Для простих подань діє інша пастка. Нехай подання відбирає тільки тих тварин, що на обліку, і через нього змінюють статус:

```sql
CREATE VIEW va AS
SELECT id, name, status FROM animals WHERE status = 'на обліку';

UPDATE va SET status = 'вибув' WHERE name = 'Бім';
```

Команда виконається без помилки, але рядок із Бімом після оновлення більше не відповідає умові `WHERE` подання й зникає з нього. Для користувача, який працює лише з поданням, це виглядає так, ніби запис пропав. Щоб заборонити такі «втечі», у кінці подання додають `WITH CHECK OPTION`:

```sql
CREATE VIEW cats AS
SELECT id, name, species, age, status
FROM animals
WHERE species = 'кіт'
WITH CHECK OPTION;

INSERT INTO cats (name, species, age, status) VALUES ('Васько', 'кіт', 2, 'на обліку');
-- INSERT 0 1: рядок відповідає умові, тож пройшов

INSERT INTO cats (name, species, age, status) VALUES ('Шарик', 'собака', 2, 'на обліку');
```

```text
ERROR:  new row violates check option for view "cats"
DETAIL:  Failing row contains (7, Шарик, собака, 2, на обліку, null).
```

З `WITH CHECK OPTION` подання не дозволяє записати через нього жоден рядок, який після запису не відповідав би умові подання. Так само відхиляється і `UPDATE cats SET species = 'собака'`.

## 10. Залежності між поданнями

Подання можуть спиратися одне на одне. Створимо подання поверх подання:

```sql
CREATE VIEW animals_active AS
SELECT id, name, species, age FROM animals WHERE status = 'на обліку';

CREATE VIEW young_active AS
SELECT * FROM animals_active WHERE age <= 2;
```

Тепер `animals_active` не можна видалити, поки існує `young_active`:

```sql
DROP VIEW animals_active;
```

```text
ERROR:  cannot drop view animals_active because other objects depend on it
DETAIL:  view young_active depends on view animals_active
HINT:  Use DROP ... CASCADE to drop the dependent objects too.
```

PostgreSQL захищає вас від випадкового руйнування ланцюжка. Команда `DROP VIEW animals_active CASCADE` видалить обидва подання, тож користуватись нею слід свідомо.

Обмеження є і в `CREATE OR REPLACE VIEW` (розділ 4). Нові колонки можна додавати лише **в кінець** списку, наприклад додати `status` після `age`. Спроба прибрати колонку завершується помилкою `cannot drop columns from view`, а спроба переставити колонки помилкою `cannot change name of view column ...`. Якщо структуру подання потрібно змінити радикально, його видаляють і створюють заново.

## 11. Матеріалізоване подання для підсумків

Матеріалізованими поданнями зазвичай зберігають не копію рядків таблиці, а **підсумки**, які дорого рахувати щоразу. Збережемо статистику по видах тварин:

```sql
CREATE MATERIALIZED VIEW species_stats AS
SELECT species, COUNT(*) AS cnt, ROUND(AVG(age), 1) AS avg_age
FROM animals
GROUP BY species;
```

Додамо нового кота віком 9 років і порівняємо:

```sql
INSERT INTO animals (name, species, age, status) VALUES ('Тигр', 'кіт', 9, 'на обліку');
SELECT * FROM species_stats WHERE species = 'кіт';
```

```text
 species | cnt | avg_age
---------+-----+---------
 кіт     |   3 |     3.3
```

Подання показує старий знімок: котів досі три, хоча в таблиці їх уже чотири. Після оновлення:

```sql
REFRESH MATERIALIZED VIEW species_stats;
```

```text
 species | cnt | avg_age
---------+-----+---------
 кіт     |   4 |     4.8
```

Звичайний `REFRESH` на час перебудови блокує читання подання. Варіант `REFRESH MATERIALIZED VIEW CONCURRENTLY` оновлює дані без блокування читачів, але вимагає, щоб у поданні був унікальний індекс. Без нього PostgreSQL повідомляє:

```text
ERROR:  cannot refresh materialized view "public.species_stats" concurrently
HINT:  Create a unique index with no WHERE clause on one or more columns of the materialized view.
```

Тому спершу створюють індекс, наприклад `CREATE UNIQUE INDEX ON species_stats(species);`, і лише після цього використовують `CONCURRENTLY`.

Список наявних подань можна переглянути в системних каталогах: `SELECT viewname FROM pg_views WHERE schemaname = 'public';` для звичайних і `SELECT matviewname FROM pg_matviews;` для матеріалізованих.

## 12. Запитання для самоперевірки

**Чи займає звичайне подання місце на диску під власні дані?**

Ні, воно зберігає лише текст запиту. Дані завжди читаються з базових таблиць.

**Чому `INSERT` у подання, що поєднує дві таблиці через `JOIN`, не виконується?**

PostgreSQL не знає, у яку таблицю й колонки записувати значення. Такі подання автоматично доступні лише для читання.

**Що додає `WITH CHECK OPTION` до простого подання?**

Забороняє вставляти чи змінювати рядки так, щоб вони перестали відповідати умові `WHERE` подання. Без нього змінений рядок просто зникає з подання.

**Матеріалізоване подання показує вчорашні дані. Як це виправити?**

Виконати `REFRESH MATERIALIZED VIEW`. Для регулярного оновлення без блокування читачів потрібен унікальний індекс і варіант `CONCURRENTLY`.

**Чому `DROP VIEW` на подання, яке використовує інше подання, завершується помилкою?**

Залежне подання перестало б працювати. Видалити обидва разом можна командою `DROP VIEW ... CASCADE`.

## Підсумок

- `CREATE VIEW` зберігає запит під іменем; фізичних даних не має;
  щоразу виконується заново й тому завжди показує актуальні дані
  базової таблиці.
- Просте подання (без `JOIN`/агрегатів) можна використовувати для
  `INSERT`/`UPDATE`; колонки поза `SELECT` подання при цьому
  отримують `NULL`/`DEFAULT`, а не значення з `WHERE`.
- `CREATE OR REPLACE VIEW` змінює запит подання без `DROP`.
- `MATERIALIZED VIEW` фізично зберігає знімок результату і не
  оновлюється сам, доки не виконати `REFRESH MATERIALIZED VIEW`.
- Звичайне подання є типовим вибором; матеріалізоване обирають, коли базовий
  запит дорогий і застарілість даних до наступного `REFRESH`
  прийнятна.
- Подання з `JOIN` призначені лише для читання; `WITH CHECK OPTION` не дозволяє записати через подання рядок, що не відповідає його `WHERE`.
- Матеріалізоване подання оновлюється командою `REFRESH`; `CONCURRENTLY` вимагає унікального індексу в поданні.

# Лекція 17. Згенеровані стовпці: VIRTUAL і STORED

*Ціна з ПДВ, прапорець "чи продано", кількість днів до закінчення
терміну — усе це похідні значення, які можна обчислити з уже наявних
колонок. Їх можна рахувати в кожному запиті окремо (`price * 1.2`), а
можна один раз оголосити прямо в структурі таблиці — тоді SQLite сам
рахує значення і сам гарантує, що воно завжди узгоджене з базовими
колонками.*

## 1. Проблема: похідне значення "вручну"

```sql
SELECT brand, price, price * 1.2 AS price_with_vat FROM cars;
```

Це працює, але формулу `price * 1.2` доведеться повторювати в КОЖНОМУ
запиті, де вона потрібна — і якщо хтось випадково збереже це значення
в окрему звичайну колонку через `UPDATE`, воно почне "розходитись" із
реальною ціною щоразу, коли `price` зміниться, а про синхронне
оновлення похідної колонки забудуть.

## 2. Згенерований стовпець (VIRTUAL) — рішення

```sql
ALTER TABLE cars ADD COLUMN price_with_vat REAL
    GENERATED ALWAYS AS (price * 1.2) VIRTUAL;

SELECT brand, price, price_with_vat FROM cars;
```

`GENERATED ALWAYS AS (вираз) VIRTUAL` оголошує колонку, значення якої
SQLite обчислює сам за формулою — щоразу, коли до неї звертаються
(`SELECT`, `WHERE`), а не зберігає постійно на диску. Перевірено:
`SELECT *` включає таку колонку з уже обчисленим значенням, як і
звичайну.

## 3. Згенеровану колонку неможливо змінити напряму

```sql
UPDATE cars SET price_with_vat = 1 WHERE id = 1;
```

```text
Error: cannot UPDATE generated column "price_with_vat"
```

Це і є гарантія узгодженості: ані `INSERT`, ані `UPDATE` не можуть
записати в згенеровану колонку довільне значення (перевірено — обидві
команди завершуються помилкою) — єдиний спосіб змінити її значення —
змінити колонку(и), від яких вона обчислюється:

```sql
UPDATE cars SET price = 800000 WHERE id = 1;
SELECT price, price_with_vat FROM cars WHERE id = 1;
-- price_with_vat перерахувалось АВТОМАТИЧНО, без жодної додаткової команди
```

## 4. VIRTUAL проти STORED — і важлива пастка

`VIRTUAL` (за умовчанням, якщо слово не вказано) обчислює значення
"на льоту" щоразу при зверненні — не займає місця на диску, але для
складної формули й частих запитів означає повторне обчислення щоразу.
`STORED` натомість фізично зберігає обчислене значення на диску (як
звичайну колонку) і перераховує його лише коли змінюються базові
колонки — швидший доступ при читанні, ціною місця на диску.

**Пастка, перевірена окремо:** `STORED` можна оголосити лише в
самому `CREATE TABLE` — додати `STORED`-колонку до вже існуючої
таблиці через `ALTER TABLE ADD COLUMN` **неможливо**:

```sql
ALTER TABLE cars ADD COLUMN is_sold INTEGER
    GENERATED ALWAYS AS (status = 'продано') STORED;
```

```text
Error: cannot add a STORED column
```

Оскільки таблиці цього курсу вже існують (створені в Практиці 1/4), на
практиці для вже наявних таблиць доступний лише `VIRTUAL` варіант через
`ALTER TABLE` — `STORED` можливий лише якби таблиця створювалась
заново з цією колонкою від початку.

## 5. WHERE за згенерованою колонкою — як за звичайною

```sql
SELECT brand FROM cars WHERE price_with_vat > 900000;
```

Згенеровану колонку можна використовувати в `WHERE` (і в `ORDER BY`,
`GROUP BY`) так само, як і будь-яку звичайну — SQLite підставляє
формулу автоматично.

## Підсумок

- `ALTER TABLE ... ADD COLUMN ім'я GENERATED ALWAYS AS (вираз) VIRTUAL`
  додає похідну колонку, яку SQLite рахує сам за формулою — без
  ризику розбіжності з базовими колонками.
- `INSERT`/`UPDATE` не можуть записати значення в згенеровану колонку
  напряму — єдиний спосіб її змінити — змінити колонки, від яких вона
  залежить.
- `VIRTUAL` рахує "на льоту" (без місця на диску), `STORED` зберігає
  обчислене значення фізично — але `STORED` можна оголосити лише в
  `CREATE TABLE`, не через `ALTER TABLE` до вже наявної таблиці.
- Згенеровану колонку можна вільно використовувати в `WHERE`,
  `ORDER BY`, `GROUP BY` — так само, як і звичайну.

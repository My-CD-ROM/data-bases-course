## Завдання 1. Похідне числове значення

До таблиці `subjects` додано VIRTUAL-стовпець:

```sql
ALTER TABLE subjects ADD COLUMN hours INTEGER GENERATED ALWAYS AS (credits * 30) VIRTUAL;
```

`SELECT id, title, credits, hours FROM subjects` показує, наприклад, `Вища математика | 5 | 150` і `Бази даних | 4 | 120`.

Бізнес-сенс: один кредит ECTS відповідає 30 годинам навантаження студента, тож `hours` показує загальний обсяг дисципліни в годинах. Формула бере лише колонку `credits` того самого рядка, тому годин не потрібно зберігати окремо й вони ніколи не розійдуться з кредитами.

## Завдання 2. Похідний логічний прапорець

У моїх таблицях немає текстової колонки статусу, тому я взяв числову колонку `grade` у `grades`:

```sql
ALTER TABLE grades ADD COLUMN is_excellent INTEGER GENERATED ALWAYS AS (grade >= 90) VIRTUAL;
```

Прапорець `is_excellent` дорівнює 1 для оцінок від 90 (id 1, 3, 7, 8) і 0 для решти, наприклад оцінка 85 дає 0. Запит `SELECT COUNT(*) FROM grades WHERE is_excellent <> (grade >= 90)` повертає 0, тобто розбіжностей між прапорцем і реальною оцінкою немає. Колонка `grade` оголошена `NOT NULL`, тому `NULL` у прапорці тут не виникає. Якби в колонці був `NULL`, порівняння дало б `NULL`, а не 0.

## Завдання 3. Свідома помилка прямого запису

```
UPDATE subjects SET hours = 100 WHERE id = 1;
Runtime error: cannot UPDATE generated column "hours" (1)
```

Те саме для другого стовпця: `Runtime error: cannot UPDATE generated column "is_excellent" (1)`. Власне повідомлення SQLite: `cannot UPDATE generated column "hours"`, а префікс `Runtime error:` і код `(1)` додає консоль.

## Завдання 4. Автоматичний перерахунок

Для дисципліни 3 («Бази даних») до `UPDATE` було `credits = 4`, `hours = 120`. Після `UPDATE subjects SET credits = 6 WHERE id = 3;` те саме `SELECT` показало `credits = 6`, `hours = 180`. Значення `hours` змінилося автоматично, синхронно з базовою колонкою, без жодної додаткової команди: SQLite обчислює VIRTUAL-стовпець за формулою щоразу, коли його читають. Після перевірки я повернув вихідне значення (`credits = 4`, `hours = 120`).

## Завдання 5. WHERE за згенерованим стовпцем

```sql
SELECT id, title, credits, hours FROM subjects WHERE hours >= 150 ORDER BY id;
```

Запит повертає дисципліни, обсяг яких не менший за 150 годин (5 і більше кредитів). Такий запис зручніший за `WHERE credits * 30 >= 150`, бо формула обчислення годин визначена в одному місці, у схемі таблиці, а не повторюється в кожному запиті. Умова читається як потрібний показник (`hours`), а не як арифметика. Якщо коефіцієнт зміниться, достатньо змінити визначення стовпця, і всі запити лишаться правильними. Також не можна помилитися у формулі в одному з запитів.

## Відповіді на контрольні питання

1. **Чому можна створити лише VIRTUAL, а не STORED, і що цьому заважає?** `ALTER TABLE ... ADD COLUMN` не дозволяє додати STORED-стовпець до наявної таблиці, SQLite відповідає `cannot add a STORED column`. STORED-стовпець фізично зберігається в рядках, а в наявної таблиці вони вже записані без нього. Такий стовпець можна створити лише разом із таблицею в `CREATE TABLE`.
2. **Що станеться при `DROP COLUMN` базової колонки?** SQLite відмовить, бо згенерований стовпець від неї залежить. На копії бази спроба `ALTER TABLE subjects DROP COLUMN credits` дала помилку `error in table subjects after drop column: no such column: credits`. Спершу треба видалити сам згенерований стовпець.
3. **Чому заборона прямого `INSERT` чи `UPDATE` у згенеровану колонку є перевагою?** Значення завжди відповідає формулі й не може розійтися з базовими колонками, бо його не можна випадково чи помилково перезаписати вручну. Для `INSERT` це теж так: `cannot INSERT into generated column "hours"`.

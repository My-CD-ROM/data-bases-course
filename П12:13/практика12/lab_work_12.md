## Завдання 1. ORDER BY за однією колонкою

Запит: `ORDER BY grade DESC`. Першим опинився рядок `id = 7`: студент 5, предмет 1 (Вища математика), дата 2026-05-20, оцінка **95**. Він перший, бо 95 — найбільше значення в колонці `grade`, а `DESC` ставить найбільші значення на початок. Останній рядок — оцінка 78.

## Завдання 2. ORDER BY за кількома колонками

Запит: `ORDER BY subject_id ASC, grade DESC`. Рядки згруповано за предметом (1, 2, 3), а всередині кожного предмета оцінки йдуть від найвищої до найнижчої (для предмета 1: 95, 90, 84, 78). Друга колонка працює як «тай-брейкер»: вона визначає порядок рядків, які мають однакове значення першої колонки. Без неї порядок усередині одного предмета був би не визначений (зазвичай за порядком зберігання).

## Завдання 3. Топ-N: ORDER BY + LIMIT

Запит: `ORDER BY grade DESC LIMIT 3` повертає оцінки 95, 92, 91 (id 7, 3, 8).

Порядок команд такий, бо `ORDER BY` спершу сортує весь результат, а `LIMIT` потім відрізає перші N рядків уже впорядкованого набору. Для контролю виконано `LIMIT 3` без `ORDER BY`: він повернув рядки з id 1, 2, 3 (оцінки 90, 85, 92), тобто просто перші три рядки в порядку зберігання. Оцінок 95 і 91 серед них немає. Без `ORDER BY` порядок рядків не гарантований, тому «топ-3» перетворюється на випадкові три рядки.

## Завдання 4. DISTINCT і BETWEEN/IN

**(а)** `SELECT DISTINCT group_name FROM university` повернув **4** унікальні групи (ІТ-22, ІТ-23, ІТ-21, ІТ-25) із 7 студентів. Це підтверджує і `COUNT(DISTINCT group_name)` = 4.

**(б)** Запит `WHERE grade BETWEEN 85 AND 95` повернув 7 рядків (оцінки 85, 88, 89, 90, 91, 92, 95). Межі включені: рядки з оцінками 85 і 95 у результаті є. Я обрав `BETWEEN`, бо умова описує безперервний числовий діапазон: це коротше й читабельніше за `grade >= 85 AND grade <= 95`, а `IN` довелося б перелічувати кожне значення від 85 до 95. Для дискретного списку значень доречніший `IN`: додатковий запит `credits IN (3, 6)` повернув 2 предмети (Програмне забезпечення і Операційні системи).

## Завдання 5. LIKE і кирилиця

- `last_name LIKE 'Ко%'` знайшов **2** рядки: Ковальчук, Коваленко.
- `last_name LIKE 'ко%'` знайшов **0** рядків.

Кількість знайдених рядків не збігається. Причина: у SQLite оператор `LIKE` нечутливий до регістру лише для ASCII-символів (латиниці), а для кирилиці порівнює літери з урахуванням регістру. Контрольні запити це підтверджують: `'Abc' LIKE 'abc%'` дає 1, а `'Ко' LIKE 'ко%'` дає 0. Функція `lower()` теж не змінює кирилицю: `lower('КОВАЛЬЧУК')` лишився `КОВАЛЬЧУК`. Це поведінка стандартної збірки SQLite без розширення ICU.

## Відповіді на контрольні питання

**1. Чому `ORDER BY` перед `LIMIT`, і що буде без `ORDER BY`?**
`ORDER BY` формує впорядкований результат, а `LIMIT` бере з нього перші N рядків. Якщо `ORDER BY` прибрати, SQLite віддасть будь-які три рядки в порядку зберігання: у цій роботі це були id 1, 2, 3 з оцінками 90, 85, 92 замість 95, 92, 91.

**2. Коли `IN`, а коли `BETWEEN`?**
`BETWEEN` — для неперервного діапазону значень із включеними межами (оцінки від 85 до 95, дати від і до). `IN` — для скінченного списку окремих значень (кредити 3 або 6, види «кіт» і «миша»). `BETWEEN` замінює `>= AND <=`, `IN` замінює ланцюжок `OR`; обидва варіанти коротші й менш схильні до помилок.

**3. Чому висновок про регістр і кирилицю важливий для курсу?**
Майже всі текстові дані (прізвища, назви, групи) українською. Пошук `LIKE 'ко%'` по прізвищах мовчки поверне 0 рядків без жодної помилки, і звіт буде хибним. Тому в шаблоні треба точно відтворювати регістр, а для нечутливого до регістру пошуку використовувати нормалізовану колонку, ICU-розширення або обробку на боці програми.

    Лекція 14. Згенеровані стовпці: VIRTUAL і STORED¶

    Ціна з ПДВ, сума позиції, прапорець «продано», кількість днів між двома датами – усе це похідні значення: їх не вводять вручну, а обчислюють з інших колонок того самого рядка. Їх можна рахувати в кожному запиті окремо, а можна один раз оголосити прямо в структурі таблиці: тоді SQLite сам рахує значення і сам гарантує, що воно завжди узгоджене з даними.

    Приклади – на таблиці автосалону cars: id, brand, price (ціна без ПДВ), status («в наявності» або «продано»), arrival_date (дата надходження), sold_date (дата продажу). Помилки й числа в лекції отримано в SQLite 3.54.

    Частина 1. Похідне значення: вручну чи один раз¶

    1. Проблема: формула в кожному запиті¶

    SELECT brand, price, price * 1.2 AS price_with_vat FROM cars;

    Запит правильний, але ціна з ПДВ потрібна в каталозі, кошику, рахунку, звіті – і формулу price * 1.2 доведеться писати в кожному з цих запитів. Змінилася ставка податку – виправляти кожне місце.

    Зберегти ціну з ПДВ в окрему звичайну колонку один раз через UPDATE теж не вихід: щойно хтось змінить price, колонка з ПДВ залишиться зі старим значенням, якщо ніхто не згадає оновити і її. Значення розійдуться.

    2. Згенерований стовпець (VIRTUAL)¶

    Згенерований стовпець – колонка, значення якої SQLite обчислює сам за формулою з інших колонок того самого рядка.

    ALTER TABLE cars ADD COLUMN price_with_vat REAL
    GENERATED ALWAYS AS (price * 1.2) VIRTUAL;

SELECT brand, price, price_with_vat FROM cars;

    VIRTUAL означає, що значення не зберігається на диску, а обчислюється щоразу, коли до колонки звертаються. Для запитів це звичайна колонка: її видно і в SELECT *, і в переліку колонок.

    ALWAYS – «завжди»: на відміну від DEFAULT, яке підставляє значення один раз під час INSERT і далі дозволяє його змінювати, згенерований стовпець завжди дорівнює результату формули.

    Довідка: команда ALTER TABLE¶

    Досі таблицю ми або створювали (CREATE TABLE), або видаляли (DROP TABLE). ALTER TABLE («змінити таблицю») змінює структуру вже наявної таблиці: додає, видаляє чи перейменовує колонки, додає обмеження. Рядки таблиці при цьому лишаються на місці, тож нічого не треба створювати наново й переносити. Загальна форма – назва таблиці і одна дія:

    ALTER TABLE таблиця дія;

    Що вміє ALTER TABLE у SQLite і в PostgreSQL (з PostgreSQL ми працюватимемо в Модулі 4):

    Дія Приклад SQLite PostgreSQL
    ADD COLUMN – додати колонку ALTER TABLE cars ADD COLUMN color TEXT; так так
    DROP COLUMN – видалити колонку ALTER TABLE cars DROP COLUMN color; так так
    RENAME COLUMN ... TO – перейменувати колонку ALTER TABLE cars RENAME COLUMN brand TO make; так так
    RENAME TO – перейменувати таблицю ALTER TABLE cars RENAME TO autos; так так
    ALTER COLUMN ... SET NOT NULL / DROP NOT NULL – заборонити чи дозволити NULL ALTER TABLE cars ALTER COLUMN price SET NOT NULL; з версії 3.53 так
    ADD CONSTRAINT – додати обмеження ALTER TABLE cars ADD CONSTRAINT price_positive CHECK (price > 0); з версії 3.53, лише CHECK так: CHECK, UNIQUE, PRIMARY KEY, FOREIGN KEY
    DROP CONSTRAINT – видалити обмеження ALTER TABLE cars DROP CONSTRAINT price_positive; з версії 3.53, лише CHECK так
    RENAME CONSTRAINT ... TO – перейменувати обмеження ALTER TABLE cars RENAME CONSTRAINT price_positive TO price_gt_0; ні так
    ALTER COLUMN ... TYPE – змінити тип колонки ALTER TABLE cars ALTER COLUMN price TYPE INTEGER; ні так
    ALTER COLUMN ... SET DEFAULT / DROP DEFAULT – задати чи прибрати значення за умовчанням ALTER TABLE cars ALTER COLUMN status SET DEFAULT 'в наявності'; ні так
    SET SCHEMA – перенести таблицю в іншу схему (Лекція 15) ALTER TABLE cars SET SCHEMA archive; ні так
    OWNER TO – змінити власника таблиці ALTER TABLE cars OWNER TO manager; ні так
    ENABLE TRIGGER / DISABLE TRIGGER – увімкнути чи вимкнути тригер (Лекція 18) ALTER TABLE cars DISABLE TRIGGER trg_name; ні так

    Обмеження ADD COLUMN у SQLite. Нова колонка завжди стає останньою. Крім того, до таблиці, де вже є рядки, SQLite не дасть додати колонку, для якої не зможе одразу заповнити ці рядки:

    • з PRIMARY KEY чи UNIQUE: Cannot add a UNIQUE column;
    • з NOT NULL без значення за умовчанням: Cannot add a NOT NULL column with default value NULL (наявні рядки отримали б NULL), а з NOT NULL DEFAULT 'в наявності' – можна;
    • зі значенням за умовчанням, яке не є сталим, наприклад DEFAULT CURRENT_TIMESTAMP: Cannot add a column with non-constant default;
    • згенерований стовпець – лише VIRTUAL, не STORED (розділ 9).

    Обмеження DROP COLUMN у SQLite. Колонку не можна видалити, якщо вона є первинним ключем, має UNIQUE чи індекс або її використовує щось інше в схемі: формула згенерованого стовпця (розділ 12), обмеження CHECK, зовнішній ключ, подання чи тригер. Спершу треба прибрати те, що на неї посилається.

    Версія SQLite має значення. Команди SET NOT NULL, DROP NOT NULL, ADD CONSTRAINT і DROP CONSTRAINT з’явилися лише в SQLite 3.53 (квітень 2026). Перевірити свою версію можна запитом SELECT sqlite_version();. У DB Browser for SQLite 3.13 вбудовано SQLite 3.46, тож там цих команд немає. У старішій версії обмеження додають через перебудову таблиці, як у Практиці 5: нова таблиця з потрібними обмеженнями, копіювання рядків, DROP TABLE старої і RENAME TO. Якщо наявні рядки порушують нове обмеження (наприклад, у колонці вже є NULL, а ми додаємо NOT NULL), команда завершується помилкою constraint failed і таблиця не змінюється.

    Що інакше в PostgreSQL. Кілька дій можна виконати однією командою через кому, а IF EXISTS / IF NOT EXISTS дозволяють не отримувати помилку, якщо колонки немає чи вона вже є:

    ALTER TABLE cars
    ADD COLUMN IF NOT EXISTS color TEXT,
    ALTER COLUMN status SET DEFAULT 'в наявності';

    Якщо PostgreSQL не може сам перетворити значення на новий тип, він просить підказати, як саме, через USING:

    ERROR:  column "status" cannot be cast automatically to type integer
HINT:  You might need to specify "USING status::integer".

    Як працювати з ALTER TABLE.

    1. Подивіться структуру до й після зміни: .schema cars або PRAGMA table_info(cars); у SQLite, \d cars у PostgreSQL.
    2. Таблицю з важливими даними спершу змінюйте на копії бази.
    3. ALTER TABLE працює в транзакції: після BEGIN; команду ALTER TABLE скасовує ROLLBACK; разом зі зміною структури, і в SQLite, і в PostgreSQL.

    3. Згенеровані стовпці в CREATE TABLE¶

    Згенеровані стовпці можна оголосити й під час створення таблиці:

    CREATE TABLE products (
    id    INTEGER PRIMARY KEY,
    name  TEXT NOT NULL,
    price REAL NOT NULL,
    qty   INTEGER NOT NULL,
    total REAL GENERATED ALWAYS AS (price * qty) STORED,
    label TEXT AS (name || ' (' || qty || ' шт.)')
);

INSERT INTO products (name, price, qty) VALUES ('Зошит', 25.5, 10), ('Ручка', 12, 30);
SELECT * FROM products;

    id  name   price  qty  total  label
1   Зошит  25.5   10   255.0  Зошит (10 шт.)
2   Ручка  12.0   30   360.0  Ручка (30 шт.)
    • total оголошено як STORED: значення обчислюється під час запису рядка і зберігається на диску (розділ 8). STORED можна оголосити лише в CREATE TABLE (розділ 9).
    • label склеює назву і кількість; || у SQLite – склеювання рядків.
    • Коротка форма AS (формула) означає те саме, що GENERATED ALWAYS AS (формула). Якщо не вказати ні VIRTUAL, ні STORED, стовпець VIRTUAL.

    Частина 2. Гарантія узгодженості¶

    4. Згенерований стовпець неможливо змінити напряму¶

    UPDATE cars SET price_with_vat = 1 WHERE id = 1;

    Parse error: cannot UPDATE generated column "price_with_vat"

    Так само INSERT зі значенням для згенерованого стовпця завершується помилкою cannot INSERT into generated column. Записати в згенерований стовпець щось своє неможливо в принципі – і саме це гарантує, що значення завжди відповідає формулі.

    У INSERT без переліку колонок згенеровані стовпці не враховуються: для products треба передати чотири значення (id, name, price, qty), а не шість. Інакше – table products has 4 columns but 6 values were supplied.

    5. Автоматичний перерахунок і логічний прапорець¶

    UPDATE cars SET price = 800000 WHERE id = 1;
SELECT price, price_with_vat FROM cars WHERE id = 1;
-- 800000.0 | 960000.0

    Ціна з ПДВ змінилася без жодної додаткової команди. VIRTUAL-стовпець обчислюється під час кожного читання, STORED-стовпець SQLite сам перераховує під час UPDATE базових колонок. Змінити згенерований стовпець можна лише одним способом – змінити колонки, з яких він обчислюється, тож «забути оновити» неможливо: за узгодженість відповідає СУБД.

    Формула може бути й порівнянням – тоді вийде логічний прапорець:

    ALTER TABLE cars ADD COLUMN is_sold INTEGER
    GENERATED ALWAYS AS (status = 'продано') VIRTUAL;

SELECT brand, status, is_sold FROM cars;

    Порівняння в SQLite дає число: 1 – істина, 0 – хибність. Якщо status дорівнює NULL, прапорець теж NULL: порівняння з NULL ні істинне, ні хибне. Якщо потрібен саме 0, формулу пишуть як coalesce(status = 'продано', 0) – функція coalesce повертає перше значення, що не є NULL.

    Частина 3. Що можна писати у формулі¶

    6. Вимоги до формули¶

    • Лише той самий рядок. Формула може використовувати інші колонки цієї таблиці, константи і вбудовані функції. Звертатися до іншої таблиці й писати підзапити не можна (subqueries prohibited in generated columns).
    • Детермінованість. Детермінована формула для тих самих вхідних даних завжди дає той самий результат. random() чи CURRENT_TIMESTAMP заборонені:
    CREATE TABLE t (a INTEGER, b TEXT GENERATED ALWAYS AS (CURRENT_TIMESTAMP) VIRTUAL);

    Parse error: non-deterministic functions prohibited in generated columns

    Причина: значення VIRTUAL обчислюється щоразу заново, а STORED – під час запису. Якби формула залежала від часу чи випадку, той самий рядок мав би різні значення, а індекс на такому стовпці став би неправильним. - Посилання на інший згенерований стовпець дозволене:

    CREATE TABLE prices (price REAL, net REAL AS (price * 0.9), gross REAL AS (net * 1.2));
INSERT INTO prices (price) VALUES (100);
SELECT * FROM prices;   -- 100.0 | 90.0 | 108.0
    • Згенерований стовпець не може бути первинним ключем і не може мати DEFAULT.

    7. Пастка: поточна дата у формулі¶

    Здається природним порахувати, скільки днів автомобіль стоїть у салоні:

    ALTER TABLE cars ADD COLUMN days_in_stock INTEGER
    GENERATED ALWAYS AS (julianday('now') - julianday(arrival_date)) VIRTUAL;

    Команда виконується без помилки: функція julianday сама по собі детермінована (для тієї самої дати дає те саме число), а недетермінованою її робить лише аргумент 'now', який SQLite бачить тільки під час обчислення. Помилка з’являється пізніше:

    SELECT * FROM cars;

    Runtime error: non-deterministic use of julianday() in a generated column

    Після цього SELECT *, будь-який INSERT і UPDATE на cars завершуються помилкою; працюють лише запити, що не чіпають цей стовпець. Лікування – видалити стовпець:

    ALTER TABLE cars DROP COLUMN days_in_stock;

    Висновки:

    • кожен новий згенерований стовпець одразу перевіряйте запитом SELECT *;
    • постійне – у стовпець, поточне – у запит. Різниця двох дат із таблиці детермінована: julianday(sold_date) - julianday(arrival_date) – скільки днів автомобіль простояв до продажу (для непроданих sold_date порожня, тож і результат NULL). Просто відняти дати-рядки (sold_date - arrival_date) не можна: SQLite відніме лише роки й дасть 0.

    Частина 4. VIRTUAL проти STORED¶

    8. Два способи зберігати похідне значення¶

    VIRTUAL (за замовчуванням) STORED
    Коли обчислюється під час читання, при кожному зверненні під час запису (INSERT, UPDATE базових колонок)
    Місце на диску не займає займає, як звичайна колонка
    Читання обчислює формулу щоразу бере готове значення
    Аналогія ціна з ПДВ на калькуляторі, коли покупець питає надрукований цінник

    На таблиці замовлень з мільйона рядків, де total = round(price * qty * (1 - discount) * 1.2, 2):

    VIRTUAL STORED
    розмір файлу бази 25 МБ 33 МБ
    вставка 1 000 000 рядків 0,71 с 0,73 с
    SELECT sum(total) 0,29 с 0,06 с

    STORED додав третину місця, читання суми стало вп’ятеро швидшим, а вставка майже не змінилася. Для простої формули (price * 1.2) різниця в читанні майже зникає: 0,063 с проти 0,056 с, а зайве місце STORED займає так само.

    9. Пастка: STORED лише в CREATE TABLE¶

    ALTER TABLE cars ADD COLUMN is_sold_stored INTEGER
    GENERATED ALWAYS AS (status = 'продано') STORED;

    Runtime error: cannot add a STORED column

    STORED-стовпець можна оголосити лише в CREATE TABLE. До наявної таблиці через ALTER TABLE можна додати тільки VIRTUAL: команда ALTER TABLE ADD COLUMN у SQLite лише змінює опис таблиці й не переписує наявні рядки, а для STORED довелося б обчислити й записати значення в кожен рядок.

    Таблиці ваших варіантів уже створені (Практики 1 і 4), тож на практиці до них можна додати лише VIRTUAL-стовпці. STORED – тільки коли таблицю створюють заново з новою структурою.

    10. Як вибрати¶

    • VIRTUAL – вибір за замовчуванням: формула проста, значення читають рідко, таблиця вже існує.
    • STORED – формула дорога, значення читають набагато частіше, ніж змінюють, і таблицю створюємо заново.
    • VIRTUAL з індексом (розділ 11) – значення зберігаються в індексі, тож пошук і сортування швидкі, а таблиця не росте (хоча індекс теж займає місце).

    Частина 5. Згенерований стовпець у запитах¶

    11. WHERE, ORDER BY, GROUP BY й індекс¶

    SELECT brand, price_with_vat FROM cars
WHERE price_with_vat > 900000 ORDER BY price_with_vat DESC;

SELECT is_sold, COUNT(*) FROM cars GROUP BY is_sold;

    У запитах згенерований стовпець поводиться як звичайний. Формула живе в одному місці: змінилася ставка – змінюємо визначення стовпця, запити ті самі.

    Згенерований стовпець можна проіндексувати (див. Лекцію 13):

    EXPLAIN QUERY PLAN SELECT brand FROM cars WHERE price_with_vat > 900000;
-- SCAN cars

CREATE INDEX idx_cars_vat ON cars(price_with_vat);
-- той самий запит:
-- SEARCH cars USING INDEX idx_cars_vat (price_with_vat>?)

    Для VIRTUAL-стовпця значення в таблиці не зберігаються, а в індексі – так: SQLite обчислює їх під час запису рядка. Важливо: умова WHERE price * 1.2 > 900000 навіть за наявності цього індексу дає SCAN – SQLite не впізнає у формулі згенерований стовпець. Індекс працює лише тоді, коли в умові стоїть ім’я стовпця.

    12. Згенеровані стовпці в структурі таблиці¶

    PRAGMA table_xinfo(cars);

    PRAGMA table_info згенеровані стовпці пропускає, а table_xinfo показує, з додатковою колонкою hidden: 0 – звичайний стовпець, 2 – VIRTUAL, 3 – STORED. Формулу видно в .schema cars у консолі sqlite3 або на вкладці «Структура бази даних» у DB Browser for SQLite.

    Базову колонку, від якої залежить згенерований стовпець, видалити не можна:

    ALTER TABLE cars DROP COLUMN price;

    Runtime error: error in table cars after drop column: no such column: price

    Спершу видаляють згенерований стовпець, потім базову колонку. (Не повторюйте DROP COLUMN на своїй базі без потреби: якщо від колонки нічого не залежить, SQLite справді видалить її разом з даними.)

    13. Згенерований стовпець чи подання¶

    У Лекції 16 буде розглянуто подання (VIEW), яке теж дозволяє зберегти обчислення під іменем. Різниця в тому, де живе формула. Згенерований стовпець належить таблиці й доступний у кожному запиті до неї, а подання – окремий об’єкт, у якому можна поєднати кілька таблиць. Для похідного значення, що залежить лише від одного рядка, достатньо згенерованого стовпця; для складніших вибірок із JOIN потрібне подання.

    14. Запитання для самоперевірки¶

    Чим GENERATED ALWAYS відрізняється від DEFAULT?

    DEFAULT підставляє значення один раз під час INSERT, далі його можна змінити. Згенерований стовпець завжди дорівнює результату формули, і змінити його окремо неможливо.

    У таблиці змінили price. Чи потрібно вручну оновлювати price_with_vat?

    Ні, SQLite перераховує згенеровані стовпці сам.

    Що покаже is_sold (формула status = 'продано'), якщо status дорівнює NULL?

    NULL. Щоб отримати 0, використовують coalesce(status = 'продано', 0).

    Чому стовпець з julianday('now') додається без помилки, а потім ламає таблицю?

    julianday сама по собі детермінована; недетермінованою її робить аргумент 'now', який SQLite бачить лише під час обчислення. Тому помилка з’являється на першому SELECT *, INSERT чи UPDATE.

    Чим STORED відрізняється від VIRTUAL з погляду місця і швидкості читання?

    STORED займає місце на диску й читається швидше, бо значення вже обчислене. VIRTUAL місця не займає, але обчислюється під час кожного читання. Для простих формул різниця в швидкості майже непомітна.

    Чи можна додати STORED-стовпець до наявної таблиці командою ALTER TABLE?

    Ні – cannot add a STORED column. Для наявних таблиць доступний лише VIRTUAL.

    Індекс на price_with_vat є. Чи скористається ним умова WHERE price * 1.2 > 900000?

    Ні, буде SCAN: індекс працює лише з іменем згенерованого стовпця.

    Що станеться, якщо спробувати видалити базову колонку price?

    SQLite відмовить, бо від неї залежить price_with_vat. Спершу видаляють згенерований стовпець.

    Підсумок¶

    • Згенерований стовпець – колонка, яку SQLite обчислює сам за формулою з колонок того самого рядка: GENERATED ALWAYS AS (формула) або коротко AS (формула).
    • Записати в згенерований стовпець напряму неможливо; значення змінюється лише разом із базовими колонками, автоматично.
    • Формула використовує лише значення того самого рядка й має бути детермінованою (без random(), CURRENT_TIMESTAMP, 'now'). Недетермінована дата ламає таблицю не під час ALTER TABLE, а під час першого ж запиту.
    • VIRTUAL обчислює значення під час читання й не займає місця; STORED – під час запису, займає місце, зате читається швидше. За замовчуванням стовпець VIRTUAL.
    • STORED можна оголосити лише в CREATE TABLE; до наявної таблиці через ALTER TABLE додається тільки VIRTUAL.
    • Згенерований стовпець працює в WHERE, ORDER BY, GROUP BY, його можна проіндексувати; індекс спрацює, якщо в умові стоїть ім’я стовпця, а не формула.
    • PRAGMA table_xinfo показує згенеровані стовпці; базову колонку, від якої вони залежать, видалити не можна.

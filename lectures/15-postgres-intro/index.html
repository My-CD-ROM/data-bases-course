    Лекція 15. Перехід до PostgreSQL. Використання PgAdmin¶

    Модуль 4 переносить ту саму базу даних (ваш власний варіант, уже з трьома пов’язаними таблицями) на іншу СУБД – PostgreSQL. SQLite чудово підійшла для навчання основ SQL: файл, ніяких серверів, нуль налаштувань. Але функцій, процедур і тригерів (теми лекцій 17–18 і практик 21–24) у SQLite немає зовсім, а PostgreSQL – це СУБД, на якій працюють справжні сайти й системи підприємств. SQL лишається SQL: змінюється сама СУБД і кілька правил, про які треба пам’ятати, коли переносиш уже готову схему.

    1. SQLite проти PostgreSQL: не діалект, а архітектура¶

    SQLite – це бібліотека всередині програми: уся база – один файл на диску, скопіював файл – переніс базу. PostgreSQL – клієнт-серверна СУБД: окрема програма-сервер працює постійно, а клієнти (pgAdmin, сайт, мобільний застосунок) під’єднуються до неї за адресою, портом (типово 5432), іменем користувача й паролем і надсилають SQL-запити.

    Клієнт-серверна СУБД – СУБД, у якій дані зберігає й обробляє окрема програма-сервер, а користувачі та програми працюють з даними через клієнти, які надсилають серверу запити.

    SQLite на час запису блокує файл бази, тож записувати одночасно може лише одна транзакція (згадайте database is locked з лекції 12, розділ 10). Сервер PostgreSQL сам керує всіма з’єднаннями й дозволяє різним користувачам одночасно змінювати різні рядки. Окремого файлу бази, який можна здати, у PostgreSQL немає: дані зберігає сервер. Тому з практики 19 здається SQL-скрипт, з якого базу можна відтворити.

    Замість одного файлу PostgreSQL організовує дані в ієрархію з чотирьох рівнів: сервер, база даних, схема, таблиця. Один сервер тримає багато баз. Схема – іменована група таблиць та інших об’єктів у межах однієї бази; схема public створюється автоматично, і всі таблиці потрапляють туди, якщо не вказати іншу. У SQLite сервера немає, база – це файл, а окремого рівня схем немає.

    2. PgAdmin – інструмент цього модуля¶

    pgAdmin – графічний клієнт для PostgreSQL, аналог DB Browser for SQLite з попередніх модулів. У дереві зліва послідовно розгортаються Servers, PostgreSQL 18, Databases, ваша база, Schemas, public і Tables: саме тут з’являться таблиці вашого варіанта. Нову базу створюють правим кліком на Databases: Create, Database.

    Вкладка Query Tool (правий клік на своїй базі, Query Tool) – аналог Execute SQL у DB Browser: сюди пишеться будь-який SQL цієї лекції. Запуск – F5 або кнопка Execute, результат – на вкладці Data Output.

    Таблицю створено, а в дереві її немає

    Дерево не оновлюється саме: правий клік на Tables, Refresh. Якщо й після цього таблиці немає, Query Tool було відкрито на іншій базі (наприклад, на службовій postgres), і таблиця створилася там. Назву бази видно в заголовку вкладки Query Tool.

    3. Перша синтаксична відмінність: автоінкремент первинного ключа¶

    -- як у SQLite (лекція 5)
CREATE TABLE owners (
    id INTEGER PRIMARY KEY,
    last_name TEXT NOT NULL,
    first_name TEXT NOT NULL,
    phone TEXT
);
INSERT INTO owners (last_name, first_name) VALUES ('Петренко', 'Ольга');

    ERROR:  null value in column "id" of relation "owners" violates not-null constraint
DETAIL:  Failing row contains (null, Петренко, Ольга, null).

    У SQLite INTEGER PRIMARY KEY – це інша назва rowid, тому номер з’являвся сам (лекція 5). У PostgreSQL rowid немає: INTEGER PRIMARY KEY тут – просто ціле число, яке не може бути NULL, і рядки ніхто не нумерує. Автоінкремент треба оголосити явно:

    CREATE TABLE owners (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    last_name TEXT NOT NULL,
    first_name TEXT NOT NULL,
    phone TEXT
);
INSERT INTO owners (last_name, first_name)
VALUES ('Петренко', 'Ольга'), ('Коваль', 'Андрій');   -- id 1 і 2

    Номери видає послідовність (sequence) – окремий об’єкт бази даних, лічильник, який щоразу видає наступне число. Колонка IDENTITY бере з неї номер для кожного нового рядка.

    Слово ALWAYS означає «номер завжди видає база», тож явний id у звичайному INSERT PostgreSQL відхиляє:

    INSERT INTO owners (id, last_name, first_name) VALUES (10, 'Ткач', 'Ірина');

    ERROR:  cannot insert a non-DEFAULT value into column "id"
DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.

    Якщо свій номер справді потрібен (наприклад, під час перенесення старих даних), це кажуть явно: INSERT INTO owners (id, ...) OVERRIDING SYSTEM VALUE VALUES (10, ...). Лічильник про такий номер не дізнається: коли він сам дійде до 10, INSERT впаде з duplicate key, тож після таких вставок теж потрібен setval (розділ 8).

    У чужому коді часто трапляється старіший спосіб – id SERIAL PRIMARY KEY. Обидва нумерують рядки автоматично, різниця – у явному id:

    SERIAL GENERATED ALWAYS AS IDENTITY
    Що це скорочення: INTEGER + послідовність + DEFAULT nextval(...) стандарт SQL, у PostgreSQL з версії 10
    Явний id у INSERT приймає мовчки, лічильник про нього не знає помилка; свідомо – OVERRIDING SYSTEM VALUE
    Наслідок наступний INSERT без id може отримати вже зайнятий номер (duplicate key) випадково зламати нумерацію важче

    Тому для нового коду курс використовує GENERATED ALWAYS AS IDENTITY.

    4. Друга відмінність: строга типізація¶

    INSERT INTO animals (name, species, age, owner_id) VALUES ('Рекс', 'собака', 'сім', 2);

    ERROR:  invalid input syntax for type integer: "сім"

    SQLite має гнучку «типову афінність»: тип колонки – радше побажання, і текст спокійно ляже в колонку INTEGER (практика 17). PostgreSQL – строго типізована СУБД: значення, яке не можна прочитати як число, у колонку INTEGER не потрапить, помилка з’явиться одразу.

    Але строгість не означає, що PostgreSQL відкидає кожне неточне значення: рядок '7' він перетворить на число 7, а дробове число 1.6 в INSERT мовчки округлить до 2. А з CSV значення приходить як текст, і текст '1.6' у колонку INTEGER не пройде: імпорт зупиниться з помилкою invalid input syntax for type integer: "1.6". Тому перед перенесенням перевірте, чи немає дробів у ваших цілих колонках.

    5. Третя відмінність: FOREIGN KEY завжди активний¶

    INSERT INTO animals (name, species, age, owner_id) VALUES ('Мурка', 'кіт', 3, 999);

    ERROR:  insert or update on table "animals" violates foreign key constraint "animals_owner_id_fkey"
DETAIL:  Key (owner_id)=(999) is not present in table "owners".

    У SQLite перевірку зовнішніх ключів треба вмикати командою PRAGMA foreign_keys = ON; на кожному з’єднанні (лекція 5; у DB Browser для цього є прапорець Foreign Keys на вкладці Edit Pragmas). У PostgreSQL перевірку FOREIGN KEY не потрібно вмикати окремо – вона активна завжди. Звідси порядок перенесення: спершу таблиці-виміри, на які посилаються (тут owners), потім фактова таблиця (animals), інакше кожен її рядок буде відхилено. І в зворотний бік: власника, у якого є тварини, не видалити – DELETE FROM owners WHERE id = 2 закінчиться помилкою з DETAIL: Key (id)=(2) is still referenced from table "animals".

    6. Четверта відмінність: реальний тип BOOLEAN¶

    ALTER TABLE owners ADD COLUMN is_vip BOOLEAN NOT NULL DEFAULT FALSE;
UPDATE owners SET is_vip = TRUE WHERE id = 1;
SELECT last_name FROM owners WHERE is_vip;

    У SQLite логічне значення зберігають як INTEGER (0/1), як прапорець is_sold з лекції 14. PostgreSQL має справжній тип BOOLEAN зі значеннями TRUE/FALSE, і число в нього не запишеш:

    UPDATE owners SET is_vip = 1 WHERE id = 1;

    ERROR:  column "is_vip" is of type boolean but expression is of type integer

    Так само не спрацює й умова WHERE is_vip = 1 (operator does not exist: boolean = integer).

    Під час імпорту з CSV це не заважає: текст 1 і 0 у файлі PostgreSQL читає як true і false, тож прапорці з SQLite можна одразу переносити в колонку BOOLEAN. У запитах, які пишете вручну, – лише TRUE і FALSE.

    7. П’ята відмінність: регістр ідентифікаторів – гарна новина для цього курсу¶

    CREATE TABLE "Vets" (id INTEGER, name TEXT);
SELECT * FROM Vets;

    ERROR:  relation "vets" does not exist

    PostgreSQL переводить назви таблиць і колонок без лапок у нижній регістр: Vets без лапок він шукає як vets, а таблицю "Vets" у лапках створив з великою літерою. Тобто "Vets" і vets – дві різні назви. Оскільки курс із самого початку використовує англійський snake_case малими літерами, жодна вже написана назва таблиці чи колонки не постраждає при перенесенні – пастка стосується лише назв з великими літерами в лапках.

    8. Найпідступніша пастка: перенесення даних зі старими id «збиває» автолічильник¶

    Дані переносять через CSV: експорт у DB Browser for SQLite (меню File, Export, Table(s) as CSV file, з рядком заголовків) і імпорт у pgAdmin (правий клік на таблиці, Import/Export Data, режим Import, формат csv, на вкладці Options – Header). pgAdmin виконує для цього команду COPY, яка, на відміну від звичайного INSERT, записує id з файлу навіть у колонку GENERATED ALWAYS AS IDENTITY. Старі номери мають переїхати разом з рядками: на них посилаються зовнішні ключі.

    Порядок колонок і згенеровані стовпці

    Header лише пропускає перший рядок файлу, назви колонок PostgreSQL не зіставляє. Колонки в CREATE TABLE мають іти в тому самому порядку, що й у CSV. Згенерований стовпець з практики 18 DB Browser теж вивантажить у файл, і імпорт зупиниться з помилкою extra data after last expected column: такий стовпець приберіть з файлу або оголосіть у PostgreSQL так само, згенерованим.

    Після імпорту порівняйте SELECT COUNT(*) кожної таблиці тут і в SQLite. Однакова кількість рядків ще не означає однакових значень, тому порівняйте ще суму якоїсь числової колонки й MAX(id) і перегляньте кілька рядків.

    Нехай таблицю owners створили заново, порожню, і імпортували з CSV двох власників з номерами 1 і 2:

    -- після імпорту CSV в owners рядки з id 1 і 2
INSERT INTO owners (last_name, first_name) VALUES ('Мельник', 'Ірина');

    ERROR:  duplicate key value violates unique constraint "owners_pkey"
DETAIL:  Key (id)=(1) already exists.

    Імпорт пройшов успішно, а помилка з’являється пізніше, на першому звичайному INSERT. Лічильник – окремий об’єкт і знає лише номери, які видав сам; COPY записав id прямо в таблицю, тож лічильник далі пропонує id = 1. Кожна невдала спроба теж забирає номер, тому другий INSERT впаде на id = 2, і лише третій пройде. Виправлення – один раз одразу після імпорту підняти лічильник до найбільшого наявного id:

    SELECT setval(pg_get_serial_sequence('owners', 'id'), (SELECT MAX(id) FROM owners));

    pg_get_serial_sequence('owners', 'id') знаходить назву лічильника колонки (public.owners_id_seq), setval ставить його на MAX(id), тобто 2. Після цього наступний INSERT без явного id отримує id = 3. Команду виконують для кожної таблиці окремо.

    Підсумок¶

    • PostgreSQL – клієнт-серверна СУБД з ієрархією: сервер, база даних, схема (public), таблиця; pgAdmin – її графічний клієнт, SQL пишемо в Query Tool, відкритому на своїй базі.
    • INTEGER PRIMARY KEY у PostgreSQL рядки не нумерує. Автоінкремент – GENERATED ALWAYS AS IDENTITY (у курсі) або старий SERIAL.
    • IDENTITY не приймає явний id у звичайному INSERT (обхід – OVERRIDING SYSTEM VALUE); SERIAL приймає мовчки.
    • Текст, що не є числом, у колонку INTEGER не потрапить; дріб у INSERT округлиться мовчки, а з CSV дасть помилку. BOOLEAN зберігає TRUE/FALSE, а не 1/0.
    • FOREIGN KEY перевіряється завжди, без PRAGMA: спершу виміри, потім фактова таблиця.
    • Назви без лапок стають малими літерами – snake_case курсу це не зачіпає.
    • Після імпорту рядків з явними id – setval(pg_get_serial_sequence(...), MAX(id)) для кожної таблиці, інакше наступний INSERT спробує повторити вже зайнятий id.

    Додаток. Як встановити PostgreSQL і pgAdmin¶

    Для практичних 19–24 потрібні сервер PostgreSQL 18 і pgAdmin 4. Нижче два способи: інсталятор (основний) і Docker (якщо Docker у вас уже є). Вистачить одного з них.

    Спосіб 1. Інсталятор (Windows, macOS)¶

    1. Відкрийте postgresql.org/download, виберіть свою систему й натисніть «Download the installer». Відкриється сайт EDB: завантажте PostgreSQL 18 для Windows x86-64 або для macOS.
    2. Запустіть інсталятор (потрібні права адміністратора) і пройдіть кроки:
      • Select Components – залиште PostgreSQL Server, pgAdmin 4 і Command Line Tools; Stack Builder не потрібен;
      • Data Directory – залиште як є;
      • Password – придумайте пароль користувача postgres і запишіть його: без нього pgAdmin не під’єднається;
      • Port – 5432; якщо інсталятор пропонує 5433, порт 5432 уже зайнятий іншим сервером (див. «Типові проблеми»);
      • Locale – Default locale.
    3. Після встановлення сервер працює як служба й запускається сам разом із комп’ютером. У Windows її видно в «Службах» під назвою postgresql-x64-18.
    4. Відкрийте pgAdmin 4. У дереві ліворуч у Servers уже є PostgreSQL 18: клацніть на нього й введіть пароль із кроку 2. Якщо сервера в дереві немає, додайте його вручну, як у кроці 3 способу 2.

    Спосіб 2. Docker¶

    Підходить, якщо Docker Desktop (або інша програма для контейнерів) у вас уже встановлена.

    1. Запустіть сервер у контейнері; пароль student замініть своїм:

      docker run --name pg18 -e POSTGRES_PASSWORD=student -p 5432:5432 -v pg18-data:/var/lib/postgresql -d postgres:18
      • --name pg18 – назва контейнера, за нею його зупиняють і запускають;
      • -e POSTGRES_PASSWORD=student – пароль користувача postgres;
      • -p 5432:5432 – порт 5432 вашого комп’ютера веде до сервера в контейнері;
      • -v pg18-data:/var/lib/postgresql – бази зберігаються в томі pg18-data і не зникнуть, навіть якщо контейнер видалити.

    2. Встановіть pgAdmin 4 окремо з pgadmin.org/download.

    3. У pgAdmin клацніть правою кнопкою на Servers, далі Register, Server:
      • вкладка General: Name – будь-яка назва, наприклад PostgreSQL 18 (Docker);
      • вкладка Connection: Host – localhost, Port – 5432, Username – postgres, Password – пароль із команди (можна позначити Save password); натисніть Save.
    4. Зупинити сервер – docker stop pg18, запустити знову – docker start pg18. Бази при цьому лишаються.

    Перевірка з’єднання¶

    Клацніть правою кнопкою на базі postgres, виберіть Query Tool і виконайте:

    SELECT version();

    Якщо результат починається з PostgreSQL 18., усе працює. Далі створіть свою базу, як описано в розділі 2.

    Типові проблеми¶

    • password authentication failed for user "postgres" – хибний пароль. Для інсталятора це пароль, заданий під час встановлення. Для Docker – пароль із першого запуску: якщо том pg18-data уже є, новий POSTGRES_PASSWORD у команді ігнорується.
    • Connection refused – сервер не запущено. У Windows запустіть службу postgresql-x64-18 у «Службах», для Docker виконайте docker start pg18.
    • Порт зайнятий. Інсталятор пропонує 5433, або Docker пише port is already allocated: на комп’ютері вже працює інший сервер PostgreSQL, наприклад і встановлений, і в контейнері. Зупиніть зайвий або запустіть контейнер на іншому порту: -p 5433:5432, і тоді в pgAdmin вкажіть порт 5433. Контейнер з помилкою спершу видаліть: docker rm pg18.

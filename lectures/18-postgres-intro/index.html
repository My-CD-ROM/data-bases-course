    Лекція 18. Перехід до PostgreSQL. Використання PgAdmin¶

    Модуль 4 переносить ту саму базу даних (ваш власний варіант, уже з трьома пов'язаними таблицями) на іншу СУБД — PostgreSQL. SQLite чудово підійшла для навчання основ SQL: файл, ніяких серверів, нуль налаштувань. Але Views, Functions, Procedures і Triggers (теми Лекцій 19-22) — це вже інструменти промислової, клієнт-серверної СУБД, і саме тому курс переходить на PostgreSQL. Ця лекція — не нова мова запитів (SQL лишається SQL), а різниця в архітектурі й кілька синтаксичних пасток при перенесенні вже готової схеми.

    1. SQLite проти PostgreSQL: не діалект, а архітектура¶

    SQLite — це один файл на диску: відкрив файл — отримав базу, без жодного сервера чи процесу, що працює постійно. PostgreSQL — клієнт-серверна СУБД: окремий процес (сервер) працює постійно й приймає з'єднання від багатьох клієнтів одночасно (саме це потрібно для Isolation з ACID, Лекція 13, у повноцінному багатокористувацькому сценарії). Замість одного файлу PostgreSQL організовує дані в ієрархію: сервер → база даних → схема → таблиця (у SQLite "сервер" і "база даних" — це просто файл, а "схеми" як окремого рівня немає).

    2. PgAdmin — інструмент цього модуля¶

    PgAdmin — офіційний графічний інструмент для PostgreSQL, аналог DB Browser for SQLite з попередніх модулів. У дереві зліва — Servers → ваш сервер → Databases → ваша база → Schemas → public → Tables — саме тут з'являться таблиці вашого варіанта. Вкладка Query Tool (права клавіша на базі → Query Tool) — прямий аналог "Execute SQL" у DB Browser: сюди пишеться і виконується будь-який SQL цієї лекції.

    3. Перша синтаксична відмінність: автоінкремент первинного ключа¶

    -- SQLite (Лекція 5): INTEGER PRIMARY KEY - псевдонім rowid, автоінкремент "з коробки"
CREATE TABLE owners (
    id INTEGER PRIMARY KEY,
    last_name TEXT NOT NULL
);

    -- PostgreSQL: явно вказати автоінкремент
CREATE TABLE owners (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    last_name TEXT NOT NULL
);

    У SQLite INTEGER PRIMARY KEY сам по собі є автоінкрементом (Лекція 5). У PostgreSQL звичайний INTEGER PRIMARY KEY не автоінкрементує — для цього потрібно явно дописати GENERATED ALWAYS AS IDENTITY (сучасний стандартний спосіб) — перевірено: після цього кожен INSERT без вказаного id отримує наступне число автоматично. Старіший, але й досі поширений варіант — псевдотип SERIAL PRIMARY KEY, який робить те саме "під капотом" (можна зустріти в чужому коді, але для нового коду курс використовує GENERATED ALWAYS AS IDENTITY).

    4. Друга відмінність: строга типізація¶

    INSERT INTO animals (name, age, owner_id) VALUES ('Рекс', 'п''ять', 1);

    ERROR: invalid input syntax for type integer: "п'ять"

    SQLite має гнучку "типову афінність" — типи колонок радше підказка, ніж жорстке правило. PostgreSQL — строго типізована СУБД: спроба вставити текст у колонку INTEGER завершується помилкою одразу (перевірено), а не мовчки якось "підлаштовується". Це загалом краще для цілісності даних, але означає: перенесені INSERT-и мають передавати значення саме тих типів, які оголошені в CREATE TABLE.

    5. Третя відмінність: FOREIGN KEY завжди активний¶

    INSERT INTO animals (name, age, owner_id) VALUES ('Мурка', 3, 999);

    ERROR: insert or update on table "animals" violates foreign key constraint
DETAIL: Key (owner_id)=(999) is not present in table "owners".

    У SQLite перевірка зовнішніх ключів вимикається за умовчанням і потребує PRAGMA foreign_keys = ON; на кожному з'єднанні (Лекція 5). У PostgreSQL перевірку FOREIGN KEY не потрібно вмикати окремо — вона активна завжди, без жодної додаткової команди (перевірено).

    6. Четверта відмінність: реальний тип BOOLEAN¶

    CREATE TABLE t (flag BOOLEAN);
INSERT INTO t VALUES (TRUE), (FALSE);

    На відміну від SQLite, де логічне значення зазвичай зберігають як INTEGER (0/1), PostgreSQL має справжній тип BOOLEAN зі значеннями TRUE/FALSE — зручно для колонок-прапорців (наприклад, замість похідного 0/1 з Лекції 17).

    7. Регістр ідентифікаторів — гарна новина для цього курсу¶

    PostgreSQL автоматично переводить неозначені (без лапок) назви таблиць і колонок у нижній регістр — перевірено: CREATE TABLE "TestTable" (...) (у лапках, регістр збережено) не знаходиться запитом SELECT * FROM TestTable (без лапок, PostgreSQL шукає testtable). Оскільки весь цей курс із самого початку використовує англійський snake_case без великих літер (розділ 9а домовленості), жодна вже написана назва таблиці чи колонки не постраждає при перенесенні — ця пастка стосується лише тих, хто називав об'єкти з великої літери чи в лапках.

    8. П'ята відмінність: перенесення даних зі старими id "збиває" автолічильник¶

    -- імпортовано рядки з явними id (1 і 2, зі старої SQLite-бази)
-- SELECT * FROM owners; --> (1, ...), (2, ...)

INSERT INTO owners (last_name, first_name) VALUES ('Новий', 'Клієнт');

    ERROR: duplicate key value violates unique constraint "owners_pkey"
DETAIL: Key (id)=(1) already exists.

    Ще одна пастка, специфічна саме для ПЕРЕНЕСЕННЯ вже наявних даних (а не для нової порожньої таблиці): якщо рядки імпортовано з явно вказаними значеннями id (наприклад, id = 1, 2 зі старої SQLite- бази), внутрішній лічильник GENERATED ALWAYS AS IDENTITY про це не дізнається і далі пропонує id = 1 для наступного INSERT — колізія з уже імпортованим рядком (перевірено відтворенням саме такого сценарію). Виправлення — один раз "підняти" лічильник до максимального вже наявного id одразу після імпорту:

    SELECT setval(pg_get_serial_sequence('owners', 'id'), (SELECT MAX(id) FROM owners));

    Перевірено: після цього наступний INSERT без явного id коректно отримує id = 3, а не знову 1.

    Підсумок¶

    • PostgreSQL — клієнт-серверна СУБД з ієрархією сервер → база даних → схема → таблиця; PgAdmin — її основний графічний інструмент, Query Tool — аналог "Execute SQL" з DB Browser.
    • Автоінкремент первинного ключа в PostgreSQL потрібно вказати явно — GENERATED ALWAYS AS IDENTITY (сучасний спосіб) чи SERIAL (старіший, теж поширений).
    • PostgreSQL строго типізована (помилка одразу на невідповідному типі) і завжди перевіряє FOREIGN KEY, без окремого PRAGMA.
    • Має реальний тип BOOLEAN; автоматично переводить неозначені ідентифікатори в нижній регістр — не проблема для вже написаного snake_case цього курсу.
    • Перенесення рядків з явним id "збиває" внутрішній лічильник GENERATED ALWAYS AS IDENTITY — після імпорту потрібно один раз підняти його через setval(pg_get_serial_sequence(...), MAX(id)), інакше наступний INSERT спробує повторити вже зайнятий id.

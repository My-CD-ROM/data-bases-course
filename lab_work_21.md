# Практика 21. Написання функцій у PostgreSQL

Середовище: PostgreSQL 16, база з Практики 19/20 (`owners`, `animals`, `vet_visits`). Усі команди, виклики й точні тексти помилок – у `lab_work_21.sql`.

## Завдання 2. Функція з умовною логікою

Функція `age_category(age_years INTEGER)` повертає категорію за віком:

| Умова | Категорія |
|-------|-----------|
| `age IS NULL` | невідомо |
| `age < 1` | малюк |
| `1 <= age < 7` | дорослий |
| `age >= 7` | старший |

Перевірка на граничних значеннях (`SELECT ... FROM (VALUES ...)`):

| age | результат | Чи відповідає межам |
|-----|-----------|---------------------|
| 0 | малюк | так |
| 1 | дорослий | так: `1 < 1` хибно, тож вік 1 уже «дорослий» |
| 6 | дорослий | так: верхня межа «дорослого» |
| 7 | старший | так: `7 < 7` хибно, тож вік 7 уже «старший» |
| NULL | невідомо | так, завдяки окремій гілці |

Межі «ліворуч закриті, праворуч відкриті»: `[0;1)`, `[1;7)`, `[7;∞)`. Гілку `IS NULL` треба ставити **першою**. Інакше умова `NULL < 1` дає не `TRUE`, а `NULL`, тож гілка пропускається, і `NULL` потрапив би в `ELSE` та помилково став би «старшим». У таблиці `animals` значень 0 і `NULL` немає, тому ці випадки перевірено на списку `VALUES`.

## Завдання 3. Функція, що повертає таблицю

`animals_by_species(p_species TEXT)` повертає `id`, `name`, `age` тварин заданого виду. Виклик `SELECT * FROM animals_by_species('кіт')` дав 4 рядки: Барсик, Мурка, Лаки, Софі.

Результат **збігається** з прямим `SELECT id, name, age FROM animals WHERE species = 'кіт'`. Підтверджено двома способами:
- візуально, бо обидва запити повернули ті самі 4 рядки;
- запитом з `EXCEPT` в обидва боки, який повернув 0 рядків: жодного рядка, що є в одному результаті й відсутній в іншому.

**Важливо.** Версія з прикладу лекції (`name TEXT`) у моїй базі **не спрацювала**, бо колонка `name` має тип `VARCHAR(50)`:

```
ERROR:  structure of query does not match function result type
DETAIL:  Returned type character varying(50) does not match expected type text in column 2.
```

Тому в робочій функції в `RETURNS TABLE` оголошено `name VARCHAR`. Альтернатива – писати `a.name::TEXT` у запиті.

## Завдання 4. Свідома помилка: COMMIT у функції

Функція `bad_commit` робить `UPDATE`, а потім `COMMIT`. `CREATE FUNCTION` проходить успішно, а виклик `SELECT bad_commit(1);` дає точну помилку:

```
ERROR:  invalid transaction termination
CONTEXT:  PL/pgSQL function bad_commit(integer) line 4 at COMMIT
```

Зміну не збережено: вік Барсика (id = 1) залишився 3.

**Чому функції заборонено керувати транзакцією.** Функція завжди викликається всередині чужої команди (наприклад, `SELECT` або `WHERE`) і сама є частиною однієї транзакції. Якби вона зробила `COMMIT`, то зафіксувала б і розірвала транзакцію викликача, а той міг уже виконати частину роботи (або мав би відкотити її цілком). Це зламало б атомарність. Керувати транзакціями можуть процедури (`CREATE PROCEDURE`, виклик через `CALL`), які виконуються як окрема команда верхнього рівня.

## Завдання 5. Функція в WHERE

Запит `WHERE age_category(age) = 'старший'` повернув Бім (7 років). Розгорнутий `CASE` у `WHERE` повернув той самий рядок.

**Зрозумілість.** Запис із функцією читається як опис: «категорія – старший». Правило класифікації записано в одному місці, його не треба повторювати в кожному запиті. Версія з `CASE` займає 5 рядків, дублює межі й легко розходиться з іншими запитами (досить помилитися в одній цифрі). Мінус функції: щоб побачити саму логіку, треба відкрити її код.

**Індекс.** Звичайний індекс по `age` (`idx_animals_age`) пришвидшує фільтр по самій колонці (`WHERE age >= 7`), але **не допомагає** умові `age_category(age) = ...`, бо планувальник не знає, як значення функції пов'язане зі значенням колонки. Допомогти може лише індекс за виразом:
- для функції за замовчуванням (`VOLATILE`) його не створити: `ERROR: functions in index expression must be marked IMMUTABLE`;
- після позначки `IMMUTABLE` індекс `idx_animals_age_cat` створюється, і в плані з'являється `Index Scan using idx_animals_age_cat` (на малій таблиці я вимикав `seqscan`, щоб це побачити).

Позначати функцію `IMMUTABLE` можна лише тоді, коли її результат залежить виключно від аргументів і ніколи не змінюється. Для `age_category` це так.

## Завдання 6. Точний збіг типів у RETURN QUERY

Функція `species_summary_bad` має `RETURNS TABLE(species VARCHAR, cnt INTEGER)`, а `COUNT(*)` повертає `BIGINT`. `CREATE FUNCTION` проходить, а виклик дає помилку:

```
ERROR:  structure of query does not match function result type
DETAIL:  Returned type bigint does not match expected type integer in column 2.
```

Виправлення (обидва працюють і повертають кіт – 4, папуга – 1, собака – 4):
1. `COUNT(*)::INTEGER` у запиті (`species_summary_cast`);
2. `cnt BIGINT` в оголошенні (`species_summary_bigint`).

**Інші типи.**
- `VARCHAR` проти `TEXT`: колонка `species` має тип `VARCHAR(30)`. Оголошення `species TEXT` дало помилку `Returned type character varying(30) does not match expected type text in column 1`. Тобто `VARCHAR` і `TEXT` теж треба узгоджувати (приведенням `::TEXT` або типом `VARCHAR` в оголошенні). Тип `VARCHAR` без довжини підходить для `VARCHAR(30)`.
- `NUMERIC` проти `REAL`: `AVG(a.age)` повертає `NUMERIC`. Оголошення `avg_age REAL` дало помилку `Returned type numeric does not match expected type real in column 2`. Виправлення: `AVG(a.age)::REAL`.
- `INTEGER` для `id` і `age` збігається з колонками таблиці, тут проблем немає.

## Відповіді на контрольні питання

**1. Чим `RETURNS TABLE(...)` відрізняється від `RETURNS INTEGER`/`RETURNS TEXT`?**
Скалярна функція повертає одне значення, і її використовують як вираз: у `SELECT`-списку, у `WHERE`, у `ORDER BY` (наприклад, `age_category(age)`). Функція з `RETURNS TABLE` повертає набір рядків і колонок, тому її викликають у `FROM` як таблицю: `SELECT * FROM animals_by_species('кіт')`. Результат можна фільтрувати, сортувати, поєднувати через `JOIN`, групувати, як звичайну таблицю.

**2. Чому помилка із завдання 4 виникає під час виклику, а не під час `CREATE FUNCTION`?**
Під час `CREATE FUNCTION` PostgreSQL перевіряє лише синтаксис тіла PL/pgSQL. Допустимість керування транзакцією залежить від контексту, з якого функцію викличуть, а він невідомий до самого виклику. Так само виконуються й перевірки типів у `RETURN QUERY`: вони теж спрацьовують лише під час виклику.

**3. Яка з функцій 1–3 могла б замінити подання з Практики 20, а яка ні?**
Подання з Практики 20 (`animals_active`) повертає набір рядків за фільтром, тож його може замінити `animals_by_species` (завдання 3): вона так само віддає відфільтровану таблицю, до того ж із параметром. Скалярні функції `age_in_months` і `age_category` не можуть: вони повертають одне значення для одного вхідного значення, а не набір рядків, і самі нічого не фільтрують. Їх можна використати всередині подання або запиту (наприклад, у `WHERE`).

**4. Чому `COUNT(*)` не можна повернути в колонку `INTEGER` без приведення?**
Бо `COUNT(*)` повертає `BIGINT`, а `RETURN QUERY` вимагає точного збігу типів колонок запиту й оголошення `RETURNS TABLE`. Автоматичного звуження `BIGINT` до `INTEGER` тут немає, тому потрібно або привести значення (`::INTEGER`), або оголосити колонку як `BIGINT`.

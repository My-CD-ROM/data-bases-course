# Практика 22. Створення процедур у PostgreSQL

Середовище: PostgreSQL 16, база з Практик 19–21 (`owners`, `animals`, `vet_visits`). Атомарна пара змін: `INSERT` у `vet_visits` (факт) + `UPDATE animals SET status = 'на лікуванні'` (пов'язаний рядок). Усі команди й точні тексти помилок – у `lab_work_22.sql`.

## Завдання 2. Свідомі помилки виклику

**1. `SELECT` замість `CALL`:**

```
ERROR:  register_visit(integer, unknown) is a procedure
LINE 1: SELECT register_visit(2, 'отит');
               ^
HINT:  To call a procedure, use CALL.
```

**2. `CALL` з меншою кількістю аргументів (1 замість 2):**

```
ERROR:  procedure register_visit(integer) does not exist
LINE 1: CALL register_visit(2);
             ^
HINT:  No procedure matches the given name and argument types. You might need to add explicit type casts.
```

**Чому в другому випадку процедуру не знайдено.** PostgreSQL шукає процедуру не лише за назвою, а за назвою разом із кількістю та типами параметрів (сигнатурою). У базі є `register_visit(integer, text)`, а виклик має сигнатуру `register_visit(integer)`. Такої комбінації немає, тому відповідник не знайдено. Параметрам `register_visit` не задано `DEFAULT`, тож пропустити другий аргумент не можна. Перший випадок інший: назва й сигнатура знайшлись, але PostgreSQL розпізнав об'єкт як процедуру, яку не можна викликати в запиті, і підказав `CALL`.

## Завдання 4. OUT-параметр

Процедура `register_visit_ret(p_animal_id, p_diagnosis, OUT p_visit_id)` виконує ту саму пару змін і через `INSERT ... RETURNING id INTO p_visit_id` повертає id нового візиту. Виклик `CALL register_visit_ret(4, 'перелом лапи', NULL);` повернув `p_visit_id = 6`. Контрольний `SELECT MAX(id) FROM vet_visits` також дав **6**, тобто значення збігається.

Без заповнювача на місці OUT-параметра виклик не працює: `procedure register_visit_ret(integer, unknown) does not exist`. Для PostgreSQL OUT-параметр входить у список аргументів `CALL`.

**Результат `\df register_visit*`:**

| Name | Argument data types | Type |
|------|---------------------|------|
| register_visit | `IN p_animal_id integer, IN p_diagnosis text` | proc |
| register_visit_ret | `IN p_animal_id integer, IN p_diagnosis text, OUT p_visit_id integer` | proc |

Колонка `Result data type` порожня в обох, а `Type` = `proc` (у функцій було б `func`). Режими параметрів позначені явно: `IN` для вхідних, `OUT` для `p_visit_id`.

## Завдання 5. Порівняння з Практикою 14

**Що процедура дозволяє не повторювати.** У Практиці 14 кожну пару змін доводилося щоразу писати вручну: `BEGIN`, `INSERT`, `UPDATE`, `COMMIT`, кожного разу з потрібними значеннями. Тепер це один рядок `CALL register_visit(2, 'отит')`. Текст обох запитів, їхній порядок і значення зі статусом (`'на лікуванні'`) записані в процедурі один раз. Не можна забути другий запит, переплутати порядок або по-різному написати статус у різних місцях.

**Де тепер зберігається перевірка вхідних даних.** У самому тілі процедури (`IF ... RAISE EXCEPTION` на початку). Вона діє для кожного виклику, звідки б його не зробили. У Практиці 14 перевірка (якщо вона була) лежала в голові або в окремому скрипті клієнта, і кожен міг її пропустити. Помилка з пояснювальним текстом (`Діагноз не може бути порожнім (тварина 4)`) перериває виконання до будь-яких змін.

**Що гарантує атомарність без `BEGIN`/`COMMIT`.** Команда `CALL` сама виконується як одна транзакція: PostgreSQL відкриває її на час виклику і фіксує, якщо процедура завершилась без помилки. Якщо будь-який крок кине помилку, відкочується все, що виклик встиг зробити. Це підтверджує додатковий дослід у `.sql`: у процедурі `register_visit_fail` `INSERT` у `vet_visits` виконався, а наступний `UPDATE ... age / 0` дав `division by zero`. Після цього в `vet_visits` залишилось ті самі 6 рядків, що й до виклику, тобто перша зміна скасована. Окремі `BEGIN`/`COMMIT` усередині процедури для цього не потрібні.

## Відповіді на контрольні питання

**1. Чим відрізнявся б виклик, якби це була функція `RETURNS VOID`, і чому для дії, що змінює дані, обирають процедуру?**
Функцію викликають у запиті: `SELECT register_visit(2, 'отит');` (на відміну від `CALL`), і результатом буде порожній рядок. Процедуру викликають окремою командою `CALL`. Для дії, що змінює дані, процедура доречніша: вона виразно позначена як самостійна дія, а не обчислення в запиті. Її не можна випадково вставити у `SELECT` чи `WHERE` (де її побічні ефекти виконувались би для кожного рядка), і саме процедури можуть керувати транзакціями (Практика 23). Крім того, вона підтримує OUT/INOUT-параметри для повернення результатів.

**2. Що станеться з першою зміною (`INSERT`), якщо `UPDATE` у тому самому виклику завершиться помилкою?**
`INSERT` буде скасовано. `CALL` виконується як одна транзакція, і помилка в будь-якому кроці відкочує весь виклик, зокрема й кроки, що вже виконались. У досліді з `register_visit_fail` кількість візитів до і після виклику однакова (6).

**3. Чому перевірку ставлять на початок тіла, а не після `INSERT` і `UPDATE`?**
Щоб помилка виникла до будь-яких змін і не довелося нічого відкочувати. Так процедура не виконує зайвої роботи, а перша ж некоректна умова одразу зупиняє виклик із зрозумілим повідомленням. Перевірка після змін спрацювала б запізно: рядки вже вставлено, і єдиним порятунком став би відкіт транзакції.

**4. Навіщо у `CALL` передавати `NULL` на місці OUT-параметра і чим OUT відрізняється від INOUT?**
OUT-параметр входить у сигнатуру процедури, тому без заповнювача PostgreSQL не знайде процедуру (`does not exist`). `NULL` лише займає місце, його значення процедура ігнорує й замінює результатом. OUT тільки повертає значення з процедури: усередину воно не передається. INOUT робить обидва: значення передають усередину, а після виклику отримують нове (наприклад, у `set_status` з теорії повертається попередній статус).

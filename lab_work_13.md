# Практична робота 13. Форматування таблиць за допомогою printf і дат

**Варіант 3 — база даних кінотеатру.** Використано фактова таблиця `tickets`, колонки `price` та `purchase_date`. Структура бази не змінювалася.

## Завдання 1. printf() для числової колонки

```sql
SELECT id, price, printf('%.2f грн', price) AS formatted_price
FROM tickets ORDER BY id;
```

| id | Сире значення | Форматований результат |
|---:|---:|---|
| 1 | 180.0 | 180.00 грн |
| 2 | 200.0 | 200.00 грн |
| 3 | 170.0 | 170.00 грн |
| 4 | 150.0 | 150.00 грн |
| 5 | 190.0 | 190.00 грн |

`%.2f` виводить число з рівно двома знаками після крапки. Додавання `грн` пояснює одиницю виміру. Сире значення може мати інший вигляд, а форматований результат є однаковим і зрозумілішим для читача. У консолі `грн` могло відобразитися як `???` через кодування, але числові результати правильні.

## Завдання 2. printf() з вирівнюванням

```sql
SELECT id, price, printf('%8.2f грн', price) AS formatted_price
FROM tickets ORDER BY id;
```

Результати: `  180.00 грн`, `  200.00 грн`, `  170.00 грн`, `  150.00 грн`, `  190.00 грн`.

`%8.2f` задає мінімальну ширину числового поля 8 символів і два знаки після крапки. Якщо число коротше, зліва додаються пробіли. Це полегшує візуальне вирівнювання значень у текстовому звіті або моноширинному виводі, хоча в табличному інтерфейсі ефект може бути менш помітним.

## Завдання 3. Зсув дати на 30 днів

```sql
SELECT id, purchase_date, date(purchase_date, '+30 days') AS date_after_30_days
FROM tickets ORDER BY id;
```

| id | Дата покупки | Дата через 30 днів |
|---:|---|---|
| 1 | 2026-09-28 | 2026-10-28 |
| 2 | 2026-09-29 | 2026-10-29 |
| 3 | 2026-09-29 | 2026-10-29 |
| 4 | 2026-09-30 | 2026-10-30 |
| 5 | 2026-09-30 | 2026-10-30 |

`date(purchase_date, '+30 days')` обчислює дату через 30 днів після покупки. У системі кінотеатру таку дату можна використати як умовну контрольну дату для нагадування чи аналізу періоду після придбання квитка. Початкова дата в таблиці не змінюється.

## Завдання 4. strftime() і групування за роком

```sql
SELECT strftime('%Y', purchase_date) AS purchase_year, COUNT(*) AS tickets_count
FROM tickets
GROUP BY purchase_year
ORDER BY purchase_year;
```

| Рік | Кількість квитків |
|---|---:|
| 2026 | 5 |

`strftime('%Y', purchase_date)` витягує рік із повної дати. Групування за повною датою створило б окремі групи для різних днів, а групування за роком об'єднує покупки одного року. Тому використовується результат `strftime()`.

## Завдання 5. Свідома помилка з некоректною датою

```sql
SELECT strftime('%Y', 'not-a-date'), date('not-a-date');
```

Фактичний результат у Python: `(None, None)`. SQLite не видала помилку виконання, а повернула `NULL` для обох виразів (`None` — представлення SQL NULL у Python). Це не можна вважати автоматичною перевіркою коректності вхідних дат: некоректний рядок не перетворюється на дату, але запит завершується.

## Контрольні питання

**1. Чим printf() відрізняється від зміни значення в таблиці?**  
`printf()` змінює лише представлення значення в результаті запиту. Фізичне значення колонки не змінюється. Для зміни даних потрібна окрема команда, наприклад `UPDATE`.

**2. Чому strftime('%Y', ...) повертає рік як текст?**  
`strftime()` формує текстове представлення частини дати відповідно до шаблону. Текстові значення порівнюються як рядки, а не як числа. Для чотиризначних років однакового формату текстове сортування зазвичай збігається з хронологічним, але для арифметичних операцій може знадобитися перетворення типу.

**3. Що результат Завдання 5 означає для CHECK-обмежень?**  
Потрібно явно перевіряти допустимість дати та враховувати `NULL`. Сам виклик `date()` або `strftime()` не гарантує коректності введення, оскільки некоректний рядок може дати `NULL`. Для обов'язкових дат також доречно передбачити `NOT NULL`.

## Висновок

У роботі застосовано `printf()` для форматування ціни та вирівнювання, `date()` для обчислення дати через 30 днів і `strftime()` для отримання року та групування квитків. Перевірка некоректної дати показала, що SQLite повертає `NULL`, а не обов'язково повідомляє про помилку. Тому введення дат потрібно перевіряти окремо.

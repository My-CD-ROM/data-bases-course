# Практика 3. ER-діаграма

**Варіант: 1 — Бібліотека**

Таблиці мого варіанта:

* `books` — вимірна таблиця 1
* `readers` — вимірна таблиця 2
* `loans` — фактова таблиця (з'єднує books і readers)

## Завдання 1. ER-діаграма повної схеми

///
erDiagram
    books ||--o{ loans : "видана в"
    readers ||--o{ loans : "оформлює"

    books {
        int id PK
        string title
        string author
        int publication\_year
        string genre
        int copies\_count
    }

    readers {
        int id PK
        string last\_name
        string first\_name
        string email
        date registration\_date
    }

    loans {
        int id PK
        int book\_id FK
        int reader\_id FK
        date loan\_date
        date return\_date
    }
///

## Завдання 2. Тип кожного зв'язку

**books — loans: 1:N**
Одна книга (наприклад, "Кобзар") може бути видана нуль, один або багато разів різним читачам — тобто в таблиці `loans` може бути багато записів з одним і тим самим `book\_id`. Але кожен конкретний запис у `loans` стосується рівно однієї книги. Тому зв'язок 1:N (один до багатьох), напрямок — від `books` до `loans`.

**readers — loans: 1:N**
Один читач (наприклад, Іваненко Іван) може взяти книги багато разів (або жодного разу, якщо він щойно зареєструвався) — тобто в `loans` може бути багато записів з одним і тим самим `reader\_id`. Але кожен конкретний запис у `loans` — це видача рівно одному читачеві. Тому зв'язок теж 1:N, напрямок — від `readers` до `loans`.

Обидва зв'язки — 1:N, як і вказано в умові для всіх варіантів курсу.Завдання 3. Первинні й зовнішні ключі кожної таблиці

**books**

* Первинний ключ (PK): `id`
* Зовнішніх ключів немає

**readers**

* Первинний ключ (PK): `id`
* Зовнішніх ключів немає

**loans**

* Первинний ключ (PK): `id`
* Зовнішній ключ (FK): `book\_id` → посилається на `books.id`
* Зовнішній ключ (FK): `reader\_id` → посилається на `readers.id`

## Завдання 4. Якщо додати ще одну сутність

Я б додав сутність **publishers** (видавництва): `id, name, city, founded\_year`.

Кожна книга видана рівно одним видавництвом, а одне видавництво могло видати багато книг. Тому новий зв'язок буде **publishers — books, 1:N** (одне видавництво — багато книг). У таблиці `books` з'явиться новий зовнішній ключ `publisher\_id`, який посилатиметься на `publishers.id`. Пряма таблиця `publishers` не буде пов'язана з `readers` чи `loans` напряму — тільки через `books`.

## Завдання 5. Порівняння з прикладом (хімчистка)

Моя діаграма побудована за тією самою структурою, що й приклад із хімчисткою:

* В обох є дві вимірні таблиці (у мене — `books` і `readers`, у прикладі — `services` і `clients`) і одна фактова таблиця з двома зовнішніми ключами (`loans` і `orders` відповідно).
* В обох випадках обидва зв'язки — 1:N: вимірна таблиця "один", фактова — "багато".
* В обох випадках дві вимірні таблиці не з'єднані напряму — `books` і `readers` (як і `services` та `clients`) пов'язані лише через фактову таблицю `loans` (відповідно `orders`), яка виконує роль "мосту" між ними.

Тобто структура однакова, різняться лише назви сутностей і атрибутів, бо предметна область інша.

## Контрольні питання

**1. Чим логічна модель відрізняється від концептуальної, і чим фізична — від логічної?**

Концептуальна модель — це найпростіший опис предметної області "людською мовою": які є сутності (наприклад, "книга", "читач") і як вони пов'язані, без жодних технічних деталей.

Логічна модель — це вже конкретна ER-діаграма з назвами таблиць, стовпців, типами даних на абстрактному рівні (int, string, date), позначеними PK і FK — але ще без прив'язки до конкретної СУБД.

Фізична модель — це те, як логічна модель реально втілена в конкретній базі даних: точні типи цієї СУБД (наприклад, у SQLite — INTEGER, TEXT, а не просто "int" чи "string"), реальний SQL-код `CREATE TABLE`, індекси тощо.

**2. Чому зв'язок M:N не можна реалізувати двома зовнішніми ключами в одній із двох основних таблиць і завжди потрібна окрема таблиця?**

Якщо зв'язок M:N (багато-до-багатьох), то один рядок з таблиці A може бути пов'язаний з багатьма рядками таблиці B, і навпаки. Якщо покласти зовнішній ключ просто в таблицю A чи B, то в одному стовпці можна зберегти лише одне значення — тобто одна книга змогла б посилатись лише на одного читача (або навпаки), а не на багатьох одночасно. Тому потрібна окрема допоміжна (сполучна) таблиця, в якій кожен рядок — це одна конкретна пара "A + B", і саме вона може містити скільки завгодно комбінацій.

**3. Що означають позначення ||, o{, |{ у синтаксисі mermaid erDiagram, і як прочитати вголос рядок A ||--o{ B?**

* `||` означає "рівно один" (обов'язково один, не менше і не більше).
* `o{` означає "нуль або багато".
* `|{` означає "один або багато" (мінімум один).

Рядок `A ||--o{ B` читається так: "рівно один запис A відповідає нулю або багатьом записам B" — тобто це зв'язок 1:N, де A — вимірна таблиця ("один"), а B — фактова таблиця ("багато").

Створення ER-діаграми
Варіант 2 — Інтернет-магазин одягу
Завдання 1. ER-діаграма
Для мого варіанта потрібно створити ER-діаграму для інтернет-магазину одягу. Я використав три таблиці: products, customers і orders.

erDiagram
    products ||--o{ orders : "замовляється"
    customers ||--o{ orders : "оформлює"

    products {
        int id PK
        string name
        string category
        string size
        real price
        int stock_quantity
    }

    customers {
        int id PK
        string last_name
        string first_name
        string email
        string city
    }

    orders {
        int id PK
        int product_id FK
        int customer_id FK
        date order_date
        int quantity
        string status
    }

У таблиці products зберігається інформація про одяг: назва, категорія, розмір, ціна та кількість товару на складі.
У таблиці customers зберігається інформація про покупців: прізвище, ім'я, електронна пошта та місто.
У таблиці orders записується інформація про замовлення. Вона має два зовнішні ключі: product_id пов'язаний з таблицею products, а customer_id — з таблицею customers.

Завдання 2. Тип кожного зв'язку
products — orders: 1
Один товар може бути замовлений багато разів різними покупцями. Але одне замовлення в цій моделі містить один товар. Тому зв'язок є 1.
customers — orders: 1
Один покупець може зробити багато замовлень. Кожне замовлення при цьому належить одному покупцю. Тому тут також зв'язок 1.

Завдання 3. Первинні й зовнішні ключі
Таблиця products:
первинний ключ — id;
зовнішніх ключів немає.
Таблиця customers:
первинний ключ — id;
зовнішніх ключів немає.
Таблиця orders:
первинний ключ — id;
product_id — зовнішній ключ, який посилається на products.id;
customer_id — зовнішній ключ, який посилається на customers.id.

Завдання 4. Якщо додати ще одну сутність
Я б додав до магазину таблицю categories, яка буде зберігати категорії одягу.
Наприклад:
categories(id, name, description)
У таблиці products тоді можна додати поле category_id, яке буде посилатися на categories.id.
Зв'язок між categories і products буде 1, тому що одна категорія може містити багато товарів, а один товар належить одній категорії.

Завдання 5. Порівняння з прикладом «Хімчистка»
Моя діаграма схожа на приклад з хімчисткою тим, що в обох випадках є дві основні таблиці та одна таблиця, яка їх пов'язує.
У моєму варіанті це products, customers і orders. У прикладі з хімчисткою — services, clients і orders.
В обох схемах фактова таблиця має два зовнішні ключі. Також обидва зв'язки мають тип 1.
Прямого зв'язку між двома основними таблицями немає. Вони пов'язані між собою через таблицю orders.

Контрольні питання
1. Чим логічна модель відрізняється від концептуальної, і чим фізична — від логічної?
Концептуальна модель показує основні сутності предметної області та зв'язки між ними без великої кількості технічних деталей.
Логічна модель вже показує таблиці, поля, первинні та зовнішні ключі. У цій роботі я створював саме таку структуру.
Фізична модель показує, як ця база буде реально створена в конкретній СУБД. Тут вже враховуються конкретні типи даних, обмеження, індекси та інші налаштування.
2. Чому зв'язок M не можна реалізувати двома зовнішніми ключами в одній із двох основних таблиць і завжди потрібна окрема таблиця?
Зв'язок M означає, що багато записів першої таблиці можуть бути пов'язані з багатьма записами другої таблиці.
Двома звичайними зовнішніми ключами в одній таблиці це зробити незручно, тому що потрібно зберігати багато різних пар зв'язків. Тому створюють окрему проміжну таблицю, у якій зберігаються зовнішні ключі обох таблиць.
Таким чином, зв'язок M перетворюється на два зв'язки 1.
3. Що означають позначення ||, o{, |{ у Mermaid erDiagram?
|| означає рівно один.
o{ означає нуль або багато.
|{ означає один або багато.
Наприклад, A ||--o{ B означає, що одному запису A може відповідати нуль або багато записів B. Це зв'язок 1.
